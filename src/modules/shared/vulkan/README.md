# Native Vulkan libraries

MacLauncher runs Vulkan on macOS through two implementations that translate it to Metal: MoltenVK and KosmicKrisp. Both appear under Graphics in Runtimes and are installed from versioned publisher binaries, together with their license notices. Settings can read the available versions without downloading any files.

Android selects a native Vulkan implementation for each game. With Automatic, it uses an installed MoltenVK version first, then an installed KosmicKrisp version, and then, when it is compatible, an installed KosmicKrisp GLES 3.2 build (described below). Every implementation runs with the architecture of the host process. The Windows Wine runtime, by contrast, keeps its own graphics package and architecture choices.

The two implementations are loaded differently. MoltenVK's dynamic library is loaded directly, whereas KosmicKrisp is reached through the Khronos Vulkan loader and a private ICD manifest that names the selected driver. The driver and loader binaries that are installed from Runtimes have no native dependencies other than system libraries. The GLES 3.2 build, however, carries its compiler and compression dependencies inside its own package and refers to them with relative library paths. Each component is also checked against the current CPU architecture and macOS version. Game sandboxes can read the selected library files and map them as executable code, without access to their parent runtime directories.

The components come from different sources. MoltenVK downloads come from the KhronosGroup releases. KosmicKrisp comes from the versioned LWJGL native distribution, where each version is identified by its release tag and source commit, while the GLES 3.2 packages record their Mesa source separately. The Vulkan loader is Homebrew's published Vulkan-Loader binary bottle and keeps its original license. Every versioned file is protected by its publisher's checksum or by a SHA-256 identity recorded at installation, and installation keeps only the native libraries and their notices.

MacLauncher also supplies Vulkan features that upstream KosmicKrisp lacks, so that ANGLE's Vulkan renderer can use them to provide OpenGL ES 3.2, including tessellation, geometry and compute shaders. These features come in an optional build, **KosmicKrisp GLES 3.2**, which is MacLauncher's adaptation of Mesa. The added features are geometry shaders, transform feedback and generated-primitive queries. For these, the build uses Mesa Poly together with KosmicKrisp's original shader compiler and GPU command encoders. Unmodified KosmicKrisp versions keep their publisher identity and feature set. On Android, ANGLE still renders through Metal by default; when its Vulkan renderer is selected instead, that renderer runs on the chosen Vulkan component.

KosmicKrisp GLES 3.2 requires Apple Silicon and macOS 26 or later, and each package states its own minimum. MacLauncher Builds publishes it as a package, which can be installed from the Graphics section in Runtimes. A package may also include an Intel (x86-64) build for processes that run as x86-64 code, such as Wine. Before the package is installed, MacLauncher checks the downloaded archive against its SHA-256 in the catalog and verifies the code signatures of its native files. An installed version then works offline. Alongside the native libraries, the package also installs its license notices and the records that identify its dependencies. The source, including MacLauncher's adaptations, is available in the tagged Builds repository.

The Vulkan packages that MacLauncher Builds publishes are built by its [recipes](https://github.com/procrastinine/maclauncher-builds/tree/main/runtimes), which also record their Vulkan sources.

Android maps `VK_KHR_android_surface` to the selected driver's `VK_EXT_metal_surface`. The driver owns the Vulkan queues, images, swapchains and synchronization, and its Metal carrier layer registers with the common graphics presenter. Each completed frame therefore follows the same Android overlay and graphics pipeline as EGL and Canvas frames. When the native window is resized, the carrier's source extent is updated independently of the display extent. Presentation borrows GPU resources until their commands complete, and it makes no CPU copy of the image for each frame.
