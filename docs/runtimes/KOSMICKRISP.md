# KosmicKrisp

macOS has no Vulkan driver of its own. Vulkan games, the Vulkan-based Direct3D translators in Wine and ANGLE's Vulkan renderer for Android therefore depend on a driver that implements Vulkan on Metal, and MacLauncher offers two: MoltenVK and KosmicKrisp. KosmicKrisp is also available as **MacLauncher KosmicKrisp**, an adapted build that adds the Vulkan features which DXVK, vkd3d-proton and ANGLE use. On this build, vkd3d-proton runs Direct3D 12 games in CrossOver and Sikarugir and reports Direct3D feature level 12_1, as [Direct3D feature levels](#direct3d-feature-levels) describes. vkd3d-proton is the Direct3D 12 translator of Valve's [Proton](https://github.com/ValveSoftware/Proton), which runs Direct3D 12 games on Linux and the Steam Deck, so a game for which vkd3d-proton is selected takes the same Direct3D 12 path as under Proton. On upstream KosmicKrisp and MoltenVK, vkd3d-proton cannot create a device.

## What KosmicKrisp is

[KosmicKrisp](https://docs.mesa3d.org/drivers/kosmickrisp.html) is a Vulkan driver in the [Mesa](https://mesa3d.org/) project, developed by LunarG for Apple Silicon Macs. Khronos has [announced](https://www.khronos.org/news/permalink/kosmickrisp-achieves-vulkan-1.4-conformance-on-apple-silicon) that it passed the Vulkan 1.4 conformance tests and is a conformant Vulkan 1.4 implementation on Apple Silicon; an earlier version was conformant to Vulkan 1.3. The Vulkan 1.4 entry in the Khronos list of conformant products is submission 997, which covers the A18 Pro and the M1, M2, M3, M4 and M5 families, each with its Pro and Max variants, on macOS 27. LunarG's Vulkan SDK for macOS includes KosmicKrisp as a Vulkan 1.4 driver and keeps MoltenVK for Intel Macs and earlier macOS versions. Because the driver is built on Metal 4, it requires macOS 26 or later, and it runs only on Apple Silicon. Mesa's documentation states that it has no iOS support.

Metal 4 shapes how the driver works. Vulkan command buffers are recorded into Metal 4 command buffers and submitted through Metal 4 command queues. A single Metal 4 compute encoder carries compute dispatches together with buffer and texture copies, render passes use Metal 4 render encoders, and resources are bound through argument tables and residency sets. Shaders pass through Mesa's NIR into the Metal Shading Language, version 4.0 on macOS 26 and 4.1 on macOS 27 and later, and Metal 4's compiler interface compiles them.

KosmicKrisp does not expose `VK_KHR_portability_subset`, the extension through which a Vulkan implementation lists the parts of Vulkan that it leaves out. Applications and the Vulkan loader therefore treat it as an ordinary Vulkan driver.

## KosmicKrisp and MoltenVK

[MoltenVK](https://github.com/KhronosGroup/MoltenVK) is the older Vulkan driver for macOS. Its README describes it as a layered implementation of Vulkan 1.4 on Metal that is not fully compliant with the Vulkan specification, and it reports what it omits through `VK_KHR_portability_subset`. MoltenVK runs on Intel and Apple Silicon Macs from macOS 12. The MoltenVK README also states that Khronos has deprecated MoltenVK and that the repository is maintained by the community on a best-effort basis. According to the same notice, Khronos recommends KosmicKrisp for Vulkan on Apple Silicon Macs, while MoltenVK remains the recommended option for Intel-based Macs and iOS.

MacLauncher uses both drivers. MoltenVK serves Intel Macs, macOS versions before 26 and virtual machines, since KosmicKrisp needs Metal 4 on physical Apple Silicon hardware. It is also the driver that CrossOver includes, and native ART execution on Android requires its Metal texture attachment interface. On an Apple Silicon Mac with macOS 26 or later, KosmicKrisp is available as well.

MacLauncher can install two KosmicKrisp builds, and a third comes with Sikarugir:

| Build | Source | CPU builds |
| --- | --- | --- |

Each build needs a Khronos Vulkan loader beside the driver. LWJGL's builds use Homebrew's published Vulkan-Loader bottle, while each MacLauncher KosmicKrisp package contains a loader built from source together with the driver.

MacLauncher KosmicKrisp's adaptations of Mesa's KosmicKrisp driver are maintained in the [MacLauncher KosmicKrisp fork](https://github.com/procrastinine/maclauncher-kosmickrisp), which applies them to a pinned Mesa commit and holds the build recipe. Its [adaptation reference](https://github.com/procrastinine/maclauncher-kosmickrisp/blob/main/kosmickrisp-patches/build-the-adapted-mesa-tree-directly-and-document/maclauncher/ADAPTATIONS.md) describes each added feature, its Metal implementation and its limits, and its [build guide](https://github.com/procrastinine/maclauncher-kosmickrisp/blob/main/kosmickrisp-patches/build-the-adapted-mesa-tree-directly-and-document/maclauncher/BUILDING.md) gives the build and test configurations. MacLauncher Builds pins the fork at an exact commit and builds the downloadable packages from it, each with a Khronos Vulkan loader built from source. Each package requires macOS 26.0 or later. The Runtimes window shows the installed version and the version that each catalog entry offers.

The package was earlier published under the ID `vulkan-kosmickrisp-gles32`. Installations under that ID stay in place and are listed as MacLauncher KosmicKrisp. On the first start of a profile that still records the earlier ID, MacLauncher converts its default version, each game's version and CPU build, and every saved Vulkan driver choice to the current ID once. A saved choice whose version cannot be read becomes **Automatic**.

## CPU builds and consumers

A Vulkan driver and its loader are native macOS libraries, and each must contain code for the CPU architecture of the process that loads it. For a Windows game, that process is Wine's native side, so the CPU of the Wine build decides, not the game's own executable. Each consumer loads these builds:

| Consumer | Loading process | KosmicKrisp build | MoltenVK build |
| --- | --- | --- | --- |
| CrossOver with Intel Wine | x64 Wine; Rosetta on Apple Silicon | x64 | x64 slice of an x64 or universal library |
| CrossOver with ARM64 Wine | arm64 Wine; FEX runs the Windows x86-64 code | arm64 | arm64 slice of an arm64 or universal library |
| Sikarugir | x64 Wine; Rosetta on Apple Silicon | x64 | x64 slice of an x64 or universal library |
| Sikarugir GPU compute helper, used by XeSS | x64 Wine helper | x64, from the Sikarugir Template | Not used |
| AnyPS5 | x64 host; Rosetta on Apple Silicon | x64 | x64 slice of an x64 or universal library |
| Prosper | x64 host; Rosetta on Apple Silicon | x64 | x64 slice of an x64 or universal library |
| Android, with JVM or ART execution, ANGLE's Vulkan renderer and native Vulkan apps | arm64 host | arm64 | arm64 slice of an arm64 or universal library |
| Shared libplacebo effects | The graphics host, arm64 or x64 | Not used | Universal library packaged with the effects |

For CrossOver, the architecture is read from the native Wine loader of the selected installation, never from version numbers or folder names. Translator lists for a Wine game then contain only builds with code for that architecture. Android always selects and installs arm64 builds, whatever the launcher's own CPU or a saved default. A universal MoltenVK library contains both slices, and the loading process uses its own.

Because LWJGL's KosmicKrisp builds contain only arm64 code, they can serve Android and ARM64 Wine but never an x64 process. KosmicKrisp needs Metal 4 on Apple Silicon in every case, so an x64 build runs only under Rosetta on an Apple Silicon Mac, and its requirement is judged by the Mac's hardware rather than by the CPU of the process. [Downloads and offline use](README.md#downloads-and-offline-use) describes how an Intel program such as AnyPS5 or Prosper is offered the x64 MacLauncher KosmicKrisp package.

## Selection and loading

**Runtimes → Graphics → Vulkan drivers** holds MoltenVK, KosmicKrisp and MacLauncher KosmicKrisp. Each consumer then chooses a driver in its own settings:

| Consumer | Setting | Automatic choice |
| --- | --- | --- |
| CrossOver and Sikarugir | **Vulkan driver** in Runtime Settings, with its default in Settings ([Selection](TRANSLATORS.md#selection)) | The Wine runtime's own driver, except that a DXVK or vkd3d-proton version installed in Runtimes pairs with MacLauncher KosmicKrisp, as described below. Sikarugir's Template prefers its KosmicKrisp on a physical Apple Silicon Mac with macOS 26 or later. |
| Android | **Vulkan implementation** in **Settings → Android** and in each game's settings ([Android](../game-types/ANDROID.md)) | An installed MoltenVK, then an installed KosmicKrisp, then a compatible MacLauncher KosmicKrisp |
| AnyPS5 and Prosper | **Vulkan** in the game's settings ([PlayStation 5](../game-types/PS5.md)) | Prefers KosmicKrisp |

When a CrossOver or Sikarugir game renders with a DXVK or vkd3d-proton version installed in Runtimes and its **Vulkan driver** stays at the automatic choice, that choice pairs the translators with MacLauncher KosmicKrisp. The installed package for the Wine process's CPU is used. When none is installed, Play offers it after consent, and an Intel Wine process gets the x64 package. With DXVK alone, the offer's **Use MoltenVK** button uses the **MoltenVK scene support** package instead, which Play installs when it is missing. vkd3d-proton needs KosmicKrisp, so its offer has no such button. On a Mac without Metal 4 or a physical Apple GPU, the pairing uses MoltenVK scene support, which Play installs after consent when it is missing. The inspector's Vulkan driver row gives the reason, such as "MacLauncher's DXVK uses MacLauncher KosmicKrisp." or, on such a Mac, "KosmicKrisp needs Metal 4 and a physical Apple GPU, so MacLauncher's DXVK uses MacLauncher's MoltenVK build." With vkd3d-proton, the second reason ends with "vkd3d-proton needs MacLauncher KosmicKrisp."

A game without such a translator keeps the runtime's own driver, and nothing is downloaded or switched for it. That includes a game that renders with the runtime's own DXMT, D3DMetal, DXVK or D9VK, or with a DXMT or D3DMetal version from Runtimes. A selected driver always takes precedence over the pairing, and so does the **Bottle setting** or **Wrapper setting** of an existing environment.

DLSS forwarding through DXVK or vkd3d-proton needs a driver with the temporal carrier that [Temporal frames](#temporal-frames) describes: MacLauncher KosmicKrisp or MoltenVK scene support, whether the pairing or a selection chose it. The runtime's own drivers have no carrier, so a game on the runtime's own DXVK starts without forwarding. When a game would otherwise forward and its selected driver has no carrier, such as a stock MoltenVK version or LWJGL's KosmicKrisp, the game also starts without forwarding, and the Vulkan driver row says "This Vulkan driver does not forward DLSS frames." MoltenVK is not included in the app; Wine routes with the runtime's own translators use the runtime's own copy.

MoltenVK's library is loaded directly. KosmicKrisp, by contrast, is reached through the Khronos Vulkan loader, which finds drivers through ICD manifests: small JSON files that name a driver library and its Vulkan version. Before a launch, MacLauncher writes such a manifest as `vulkan-icd.json` and points the loader to it with `VK_DRIVER_FILES` and `VK_ICD_FILENAMES`. A manifest supplied with the driver keeps its fields, while `library_path` becomes the absolute path of the selected driver and `is_portability_driver` is set to false. A driver without a manifest of its own, such as a MacLauncher KosmicKrisp package, receives one that declares Vulkan 1.4.0, because the loader withholds Vulkan 1.1 and later features from a driver declared as Vulkan 1.0. An unchanged manifest is not rewritten. [Loading](TRANSLATORS.md#loading) describes where Wine finds the loader.

A MacLauncher KosmicKrisp package is installed only after its archive matches the SHA-256 recorded in the MacLauncher Builds catalog and the code signatures of its native files are verified. Besides the driver, `libvulkan_kosmickrisp.dylib`, and the loader, `libvulkan.1.dylib`, the package contains the compiler and compression libraries that the driver loads through relative paths, its license notices and records of its dependencies. Each version is installed once and shared by every game that selects it, and an installed version works offline.

Upstream KosmicKrisp keeps compiled pipelines across launches only through the `VkPipelineCache` data that an application or translator stores itself. MacLauncher KosmicKrisp also caches the Metal Shading Language that it generates from each shader and the Metal libraries compiled from that source, so a shader that was already translated and compiled is reused instead of being processed again. For Wine games, CrossOver and Sikarugir point Mesa's shader cache to `cache/mesa` in the game's MacLauncher runtime directory through `MESA_SHADER_CACHE_DIR`, apart from the bottle and the Wine home. KosmicKrisp derives the pipeline cache UUID from its driver build, so cache data from a different build is not reused. In MacLauncher KosmicKrisp, shader cache keys also record the enabled device features that change shader compilation.

The per-game Mesa cache defaults to a `4G` budget through `MESA_SHADER_CACHE_MAX_SIZE`. An explicit value in **Settings → Environment variables**, a game's **Runtime Settings**, or an external Wine environment is preserved. KosmicKrisp's [translator environment variables](TRANSLATOR_ENVIRONMENT.md#kosmickrisp) accept values such as `8G` or `512M`. Launches without the per-game Mesa cache receive no cache-budget default.

MacLauncher KosmicKrisp also moves the native compile of a compute pipeline out of pipeline creation. When a single compute pipeline has no compiled Metal pipeline in the cache, creation returns as soon as its Metal Shading Language is generated, sparse residency guards included. The Metal library and pipeline then compile on a bounded compiler queue at background priority, which leaves the performance cores to the game. The first bind of the pipeline compiles it on the binding thread when that compile has not started yet; when it is already compiling, the bind waits and raises the compiling thread to user-initiated priority for the wait. A native compile failure loses the device at that first use. Destroying a pipeline does not wait. Once the last pipeline or pipeline cache that references the shader is destroyed, a compile that has not started is cancelled, and a compile in progress finishes at user-initiated priority with its result discarded; destroying the device does the same for every remaining compile. Creation stays synchronous for calls that create several pipelines, creation feedback, the compile-required and early-return failure flags, pipeline statistics and internal-representation capture, indirect-bindable pipelines, shaders that use 64-bit atomic locks, and sparse variants selected at bind.

### Temporal frames

MacLauncher KosmicKrisp also accepts the game's DLSS Super Resolution inputs through a `VkTemporalFrameInfoMVK` structure recorded by vkd3d-proton or the D3D11 NGX adapter through DXVK's interop interfaces. The driver forwards each frame to `rsProcessTemporalFrame` in MacLauncher's shared graphics pipeline, where the selected upscaler and compatible ordered effects run. Without another selected method, the pipeline uses MetalFX. KosmicKrisp itself creates and encodes no MetalFX scaler, interpolator or other upscaler.

This route forwards color, depth, motion, output geometry, exposure, jitter, motion-vector scale, reset and depth conventions, pre-exposure and frame time. Camera near and far planes and vertical field of view are present only when the game supplies Streamline constants. Although the structure has slots for HUD-less color, UI and Ray Reconstruction resources, this consumer forwards Super Resolution frames without those attachments or camera matrices. The shared pipeline writes a tracked output texture before the driver copies its complete result to the game's output image; a busy frame can keep a previous complete result. No copy occurs before a feature has a valid result. [Frame sources and runtime adapters](../graphics/INPUTS_AND_ADAPTERS.md#scene-producers) describes the other translator routes and their scene inputs.

## Features of MacLauncher KosmicKrisp

MacLauncher KosmicKrisp adds Vulkan features that upstream KosmicKrisp does not expose at the same Mesa commit. Each one is implemented on Metal. Some exist because a particular consumer requires them, as [Where the differences matter](#where-the-differences-matter) explains; the others widen what Vulkan applications in general can use.

Many of these features are emulations that `KK_EMULATION` selects, as [Performance and conformance](#performance-and-conformance) describes. In the default performance mode, the following are reported only when `KK_EMULATION` selects them: 64-bit floating point, multisampled storage images, vertex input dynamic state, descriptor heaps, multisampled rendering to single-sampled images, non-seamless cube maps, zero-initialized device memory, block-compatible views of several layers, depth bias control, multiview together with geometry and tessellation shaders, fragment barycentrics, and ray tracing. The [feature table](#feature-table) lists every capability with its implementation and Apple GPU families.

### Rasterization, geometry and queries

- Transform feedback (`VK_EXT_transform_feedback`) with geometry streams, and primitives-generated queries (`VK_EXT_primitives_generated_query`). Transform feedback uses Mesa Poly together with KosmicKrisp's own shader compiler and GPU command encoders.
- Non-solid polygon fill (`fillModeNonSolid`), which provides wireframe and point fill modes.
- Wide, rectangular, smooth and stippled Bresenham lines.
- Pipeline statistics queries.
- Variable multisample rate, which allows rendering without attachments at differing sample counts, as Direct3D 11.1 and 12 need.
- Depth bias control (`VK_EXT_depth_bias_control`), including exact and forced UNORM representations.
- Conservative rasterization (`VK_EXT_conservative_rasterization`), with an overestimation of 1/256 pixel, rasterized degenerate triangles and a fully covered fragment input. Underestimation and post-depth coverage are not supported.
- Fragment shader interlock (`VK_EXT_fragment_shader_interlock`) with pixel interlock and sample interlock, which DXVK and vkd3d-proton use for rasterizer-ordered views. Single-sampled pixel interlock and sample interlock use Metal's raster order groups directly. In multisampled pipelines, pixel interlock runs the shader's ordered section inside a pixel-scope envelope, which orders the fragments of one pixel across all samples that a primitive covers.
- Rasterization-order access (`VK_EXT_rasterization_order_attachment_access`) for color attachments on Apple GPU family 7 and later. Depth and stencil attachments have no such access.
- Mesh and task shaders (`VK_EXT_mesh_shader`) with mesh shader queries, and multiview together with geometry and tessellation shaders.

### Resources and memory

- Sparse binding and sparse residency for buffers, 2D and 3D images and aliased memory, together with shader resource residency. These are built on Metal placement sparse resources and are exposed when the Metal device supports them.
- Single-texel alignment for uniform and storage texel buffer views.
- Multisampled storage images with one, two or four samples.
- Descriptor heaps (`VK_EXT_descriptor_heap`), device-generated commands (`VK_EXT_device_generated_commands`) and device address commands (`VK_KHR_device_address_commands`).
- Vertex input dynamic state, and extended dynamic state for polygon mode, rasterization samples, sample mask, alpha to coverage, line stipple and conservative rasterization mode.
- Dynamic rendering with unused attachments, multisampled rendering to single-sampled images, sliced views of 3D images, non-seamless cube maps, image compression control, image alignment control (`VK_MESA_image_alignment_control`) and zero-initialized device memory.
- External memory through file descriptors, memory priority and pageable device-local memory.
- `VK_KHR_maintenance11` and `VK_KHR_extended_flags`.
- Minimum and maximum sampler filtering on every Apple GPU; upstream offers it from Apple GPU family 10.
- Custom border colors with border color swizzling, and minimum LOD for image views, enabled by default. Upstream KosmicKrisp treats them as experimental features and enables them only when `MESA_KK_EXPERIMENTAL` names them. In both builds, a value of `MESA_KK_EXPERIMENTAL` replaces the default selection.

### Shaders

- 64-bit floating point, computed in software as binary64 arithmetic, with fused multiply-add, round-to-nearest-even and preserved signed zero, infinity and NaN.
- 64-bit integer atomics on buffers and shared memory, and on images on Apple GPU family 8 and later.
- Independent float controls for each width. A shader can request preserved or flushed 32-bit denormals, and 16-bit and 64-bit denormals are preserved.
- 8-bit floating point (`VK_EXT_shader_float8`), cooperative matrices in compute shaders (`VK_KHR_cooperative_matrix`) and long vectors (`VK_EXT_shader_long_vector`).
- Compute shader derivatives in linear groups, fragment shader barycentrics where Metal reports barycentric coordinate support, and quad control (`VK_KHR_shader_quad_control`).
- Subgroup operations in vertex, tessellation and geometry shaders as well as compute and fragment shaders, and required subgroup sizes for compute shaders.

### Presentation

- `VK_GOOGLE_display_timing` for requested presentation times and presentation history.
- `VK_KHR_incremental_present`, which accepts damage regions and presents the complete image.
- `VK_EXT_headless_surface` for offscreen swapchains on macOS, where upstream builds leave it out.

### Limits

| Limit | Upstream KosmicKrisp | MacLauncher KosmicKrisp |
| --- | --- | --- |
| Push constants | 256 bytes | 4,096 bytes |
| Simultaneous memory allocations | 4,096 | 8,192 |
| Indirect draw count | 65,535 | 2<sup>30</sup> |

Upstream KosmicKrisp does not expose ray tracing. MacLauncher KosmicKrisp builds and traverses acceleration structures in compute passes and runs ray tracing pipelines as continuation dispatches, without Metal ray tracing. It reports acceleration structures, ray queries and ray tracing pipelines only when `KK_EMULATION` selects the `ray_tracing` entry.

## Where the differences matter

Upstream DXVK and vkd3d-proton are the Direct3D-to-Vulkan translators that Valve's [Proton](https://github.com/ValveSoftware/Proton) uses on Linux: DXVK for Direct3D 8 to 11 and vkd3d-proton for Direct3D 12. A game in CrossOver or Sikarugir that selects a version of either one from Runtimes runs on MacLauncher KosmicKrisp while its Vulkan driver stays at the automatic choice, so it uses the same translators as under Proton, and the driver carries their Vulkan work to Metal. D3DMetal and DXMT remain the alternatives that translate Direct3D to Metal directly, and the translator is selected for each game. In either case, the Wine runtime stays CrossOver's or Sikarugir's.

### Direct3D 8 to 11 through DXVK

DXVK 2.x and 3.x require Vulkan 1.3 and a fixed set of device features, among them geometry shaders, non-solid polygon fill, and the robust buffer access and null descriptors of robustness2. Upstream KosmicKrisp lacks non-solid fill, and MoltenVK lacks geometry shaders and those robustness2 features, so these DXVK versions cannot create a device on either. MacLauncher KosmicKrisp provides all of them, and a DXVK version installed in Runtimes runs on it while the Vulkan driver stays at the automatic choice. With MoltenVK, Direct3D 8 to 11 instead use DXVK builds made for it: the DXVK-macOS packages and the Sikarugir Template's `dxvk` folder. DXVK also uses transform feedback for Direct3D stream output when the driver supports it.

### Direct3D 12 through vkd3d-proton

vkd3d-proton refuses to create a device unless the driver provides transform feedback queries, single-texel alignment of texel buffer views, vertex attribute divisors including a zero divisor, the robust buffer and image access and null descriptors of robustness2, push descriptors, shader draw parameters and mirror-clamp-to-edge sampling. Upstream KosmicKrisp lacks transform feedback and single-texel alignment, while MoltenVK lacks transform feedback and the robustness2 features. MacLauncher KosmicKrisp provides each requirement. The automatic Vulkan driver pairs vkd3d-proton with it, and a launch with another selected driver warns that KosmicKrisp is recommended for vkd3d-proton.

With vkd3d-proton selected for **Direct3D 12** and the **Vulkan driver** at its automatic choice or set to MacLauncher KosmicKrisp, a Direct3D 12 game in CrossOver or Sikarugir runs through vkd3d-proton on this driver. Intel Wine, which Sikarugir and CrossOver's Intel builds use, loads the x64 package under Rosetta, while CrossOver's ARM64 Wine loads the arm64 package, as [CPU builds and consumers](#cpu-builds-and-consumers) shows. vkd3d-proton reports Direct3D feature level 12_1 and shader model 6.8 on this driver in performance mode, and feature level 12_2 and shader model 6.9 in conformance mode; [Direct3D feature levels](#direct3d-feature-levels) gives the conditions. Games that call DLSS can also pass their Super Resolution inputs through vkd3d-proton to MacLauncher's shared graphics pipeline, as [Temporal frames](#temporal-frames) describes.

### Direct3D feature levels

DXVK and vkd3d-proton each derive a game's highest Direct3D feature level from the driver's features. Their conditions are:

| Feature level | DXVK, for Direct3D 11 | vkd3d-proton, for Direct3D 12 |
| --- | --- | --- |
| 11_1 | Logic operations, and stores and atomics in vertex pipeline stages | The same, plus 64 storage buffer and 64 storage image descriptors per stage |
| 12_0 | Tiled resources tier 2 and typed UAV loads of additional formats | Tiled resources tier 2, resource binding tier 2 and typed UAV loads of additional formats |
| 12_1 | Rasterizer-ordered views and conservative rasterization tier 1 | Rasterizer-ordered views and conservative rasterization tier 1 |
| 12_2 | Not offered | Shader model 6.5, ray tracing tier 1.1, variable shading rate tier 2, mesh shader tier 1, sampler feedback, tiled resources tier 3, conservative rasterization tier 3, resource binding tier 3 and further options |

Tiled resources tier 2 rests on Vulkan sparse residency, so feature level 12_0 needs the sparse features that MacLauncher KosmicKrisp exposes where Metal supports placement sparse resources. Both translators report rasterizer-ordered views only when the driver offers pixel interlock. MacLauncher KosmicKrisp provides pixel interlock together with conservative rasterization, so vkd3d-proton reports at least feature level 12_1 on it. Feature level 12_2 adds ray tracing, mesh shaders and variable shading rate tier 2, which vkd3d-proton implements through `VK_KHR_fragment_shading_rate`. MacLauncher KosmicKrisp exposes all three, and the levels that vkd3d-proton reports depend on the [emulation mode](#performance-and-conformance):

| Mode | Feature level | Shader model |
| --- | --- | --- |
| Performance, the default | 12_1 | 6.8 |
| Conformance | 12_2 | 6.9 |

Performance mode reports ray tracing only when `KK_EMULATION` selects it and keeps fragment barycentrics off, although vkd3d-proton reports mesh shaders only with them. DXVK offers no level above 12_1.

### OpenGL ES on Android through ANGLE

[ANGLE](https://chromium.googlesource.com/angle/angle) provides OpenGL ES to Android games. Its Metal renderer, which is the default, offers OpenGL ES 3.0 in the ANGLE version that MacLauncher includes. When an APK requires a newer OpenGL ES version and no backend has been chosen explicitly, launch switches to ANGLE's Vulkan renderer with the selected Vulkan implementation, and installs MoltenVK after consent when none is installed. Native ART execution uses MoltenVK for its shared buffers.

ANGLE's Vulkan renderer enables geometry and tessellation shaders, which OpenGL ES 3.2 requires, only when the driver supports transform feedback together with primitives-generated or pipeline statistics queries. Upstream KosmicKrisp and MoltenVK lack transform feedback, so ANGLE's conformant feature set stops at OpenGL ES 3.1 on them. MacLauncher KosmicKrisp supplies transform feedback and both kinds of query. The OpenGL ES version that an app sees comes from context creation on the selected backend.

### Vulkan games, AnyPS5 and Prosper

Games and runtimes that use Vulkan directly receive the selected driver's features without a translator in between. AnyPS5 and Prosper run as x64 programs, so they load an x64 driver build, and their automatic choice prefers KosmicKrisp.

### D3DMetal and DXMT

D3DMetal and DXMT translate Direct3D to Metal without Vulkan, so the Vulkan driver has no effect on them. D3DMetal, Apple's translator from the Game Porting Toolkit, covers Direct3D 11 and 12 for 64-bit games on Apple Silicon. DXMT covers Direct3D 10 and 11 from macOS 14. [Graphics translators](TRANSLATORS.md) describes both, together with their selection.

## Apple GPU families

Apple groups its GPUs into families, and the native Metal capability of a Mac depends on the family of its chip. Apple's [Metal Feature Set Tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) of October 23, 2026 assign the Mac chips as follows:

| Family | Mac chips |
| --- | --- |
| Apple7 | M1 series |
| Apple8 | M2 series |
| Apple9 | M3 and M4 series |
| Apple10 | M5 series |
| Apple11 | M6 series |

Metal 4 is available from Apple7 onward, so every Mac that runs KosmicKrisp is Apple7 or later. MacLauncher KosmicKrisp determines the family when the Vulkan device is created and uses a native Metal path where the family provides one:

- Apple8 and later report 64-bit integer image atomics (`VK_EXT_shader_image_atomic_int64`) and storage image and storage texel buffer support for `R64_UINT` and `R64_SINT`, which rely on native 64-bit texture minimum and maximum atomics. Apple7 does not report them.
- Sparse binding and sparse residency are reported when the Metal device supports placement sparse resources with 64 KiB sparse pages. On macOS 26.4 and later, this follows Metal's placement sparse query; earlier macOS 26 releases also require Apple8.
- Apple10 and later report depth bounds testing (`depthBounds`) and use Metal's depth bounds test; earlier families do not report the feature. Sampler LOD bias and minimum and maximum sampler filtering use the Metal sampler, while earlier families apply the bias and compute the reduction in the shader. The native reduction is reported for formats that support linear filtering, the shader reduction for every sampleable format. 1D, 2D and cube images reach 32,768 pixels, against 16,384 on earlier families.
- On Apple7 and Apple8 with macOS 26, multisampled pipelines keep Metal's triangle merging for fragment shaders that need full-quad helper invocations or unmerged triangles for barycentrics, because the method that disables merging breaks derivatives in multisampled rendering on those GPUs. Edges shared by merged triangles can then differ from Vulkan rasterization rules.

The [feature table](#feature-table) names, for each capability, the family from which Metal lists it and the families on which KosmicKrisp takes its native path.

## Performance and conformance

MacLauncher KosmicKrisp emulates Vulkan capabilities that Metal does not provide directly, using shader lowering, compute passes or captured geometry. Each emulation is a named entry, and the `KK_EMULATION` environment variable selects which entries the device reports. Upstream KosmicKrisp has no such entries and does not read the variable.

Two modes set the starting selection:

- `performance`, the default: each entry uses its performance default.
- `conformance`: every entry is enabled.

In performance mode, an entry is off only when turning it off lowers no Direct3D shader model or feature level reported by DXVK or vkd3d-proton and does not prevent either translator from creating its device. All other entries stay on, with two exceptions:

- Ray tracing interfaces are reported only when selected explicitly, with `+ray_tracing` or `conformance`.
- Fragment barycentrics are off, although vkd3d-proton reports mesh shaders only with `+fragment_barycentric` or `conformance`. Applications that use reported barycentric support for all fragment interpolation move every fragment shader to per-corner transport.

For example, vkd3d-proton reports shader model 6.2 and later only when FP32 flush-to-zero, FP32 denormal preservation and independent denormal controls are all reported. Disabling either denormal entry limits vkd3d-proton to shader model 6.1, so both entries stay on in performance mode.

`KK_EMULATION` is set like the other KosmicKrisp variables, globally in **Settings → Environment variables** or for one game in its **Runtime Settings**, as [translator environment variables](TRANSLATOR_ENVIRONMENT.md) describes. AnyPS5 sets a value of its own unless the game sets one ([PlayStation 5](../game-types/PS5.md)).

### Syntax

`KK_EMULATION` is read once, when the Vulkan physical device is created. Its value is a comma-separated list of tokens, and whitespace around each token is ignored. Tokens apply from left to right:

| Token | Effect |
| --- | --- |
| `performance` or `conformance` | As the first token, selects the mode. Without either, performance mode applies. |
| `apple7` to `apple11`, or `mode=7` to `mode=11` | Chip preset: enables every entry whose native family is at or below that family, in addition to the selection so far. |
| `+name` | Enables the entry `name`. |
| `-name` | Disables the entry `name`, unless the entry is native on the running device. |
| `-VK_extension_name` | Hides that device extension together with its feature and property fields, including their core-version query aliases. |
| Any other token | Prints one warning line to standard error and is ignored. This includes a mode name after the first position and a family number outside 7 to 11. |

The last token for an entry takes effect, so `apple9,-name,+name` enables `name` again. Extension hiding applies after entry selection. Disabling an entry removes the extensions, features, properties and format features that it controls, and an extension whose Vulkan dependencies the selection removes is removed as well. Enabling an entry keeps the support that the device otherwise reports and adds nothing beyond it; `+denorm_flush` leaves FP16 and FP64 flush-to-zero unsupported. The variable changes only the reported capabilities; command recording and shader compilation do not read it.

Examples:

- `performance,-denorm_preserve` keeps the performance defaults and disables denormal preservation.
- `conformance,-ray_tracing` enables every entry except ray tracing.
- `conformance,-VK_KHR_ray_query` enables every entry and hides `VK_KHR_ray_query`.

### Native families and chip presets

An entry can declare the first Apple GPU family on which Metal provides all of its behavior natively. On a device of that family or later, the entry uses its native path and stays reported in every mode: `-name` does not remove it, while `-VK_extension_name` still hides its extension. A chip preset `appleN` enables every entry that is native on family N or earlier. On an earlier device these entries are emulated; on a device of family N or later they are already native. The **Native family** column of the switch table gives each entry's declaration, and "No Apple family" marks an entry that no family provides natively. Such an entry follows its selection on every family.

`sampler_filter_minmax` is native from Apple10. On an Apple10 or later Mac, it uses the Metal sampler reduction and stays reported even with `-sampler_filter_minmax`. On earlier Macs it is emulated, and `apple10` or `apple11`, or `mode=10` or `mode=11`, enable it; for example, `performance,-sampler_filter_minmax,apple10` enables it again after the earlier token disabled it. `apple7` to `apple9` select no entries.

### Capabilities without a Metal feature

Apple's tables list no Metal feature for the following capabilities. KosmicKrisp emulates each of them:

- **Conservative rasterization**: triangles are expanded in a compute pass, and a fragment prologue computes coverage. Overestimation is provided; underestimation and conservative points and lines are not.
- **Transform feedback**: vertices are captured through the compute geometry path and written to the feedback buffers. Feedback queries and draw-from-feedback use small compute kernels.
- **Geometry shaders**: the geometry stage runs as a compute pass, and its output is drawn from memory.
- **Custom border colors**: Metal provides transparent black, opaque black and opaque white (Apple7). Other colors are substituted in the shader. `VK_EXT_custom_border_color` and `VK_EXT_border_color_swizzle` are advertised when `MESA_KK_EXPERIMENTAL` includes `custom_border`, which its default selection does.
- **Non-seamless cube sampling**: the tables list no non-seamless cube mode. The `non_seamless_cube` entry projects such samples onto a single face and is off in performance mode.

### Tessellation

Apple's tables list tessellation (Apple3) under the Metal 3 programming model only; the Metal 4 programming model has no tessellation stage. Because KosmicKrisp runs on Metal 4, it does not use Metal's tessellation API. Instead, the vertex and tessellation control stages run as compute passes, and a compute tessellator generates the tessellated primitives. These are then drawn through the same path as geometry-shader output, on every family.

## Environment variables

KosmicKrisp variables have global values in **Settings → Environment variables**, shared by both builds, and per-game values in **Runtime Settings**. [Translator environment variables](TRANSLATOR_ENVIRONMENT.md#kosmickrisp) lists the Mesa and KosmicKrisp variables that both builds read, among them `MESA_KK_DEBUG`, `MESA_KK_EXPERIMENTAL` and the Metal GPU capture variables. MacLauncher KosmicKrisp also reads the following:

| Variable | Effect |
| --- | --- |
| `KK_EMULATION` | Selects the emulated capabilities, as [Performance and conformance](#performance-and-conformance) describes. |
| `KK_PERF_TRACKING` | Any value other than `0` or `false` writes interval timing records as newline-separated JSON to standard error. |
| `KK_PERF_TRACKING_LOG` | Appends the timing records to this file instead of standard error. |
| `KK_PERF_TRACKING_INTERVAL_MS`, `KK_PERF_TRACKING_INTERVAL_FRAMES` | Interval between records in milliseconds, 1000 by default, and in frames, 60 by default. A record is written when either interval elapses. |
| `KK_PERF_TRACKING_COMPILES` | Any value other than `0` or `false` adds a record for each shader compilation. |
| `KK_PERF_TRACKING_SUBMITS` | `1` adds records for each queue submission and timeline wait. |
| `KK_PERF_TRACKING_BARRIERS` | `1` adds records for each render pass, with its attachments, and for each barrier. |
| `KK_PERF_TRACKING_GPU_ENCODERS` | `1` adds the GPU time of command encoders, measured with Metal 4 counter heaps, to the records. |
| `KK_CAPTURE_DIR` | Captures frames on request. When a file named `request` exists in this folder at a present, the first presented image is written as `frame-N.ppm` with metadata in `frame-N.txt`, and the request file is removed. |
| `KK_DEBUG_MSL_SALT` | Adds a comment containing the value to every Metal Shading Language source and the value's hash to the shader cache identity. |

`MESA_KK_EXPERIMENTAL` also accepts `opaque_sync` in MacLauncher KosmicKrisp, which implements opaque file descriptor semaphores with shared Metal events within one process.
