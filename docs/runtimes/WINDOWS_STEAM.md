# Windows Steam games

All three [Wine runtimes](WINE.md), CrossOver, Sikarugir and WineCX, can use an optional Steam client bridge. While a Windows game runs, the bridge connects the game's original Steam API to the Steam client for Mac, so Steam itself answers the game's account, ownership and ticket requests.

## Play

The bridge is offered for a game that includes `steam_api.dll` or `steam_api64.dll` and whose app ID is recorded in a local Steam library manifest, a completed MacLauncher Steam download or a `steam_appid.txt` in the game folder. When the app ID comes from files in the game folder, they must agree on one valid app ID. The Steam client for Mac must also be installed. Play does not offer the bridge for any other game.

When the bridge package or its Windows Steam client files have no usable version, Play asks about them once for the game, in one of two ways. Installed versions and registered folders are usable, so Play asks nothing while both have one.

- When no other download is needed, the game gets its own **Play with Steam?** dialog. It names what **Play with Steam** downloads, the Steam client bridge, the Windows Steam client files from Valve or both, whichever has no usable version, and says that Steam starts if it is not running. **Play with Steam** downloads them and continues to the game. Steam then starts for that Play without a second question, unless the game's **Steam client on Play** preference is **Don't start**. **Play Without Steam** runs the game without the bridge.
- When the same launch also downloads another component, such as a Wine engine, the launch's single **Download what <game> needs?** dialog lists the bridge on its own line with its version and size and adds an **Also connect to Steam** checkbox, which is selected by default. Approving the dialog with the checkbox selected has the same effect as **Play with Steam**. Clearing it declines only the bridge, and Play continues with the other downloads. The dialog's buttons are **Download and Play** and **Cancel**, with no **Play Without Steam** button. **Cancel** stops the Play.

Sizes appear only when they are known offline. The bridge's size comes from its last catalog refresh, and an approximate total for the Windows Steam client files comes from the last completed download; that total includes every archive downloaded before the client files were found. Without it, no size is shown for the Valve download. Neither size is read from the network before consent. A failed catalog request reports the HTTP status and the catalog URL, and when the published catalog is missing, no other source stands in for it.

Choosing **Play Without Steam**, or clearing the checkbox, is remembered for that game, and later Plays start it without asking. A Refresh keeps that choice. Installing the bridge in **Runtimes → Steam client bridge** makes every Windows Steam game eligible again, as the dialog states. When a consented download fails, Play shows its error and stops: the failure is not saved as a refusal, and the game does not start without Steam instead.

Once the bridge is installed, later Plays use it without a dialog while Steam is running. When Steam is not running, Play follows the game's **Steam client on Play** preference, described in [Steam API support](STEAM_API.md#steam-client-on-play). With **Ask**, Play shows the same **Play with Steam?** question with **Play with Steam** and **Play Without Steam**. Choosing **Play Without Steam**, or having the **Don't start** preference, starts the game without the bridge.

## Runtimes and inspector

**Runtimes → Steam client bridge**, under the Compatibility heading, has two sections, **Steam client bridge** and **Windows Steam client files**. Each lists its installed and downloadable versions with the usual install, uninstall, **Default** menu and **Register custom…** controls. Play uses the game's own **Version** choice, then the saved default, then the newest installed version or registered folder.

The bridge section lists the bridge packages from MacLauncher Builds. Each installed package is checked against the loader paths that the running MacLauncher uses, whatever its version number. An incompatible package stays listed with the reason and is not used; Play offers a replacement through the same download consent and resumes once the replacement is installed. **Register custom…** accepts a bridge package folder in its published layout, a payload folder whose `manifest.json` names the bridge's parts in its `steamBridge` entry together with the package record beside it, or a file inside that folder. A folder of an installed version qualifies. The same loader-path check applies, and every part that the manifest names must be a file in the folder.

The **Windows Steam client files** section holds `steamclient.dll` and `steamclient64.dll` from Valve's Steam client download. Its one source row, under the **Versions** heading like every other runtime's, is named **Valve CDN** and links to Valve's Steam client page. **Refresh Valve versions** reads Valve's current client listing and lists the archive that holds both files, identified by its content hash and labeled with Valve's client version. Refresh reads only the archives' file directories, in parts, without downloading the archives. Valve lists only its current client, so an earlier version stays listed while it is installed. Every installed version is kept beside the others, and removing one keeps the rest. **Register custom…** accepts a folder that holds both files, or a file in it. `steamclient.dll` must be a 32-bit and `steamclient64.dll` a 64-bit Windows image, and nothing in the folder is changed. A registered folder, and a copy whose record has no Valve client version, is labeled with the client build that `steamclient64.dll` states in its version resource, as in **Steam client 10.96.30.42**. Valve's client versions and these client builds are separate numbering schemes and are never compared, so installed copies are listed by installation time, newest first, and the newest installed copy is the most recent installation. Both files are Windows code, so these versions carry no processor label.

Installing a bridge version, from Runtimes or from Play, also installs the client files when no usable version exists. A copy installed that way, without a game choice or a saved default, is recorded as installed by Play, and like other such versions the [upkeep pass](../development/DATA_MODEL.md#derived-data-upkeep) removes it once a newer usable version is installed and nothing uses it. Uninstalling the last bridge version removes the client files that bridge installations brought in, including copies that earlier MacLauncher versions installed with the bridge. Versions installed from the client files section, and the saved default, stay.

After a Play that used the bridge, the game's inspector shows a **Steam** row naming the bridge version for as long as that version stays installed. A game whose last Play did not use the bridge shows no such row.

## Downloads and verification

Finding the Steam client and reporting installed status happen offline, and the Runtimes status reads only the recorded file sizes. A consented installation reads Valve's current download metadata, verifies the selected archive against the SHA-1 content hash and, when listed, the SHA-256 that Valve publishes for it, and keeps the verified files for offline use. The bridge does not require a particular Steam client version, and it does not compare that client's files with a hash list.

## Implementation

The game runs in the selected CrossOver bottle, Sikarugir environment or WineCX prefix, while the bridge and the Windows Steam client files stay in MacLauncher's runtime directories outside that environment. Wine loads them from there through `WINEDLLPATH` and DLL overrides set for that launch. The bridge creates no copy of the environment and installs no files into `drive_c`, so ordinary Wine settings and game drive mappings use the selected environment as usual.

MacLauncher's helper program writes only the Steam discovery entries under `HKCU\Software\Valve\Steam`, including its own active process ID, the paths of the client DLLs in MacLauncher's runtime directories, `SteamPath` and `SteamExe`, and then stays alive as the game's parent. MacLauncher's loader maps the original Windows Steam client DLL without running its Windows initialization and redirects the DLL's shared exports to `lsteamclient`, which loads the native Mac client library. An unsupported executable export stops the bridge's process. The loader does not alter the game, its Steam API or its DRM, and it does not modify the installed Wine runtime or the Steam client for Mac. Each module the loader loads by path, namely the original client DLL, `lsteamclient` and the loader itself, keeps that path as its module file name. A game wrapped in Steam's DRM (SteamStub) opens the client DLL by its module file name before the game starts and compares the file with the loaded image, so the check reads the original client DLL. The TLS callbacks of the first executable can run before the loader is installed in the child process.

An Unreal packaged game starts through a bootstrap executable. When the bridge is used, Play reads the target path and arguments embedded in that bootstrap and passes the target program directly to the helper, which puts the Steam loader in the game process before the program's entry point. The target must be a compatible Windows PE executable inside the game folder, and the working directory and additional launch arguments are kept.

The bridge package contains Windows i386 and x86_64 components and native x86_64 and arm64 components. To convert paths, the native components use functions exported by the selected Wine runtime, including the Wine 10 interface. When the package, the client or the needed native architecture is missing, the bridge is not prepared. Failures in the native API are left to the game's own handling of client errors. Existing environment copies under `steam-environments` are kept, although the bridge no longer uses them; they may contain saves, so they are not removed automatically.

Whether a title can start is decided by Steam and by the game's own checks. A working client connection says nothing about the game's other Windows APIs, its graphics or its anti-cheat requirements.
