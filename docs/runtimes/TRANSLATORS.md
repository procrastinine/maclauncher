# Graphics translators

This page covers the graphics translators that Windows games use in the [Wine runtimes](WINE.md), [CrossOver](CROSSOVER.md), [Sikarugir](SIKARUGIR.md) and [WineCX](WINECX.md): where their versions come from, how a game chooses one, how MacLauncher loads it and what happens when it cannot load. A translator converts a game's Direct3D or Vulkan calls to Metal, either directly or through a Vulkan driver that runs on Metal. Each Wine distribution brings its own set. CrossOver includes engines such as D3DMetal, DXMT and DXVK and chooses among them with its own graphics selector, Sikarugir supplies its engines in the Template that accompanies each Wine version, and each WineCX release includes DXVK, DXMT and MoltenVK.

Each game can choose a default Direct3D engine, a translator for each Direct3D version from 8 to 12, a Vulkan driver and video codecs, while Settings holds the defaults for all games. A choice can be a copy that comes with the selected Wine, an upstream release, files registered locally or the user's own copy of Apple's Game Porting Toolkit. MacLauncher keeps these versions outside the Wine distributions, whereas community tools such as [CXPatcher](https://github.com/italomandara/CXPatcher) update translators by patching a copy of the CrossOver application. Compared with running the same game in CrossOver, Sikarugir or WineCX alone, this has several effects:

- A game can use a newer or older translator than the one its Wine distribution includes, while other games keep their own choices. The CrossOver application, Sikarugir engines and Templates are never modified for this.
- Versions installed in Runtimes are stored apart from CrossOver and the Templates, so updating or replacing those leaves the installed versions, and the games that chose them, unaffected.
- Each translator version is installed once, and every game and Windows environment that uses it links to that single installation.
- Compatibility is decided from the translator's actual files when Play starts. A choice that cannot load falls back to the same engine from the selected Wine, and the inspector names both.
- [Graphics effects](../graphics/SHARED_PROCESSING.md) and temporal upscaling are prepared for the translator that the game actually uses after any fallback.

## Translators and drivers

| Translator | Graphics API | Role |
| --- | --- | --- |
| DXMT | Direct3D 10 and 11; Direct3D 12 when supplied by the package | Translates to Metal. |
| D3DMetal | Direct3D 11 and 12 | Apple's translator to Metal, from the Game Porting Toolkit. |
| DXVK | Direct3D 8, 9, 10 and 11 | Translates to Vulkan. Its packages differ in which Direct3D versions they include. Sikarugir Templates have `dxvk`, `dxvk3` and `d9vk` folders, of which `d9vk` holds only Direct3D 8 and 9 libraries and is labeled by the release that its version file names, and Gcenx's macOS builds have async variants. The historical D8VK and D9VK releases cover Direct3D 8 and 9, which modern DXVK now includes. |
| vkd3d-proton | Direct3D 12 | Translates to Vulkan. |
| Wine vkd3d | Direct3D 12 | Wine's own Direct3D 12 libraries. |
| WineD3D | Direct3D | Wine's built-in Direct3D translation. |
| MoltenVK | Vulkan | Vulkan driver that runs on Metal. |
| KosmicKrisp | Vulkan | Vulkan driver from Mesa that runs on Metal on Apple Silicon. |
| GStreamer codecs | Video | Plugins for Wine's video playback. |

Upstream DXVK and vkd3d-proton are also the Direct3D translators of Valve's [Proton](https://github.com/ValveSoftware/Proton) on Linux. When a game selects a version of one of them from Runtimes and leaves its Vulkan driver at the automatic choice, MacLauncher KosmicKrisp becomes its driver on a Mac with Metal 4 and a physical Apple GPU. The game's Direct3D calls are then translated the same way as under Proton, and KosmicKrisp runs the resulting Vulkan work on Metal, while the Wine runtime is still CrossOver's or Sikarugir's. [Where the differences matter](KOSMICKRISP.md#where-the-differences-matter) describes what each translator requires from the driver.

## Versions and sources

**Runtimes → Graphics** groups the translators by what they produce. **DirectX → Vulkan** holds DXVK, Wine vkd3d and vkd3d-proton, **DirectX → Metal** holds DXMT and D3DMetal, **Vulkan drivers** holds MoltenVK and KosmicKrisp, and **Video codecs** holds GStreamer. Within these groups, each translator has its own section, whose versions come from the shared runtime catalogs or from local registration. Because every Wine runtime uses the same installed versions, selecting a translator for another game adds no copy of its files. Refresh reads the published releases of one source, while status and the inspection of registered files work offline.

| Translator | Download sources | Local sources |
| --- | --- | --- |
| MoltenVK | KhronosGroup/MoltenVK | Library, folder, archive or installed runtime |
| KosmicKrisp | LWJGL's KosmicKrisp builds of Mesa; MacLauncher KosmicKrisp from MacLauncher Builds | Driver and loader folder, archive or installed runtime |
| DXMT | 3Shain/dxmt builtin releases; Sikarugir Template | Folder, archive or installed runtime |
| DXVK | DXVK upstream, including historical D8VK/D9VK variants; DXVK-macOS with an async variant; Sikarugir Template components; MacLauncher DXVK from MacLauncher Builds | Folder, archive or installed runtime |
| Wine vkd3d | Link to the Wine upstream source | Read-only copies included with registered runtimes |
| vkd3d-proton | HansKristian-Work/vkd3d-proton | Folder or archive |
| D3DMetal | Sikarugir Template | Apple Game Porting Toolkit disk image or folder; installed runtime |
| GStreamer codecs | Official GStreamer macOS runtime packages | Prepared plugin folder together with the libraries its plugins depend on |

Every macOS library that Wine loads must contain code for the CPU architecture of Wine's native loader. Sikarugir, WineCX and CrossOver's Intel Wine run as x86-64 processes, also on Apple Silicon through Rosetta, while a CrossOver installation with an ARM64 Wine loader runs as an arm64 process and leaves Windows x86-64 code to FEX. MacLauncher reads the architecture from the selected installation's native Wine loader and lists only translator installations with code for it. Because KosmicKrisp itself requires Apple Silicon, Intel Wine needs an x86-64 build of it: a Sikarugir Template's driver, an installed MacLauncher KosmicKrisp package that includes an Intel (x86-64) build, or a locally registered build with Intel code. LWJGL's KosmicKrisp builds contain only arm64 code, so they can serve ARM64 Wine but never Intel Wine. [KosmicKrisp](KOSMICKRISP.md#cpu-builds-and-consumers) lists the build that each program loads.

MacLauncher KosmicKrisp is an adapted build of KosmicKrisp. The features it adds to upstream include the non-solid polygon fill that DXVK requires, the transform feedback and single-texel alignment of texel buffer views that vkd3d-proton requires, and the transform feedback and primitives-generated queries that ANGLE's Vulkan renderer needs for OpenGL ES 3.2 shaders. With MacLauncher KosmicKrisp as the Vulkan driver, vkd3d-proton runs Direct3D 12 games in CrossOver, Sikarugir and WineCX and reports Direct3D feature level 12_1 in performance mode and 12_2 in conformance mode. [KosmicKrisp](KOSMICKRISP.md) lists its features, compares it with upstream KosmicKrisp and MoltenVK, and shows which Direct3D feature levels depend on them.

Each source card has its own Refresh control and publisher link. When a source groups several catalogs, a Variant control switches between them, and Refresh updates them together. Download cards list their versions newest first by the publisher's release: the release tag for upstream sources such as DXVK and vkd3d-proton, and the Template version for Sikarugir Template components. The **Vulkan drivers** entry also holds **MoltenVK scene support**, MacLauncher's MoltenVK build from MacLauncher Builds. It forwards DLSS frames from DXVK and vkd3d-proton, and the automatic Vulkan driver choice uses it on a Mac without Metal 4 or a physical Apple GPU, as [Selection and loading](KOSMICKRISP.md#selection-and-loading) describes.

Translator versions are selected per game, with **Automatic** using the Wine runtime's own copy, and the translator sections in Runtimes have no global default version. DXVK upstream is the primary download card. It lists Windows PE builds but not Linux `dxvk-native` packages, and its description states that DXVK 2.x and 3.x need Vulkan 1.3 and the driver features of compatible KosmicKrisp builds. Two more cards are under **Additional sources**. The first is DXVK-macOS, whose **Standard** and **Async** variants list Gcenx's builds for MoltenVK. The second offers the Sikarugir Template components: `dxvk` supplies DXVK async with D9VK for MoltenVK, `dxvk3` supplies DXVK for KosmicKrisp, and `d9vk`, listed as **DXVK subset (d9vk)**, holds only Direct3D 8 and 9 libraries. Historical D8VK and D9VK releases are variants of DXVK upstream, and a historical catalog with no releases adds no variant. A Template component's name only identifies its folder; its Direct3D API coverage and component version are read from the installed files. The version of the Template package itself is kept separate from its components' versions.

D3DMetal has two cards: an Apple Game Porting Toolkit card that registers an Apple download, chosen with its button or dropped on the card, and a Sikarugir Template card, which is its download source. DXMT likewise lists its Template card next to DXMT upstream. The GStreamer panel offers official runtime packages and prepared local codec folders.

For LWJGL's KosmicKrisp driver, the LWJGL package version is shown as the package it came from, and a KosmicKrisp component version appears only when the component's metadata supplies one. When releases or builds share a short label, each keeps its publisher revision or exact build identifier, instead of a number for its position in a list.

A registered folder or installed application is used in place: MacLauncher refers to the selected files where they are. A registered archive or disk image, by contrast, is extracted once into shared storage. A disk image is attached read-only, and its volume is copied when it contains the component. When the volume holds no component but has disk images at its top level, as Apple's Game Porting Toolkit download does, MacLauncher searches one level deep and copies only the nested image that contains the component. An image with a license agreement is attached with `hdiutil`, because `diskutil image attach` waits for the agreement. Downloaded publisher archives are cached by release asset, and every translator section shares that cache, so installing another component from the same Template reuses the earlier download. An installed Template component keeps its complete folder tree, including notices, and no other Wine engine is installed with it. Removing a local registration leaves the original files in place.

A Sikarugir Template card installs only the chosen folder of a Template release, such as `d3dmetal` or `dxvk3`, as a copy in MacLauncher's runtime storage. The folder keeps its licence, read-me and other notices, and no Wine engine or other folder is installed. Copies that come with an installed Sikarugir engine stay part of that engine and are separate from these copies. A listed Template version is labeled with the Template release and folder, as in **Template 1.0.27 · d3dmetal**. When an installed Sikarugir engine already includes the same release, the label adds that folder's component version, as in **Template 1.0.24 · d3dmetal · D3DMetal 4.0b3**. Otherwise the card states that the component version in that Template release is known after download, because the publisher's release lists only the Template version. Once installed, the copy is labeled with its component version and **Managed copy from** its Template release, as in **DXMT 0.80-244-g7c8dee1 · Managed copy from Sikarugir Template 1.0.21**.

The installed lists also show matching components that come with registered CrossOver applications and Sikarugir Templates. Each of these Included rows is labeled with the component's own release followed by its host, which is the application or Template that it comes with, as in **DXVK 1.10.3 · CrossOver 26.3** or **DXVK 3.1.1 async · Sikarugir Template 1.0.24**. The row's details give the full version text and CPU architectures. A component without readable version metadata is labeled with its engine and host alone. If two rows would still read the same, the label first adds the Template folder name, such as `dxvk3` or `d9vk`. Then it adds any part of the host's version label that the row does not already show, such as its Wine version, and finally the host's name. Each game's Runtime Settings uses the same component and host label but tells matching labels apart by their Direct3D coverage instead (see [Selection](#selection)). In the Installed list, **Newest first** and **Oldest first** order these rows, together with installed and registered copies, by component version and then by host version. Included rows carry an **Included** badge and refer to the original files. Because they belong to their source, they have no install, repair, default or removal actions. Wine vkd3d has its own panel of included copies, which stay with Wine and are separate from vkd3d-proton; Wine's upstream source archives are not offered as Windows runtime downloads.

A registered copy is labeled the same way, with its component version first and its source after it. The version is read from the component's `version` file or, without one, from the framework named after its engine, using the `version.plist` and then the `Info.plist` in that framework's resources. The source is **CrossOver** or **Sikarugir** when the files lie inside a CrossOver application or a Sikarugir Template or wrapper, and **Registered** otherwise, as in **DXVK 1.10.3 · Registered**. When two registrations of the same translator would read the same, each label adds the registered file or folder name. Runtimes and Runtime Settings show the same label.

When an installed application is selected, MacLauncher finds the component folder, framework or driver library inside it. If the component cannot be identified, the component folder or library has to be selected directly. Components registered from CrossOver, including one selected inside a CrossOver application, are used for CrossOver launches only.

Runtimes also lists, on the row of each installed CrossOver application, Sikarugir engine and WineCX version, the translator versions it includes, as in **Includes DXMT 0.80-244-g7c8dee1 · DXVK 3.1.1 async (d9vk, dxvk3) · DXVK 1.10.3 async (dxvk) · D3DMetal 4.0b3 · MoltenVK 1.4.1 · KosmicKrisp 26.3.0-devel · GStreamer 1.28.1.1**. Every Wine source uses the same order: DXMT, DXVK, D3DMetal, vkd3d-proton, MoltenVK, KosmicKrisp and GStreamer, with the newest version of an engine first. Template folders are named when one engine has several versions in the same Template. A Direct3D set that ships its own DXGI for only some Windows architectures names the games it serves, as in **DXVK 1.10.3 for 32-bit games** for WineCX 4.8.1. A Vulkan driver without version text takes the version that its library states, which is MoltenVK's version string or KosmicKrisp's Mesa version, and GStreamer takes the version of its core library. WineD3D and Wine vkd3d are left out because they follow the Wine version. The summary is built from the descriptions that MacLauncher keeps for the installed files after preparing them locally. A Sikarugir version listed for download names the same translators when an installed engine uses its Template release; for any other release, it states that the translator versions in that Template are known after download.

D3DMetal is Apple's proprietary component, which MacLauncher neither hosts nor builds. It is downloaded from the Sikarugir Template or supplied locally, for example from the user's own Game Porting Toolkit download. Apple's Game Porting Toolkit license applies to it, including its Apple hardware and distribution restrictions, and the supplied notice stays with the component. Registering either Apple's Game Porting Toolkit disk image or the evaluation environment image inside it imports the evaluation environment volume. That volume contains Apple's license, acknowledgements and read-me files and the `redist` folder, which holds D3DMetal.framework, `libd3dshared.dylib` and the Wine Direct3D, DXGI and NVAPI libraries that load it. The `redist` folder becomes the component and is labeled with the framework's version, as in **D3DMetal 4.0b3 · Registered**. The toolkit's sample code, documentation and installer packages are not imported, and the supplied image stays where it is. Before the import is kept, and for a disk image before anything is copied from the attached volume, Apple's license file is shown as scrolling plain text in a license sheet on the launcher window. **Agree and Import** continues. **Cancel**, the default button, ends the import and keeps nothing, as do Escape and closing the launcher window. An agreed license is recorded by the SHA-256 of its file in `runtimes/accepted-licences.json`, so the sheet appears again only for a different license text.

For GStreamer, the plugin folders that come with registered CrossOver applications and Sikarugir Templates are listed as read-only sources. CrossOver's plugin folder is labeled with the GStreamer release that its `libgstreamer-1.0` library records as its current version, as in **GStreamer 1.24.4 · CrossOver 26.3**. A folder without such a version is labeled with its engine and host alone, since the ABI numbers in library file names do not give a codec version. Local registration comes with links to the official project and its downloads.

Refresh reads the official macOS package index and its release directories, and lists runtime packages apart from development and debug packages. GStreamer publishes development releases in odd minor series, such as 1.29, and stable releases in even ones, so development runtime packages are marked as pre-releases and remain selectable. Unless a version has been chosen explicitly, the newest stable release is preselected, and an explicit choice stays selected while the list is refreshed. Install verifies the publisher's checksum when one is available and extracts the framework into MacLauncher's runtime storage. Package scripts and the system installer are not run, and nothing is installed into `/Library/Frameworks`. The extracted framework includes plugin and dependency libraries, and plugin directories are recorded separately from those dependencies.

Local GStreamer registration accepts a prepared codec directory. Before it can be selected through `GST_PLUGIN_PATH`, its plugin dependencies must resolve to the intended GStreamer and GObject libraries. Installing a runtime package does not replace `winegstreamer` or another Wine module.

A GStreamer component keeps every library and resource that its plugins need, with plugin search directories kept apart from dependency directories. Preparation follows the actual native dependencies of the selected Wine and shares the libraries that Wine already provides, including its GStreamer and GObject core. Libraries found through loader-relative paths are prepared together in one shared folder, where unchanged files and resources stay links. The component's dependency and framework directories are not added to global dynamic-library search paths. Wine's scanner and system-plugin paths stay in use, and no Wine module is replaced.

An optional plugin is left out with a warning when it lacks a required CPU slice, declares a higher minimum macOS version in its binary, or strongly imports a symbol that the Wine library it depends on does not export. Other usable plugins and the runtime defaults stay available. Weak imports, and dependency or export information that cannot be read completely, are treated as unknown and produce diagnostics. An absolute or dynamic dependency path whose target cannot be confirmed is reported as unresolved. When a plugin reaches a known package core library by a path that bypasses the prepared view of Wine's libraries, that optional plugin is unavailable, and its path is reported as the reason. A registered prepared plugin folder without directory metadata keeps its existing search directories.

## Installed versions and links

A translator version is stored once, in its own installation in Runtimes, and games refer to it through links in two places. The first is a shared graphics view, a folder of such links keyed by the Wine CPU and the checksums of the selected files, so every game with the same selection reuses one view. The second, for native DLLs only, is the Windows environment that uses them. Equivalent library links resolve to the same installed source.

Real copies are made only where a link cannot work. A Wine loader that must carry its own code signature is copied, and so is D3DMetal's `libd3dshared.dylib`, which looks for its framework beside itself. These copies, too, are prepared once for each set of inputs and shared between games.

When a shared graphics view is out of date, a new version of it is built as a separate shared view. Earlier versions stay in place until routine storage cleanup can remove them.

## CPU build labels

Labels use the CPU names that [Processor builds](README.md#processor-builds) defines. [KosmicKrisp](KOSMICKRISP.md#cpu-builds-and-consumers) lists the build that each program loads.

- In **Runtimes**, the **DirectX → Vulkan**, **DirectX → Metal** and **Vulkan drivers** entries mark every installed version with its build, which is read from the CPU slices of its installed library. Both builds of one version appear as two rows.
- For CrossOver, Sikarugir and WineCX games, the inspector's **Vulkan** row ends with the build that the Wine process loads, taken from the same inspected Wine layout that Play prepares translator files for. It reads **Intel (Rosetta)** for Intel Wine on Apple Silicon, including CrossOver's Intel Wine, **Intel** on an Intel Mac and **Apple Silicon** for ARM64 Wine, including the CrossOver 27 FEX preview. Direct3D rows name Windows libraries and carry no Mac CPU.
- Every Vulkan driver choice of a game has the build of the program that loads it, such as Intel for AnyPS5 and Prosper and Apple Silicon for Android, so the menu does not repeat it. The choice list checks each library for that CPU, using the same check that selects the library at launch.
- Each installed version of a driver package is one choice in a game's menu, even when both of its CPU builds are installed.

## Selection

A game's Runtime Settings chooses installed components for each graphics API and shows which choices share libraries. Settings holds the default of each control for all games, which a game's Runtime Settings can override. Versions and sources are read from installed files, and a change applies on the next launch. Because a saved choice names one installed version, installing a newer version adds a choice without changing the games that use an older one.

| Control | Choices |
| --- | --- |
| Default Direct3D engine | The shared renderer choice for every Direct3D API without a choice of its own: the runtime's automatic choice, the engines that come with the selected runtime, and named versions installed in Runtimes. |
| Direct3D 8, 9, 10 / 10.1 and 11 | Installed implementations that contain the corresponding DLLs. Modern DXVK can serve several of these APIs, while the historical D8VK and D9VK releases remain choices with their own source and version. |
| Direct3D 12 | Wine vkd3d, D3DMetal, or a vkd3d-proton or D3DMetal version installed in Runtimes. The automatic Vulkan driver pairs vkd3d-proton with MacLauncher KosmicKrisp, and a launch with another selected driver warns that KosmicKrisp is recommended for it. |
| Vulkan driver | The automatic driver, the drivers that come with the selected runtime, and MoltenVK or KosmicKrisp versions installed in Runtimes. The automatic driver is the runtime's own, except that a DXVK or vkd3d-proton version installed in Runtimes pairs with MacLauncher KosmicKrisp. |
| Video codecs | The runtime defaults or a registered GStreamer plugin folder. Wine's own video modules stay with Wine. |

With the automatic Vulkan driver, a DXVK or vkd3d-proton version from Runtimes uses MacLauncher KosmicKrisp, and Play offers the package after consent when it is missing. DXVK 2.0 and later and vkd3d-proton cannot create a device on MoltenVK. On a Mac without Metal 4 or a physical Apple GPU, or after the KosmicKrisp offer is declined, those Direct3D versions therefore use the runtime's automatic choice with the runtime's own Vulkan driver. A DXVK 1.x build made for MoltenVK, such as DXVK-macOS, uses the **MoltenVK scene support** package there instead, and its offer's **Use MoltenVK** button selects that package. A game with only the runtime's own translators keeps the runtime's own driver, and a selected driver or an existing environment's setting takes precedence over the automatic pairing. Both packages forward DLSS frames from DXVK and vkd3d-proton; when the selected driver cannot forward them, the game starts without DLSS forwarding. [Vulkan driver selection](KOSMICKRISP.md#selection-and-loading) gives the details.

Every list follows the same order. When a game runs in an existing CrossOver bottle or Sikarugir wrapper, the list opens with **Bottle setting** or **Wrapper setting** and its current value, which is read from the environment's configuration without starting Wine. Next comes the runtime's automatic choice, labeled **CrossOver's automatic choice**, **Sikarugir's automatic choice** or **WineCX's automatic choice**, which keeps that runtime's usual behavior apart from the Vulkan driver pairing above. The named choices follow, each with its engine, version and source, such as the DXMT version that a CrossOver release includes. Versions are read from release labels, component version files, framework metadata or the runtime's changelog. A label keeps a release's beta or prerelease marker, as in **D3DMetal 4.0b3**, and adds **async** when the version text names an async build. Replacement DLLs are not used as a version source, because their version resources report Windows component versions instead of translator releases. A component without readable version metadata still shows its engine and source. Components that come from CrossOver are listed only for CrossOver launches.

An optional label that cannot be read, or an unrelated package entry that cannot be accessed, produces a diagnostic. When the optional inspection of exports is incomplete, the basic PE machine type and the builtin or native form are still available. Invalid required binaries and component paths that escape their folder are still errors.

A Direct3D API without a choice of its own keeps the default Direct3D engine. Each list has one automatic entry, and copies that load the same libraries and have the same scope share one option. If a narrower copy, such as a Template's `d9vk` folder, has the same Direct3D 8 and 9 libraries and the same effect on the other APIs as a wider copy such as `dxvk3`, the wider copy represents both, although a saved choice of the narrower copy is listed in its place. When component labels match but cover different APIs, their names include that coverage. Opening the settings changes no saved choices or runtime defaults.

When one installed version serves several APIs through shared libraries, their choices are linked and change together. A choice that would place a different copy of a library that another API's saved choice needs also changes that API, to the same version when it serves that API and otherwise to **Automatic**, so no saved choice is left in conflict. **Automatic** and an existing environment's **Bottle setting** or **Wrapper setting** remain available. Settings and the inspector share the same plain fallback notices. A saved copy that is missing appears as **Saved selection (unavailable)**, while the saved choice itself stays unchanged. The inspector keeps showing the recorded choice that ran, and older records without a structured reason show a neutral fallback notice.

Copies installed in Runtimes are available as choices before Wine is installed. Included choices refer to components in registered CrossOver applications and installed Sikarugir Templates, including copies supplied by another installed Wine version, and their files remain with that installation. Malformed optional metadata of one choice does not hide other choices. Descriptions of installed copies are kept with their runtime records, and descriptions of external files are cached per file, so an unchanged file reuses its inspection results while local background preparation updates missing or changed descriptions. Settings keeps its cached lists enabled during a refresh. Until a game's lists arrive, a saved choice is named from a cached list, from the rows recorded at the game's last launch, or from the installed inventories: a copy installed in Runtimes by its version label, and an included copy by the reference to the game's Wine runtime that carries its name. A choice without a cached or current list cannot be changed until its list arrives. Settings lists and the inspector use these descriptions without repeating load checks, and Play checks the selected files before loading them.

**MacLauncher DXVK** is MacLauncher Builds' DXVK 3.1.1 package, listed in Runtimes beside DXVK. Its `x64` and `x32` folders hold the DXVK libraries and a paired `dcomp.dll`, which presents DirectComposition content in the game's window. The build adds KosmicKrisp to DXVK's descriptor heap allow-list, offers asynchronous pipeline compilation only when `DXVK_ASYNC=1` or `dxvk.enableAsync` asks for it, and keeps its shader cache in MacLauncher's cache folder. Like any DXVK version, it is selected per game, and with the Vulkan driver on Automatic, a game whose Direct3D choice uses it runs on MacLauncher KosmicKrisp. MacLauncher Builds' `docs/DXVK_ADAPTATIONS.md` and `docs/DXVK_COMPOSITION.md` describe how the package is built and patched.

DXVK-macOS packages come in two layouts: Wine builtin libraries, as in Gcenx's `-builtin` packages, and plain native Windows DLLs. CrossOver's lists offer a DXVK-macOS installation only when its Direct3D libraries are Wine builtin DLLs, which is read from the files themselves, whereas Sikarugir's lists offer both layouts. A registered folder or archive is offered to both runtimes whatever its layout, and so is a package whose form cannot be read. A saved choice stays selected and goes through the same file-based loading checks as any other choice.

Direct3D APIs can share DXGI, native Unix modules and Windows thunks, but each DLL or module location holds a file from only one source. When the selected choices would place different files at the same location, the affected APIs keep the components that the default Direct3D engine would use. An API that loses its own choice this way shows the shared-library notice, which names the API whose choice provides the other copy; an API that keeps its choice shows none. For example, DXVK's Direct3D 8 library loads DXVK's own Direct3D 9 library, so it cannot be combined with a different Direct3D 9 choice. Choosing the same DXVK version for Direct3D 9, or **Automatic** for Direct3D 8, resolves the conflict. Companion files are identified from direct PE imports and matching Unix modules. When that information is incomplete, the whole package is treated as one group, and no ABI is guessed from engine names or versions.

An explicit choice for any Direct3D API takes effect on its own, including when the default Direct3D engine is **Automatic**. On CrossOver and Sikarugir, DXGI comes from an explicit Direct3D 12 choice, or otherwise from an explicit Direct3D 11 choice, followed by Direct3D 10. APIs without an explicit choice then use that DXGI provider's libraries. D3DMetal and DXMT use DXGI and Unix companions from the selected package, so another version of the same engine cannot supply its bridge. vkd3d-proton uses DXVK's DXGI, while Wine's vkd3d uses Wine's DXGI. Direct3D 10 and 11 libraries reach DXGI through their own build's private interfaces, so they load only with the DXGI of the same package. A package without its own DXGI, such as CrossOver's DXVK 1.10.3, uses Wine's DXGI; when another DXGI is placed, Direct3D 10 and 11 use the DXGI provider's own libraries. Some packages include their own DXGI for one Windows architecture but not the other, such as the DXVK in WineCX 4.8.1, whose 64-bit folder has no `dxgi.dll`. Such a package is complete only for the architecture with its DXGI, so its libraries for the other architecture are left out, and games of that architecture are not offered the package. Direct3D 8 and 9 do not use DXGI and follow the provider only when its libraries do not conflict with another Direct3D choice.

For vkd3d-proton, MacLauncher uses the selected compatible DXVK copy, or otherwise an installed compatible copy. When the matching translator is missing, Play downloads it after confirmation and resumes preparation. When DXVK supplies DXGI and Direct3D 12 is automatic, Direct3D 12 uses vkd3d-proton. An explicit incompatible choice stays saved, but the launch uses the compatible implementation, and its row shows why. Wine's builtin DXGI and vkd3d-proton, or DXVK's DXGI and Wine's builtin Direct3D 12, are never loaded together.

On CrossOver, choosing the D3DMetal included with CrossOver for Direct3D 12 selects CrossOver's own D3DMetal renderer, just as choosing that D3DMetal as the default Direct3D engine does. This applies when the default Direct3D engine is **Automatic**, the referenced bottle's setting or that D3DMetal, and no other Direct3D API has a choice of its own. CrossOver then runs D3DMetal itself and no library is placed for the game, because the D3DMetal included with CrossOver has no Direct3D 10 library to pair with its DXGI.

CrossOver's automatic renderer uses its global graphics selector until a library has to be placed privately for a specific API. A choice for one API goes through the private Wine loader, and APIs without a placed library use Wine's builtin implementation, so no unrelated API needs a concrete selection first. CrossOver's application files remain unchanged.

A game saved by an earlier MacLauncher version keeps its earlier **Graphics** and **DXMT support** selections, and on Sikarugir its earlier Vulkan driver, until a Direct3D engine or Vulkan driver is chosen in the new controls. The new choice then replaces them, and the earlier controls are no longer shown.

Temporal upscaling integration follows the translator engine that is actually resolved and its matching libraries, whatever catalog or setting identifier it came from. For Direct3D 11, the DXMT version actually used also supplies this integration. MacLauncher's adapted DXMT libraries require a matching native library and Windows thunk, so a DXMT version that does not match them still renders the game, and the inspector reports that temporal integration is unavailable. Engine settings apply to every engine that the game actually uses for its Direct3D APIs.

## Loading

How a selected component is loaded depends on its source and form. When every Direct3D API uses CrossOver's files, CrossOver's own engines are chosen through CrossOver's graphics backend selector. That selector applies to the whole game, so when any Direct3D API, such as Direct3D 12 with vkd3d-proton, uses a library from another source, the selected CrossOver engine's files are placed through the private loader as well, and each API keeps its choice. A Direct3D engine from any other source is loaded in one of two ways:

- Replacement Wine builtin DLLs are placed in private Windows DLL directories, with their Unix modules beside the private Wine loader. When a replacement builtin's package has no Unix module of its name, the Wine engine's module of that name is placed in the same private location; WineCX 4.8.1's DXMT `winemetal.dll` uses the engine's `winemetal.so` this way. D3DMetal's matching bridge and framework are selected together.
- Upstream native Windows DLLs are linked into the environment's `system32` or `syswow64` directory and enabled with native DLL overrides. An existing DLL is set aside before it is replaced and restored when that selection is removed. Native DLLs are not placed for a **Bottle setting** or **Wrapper setting**, so the environment keeps its own files.

When the placed Direct3D engines are D3DMetal and WineD3D, CrossOver keeps its D3DMetal backend so that its DLSS redirect remains available. With any other combination of engines, CrossOver's global selector is bypassed through WineD3D, and each selected library is still loaded.

Wine opens its Vulkan library by name: `libMoltenVK.dylib` in CrossOver and WineCX, and the Vulkan loader `libvulkan.1.dylib` in Sikarugir. Each Unix Wine module carries an rpath to the engine's own library folder, which the dynamic loader searches before `DYLD_FALLBACK_LIBRARY_PATH`. To override the Vulkan driver, the selected Vulkan library is therefore linked under these names in the private folder that `DYLD_LIBRARY_PATH` names, beside the private `ntdll.so`, and no other library is placed in that folder. With KosmicKrisp, the library at that location is the Khronos loader, accompanied by an explicit driver description that names the selected driver. A driver that ships its own description keeps its other fields, while `library_path` is set to the absolute path of the selected driver and `is_portability_driver` to false. A KosmicKrisp package without a description of its own receives a generated description that declares Vulkan 1.4, whichever way the game is launched, because the loader withholds Vulkan 1.1 and later features from a driver declared as Vulkan 1.0. This method works with every Direct3D backend. `CX_LIBVULKAN` also names the selected library, although CrossOver and WineCX read it only while the WineD3D backend is active.

Sikarugir and WineCX load the same selected components through a private graphics view and Vulkan driver description. A Wine tree whose Vulkan layer reads `CX_LIBVULKAN`, such as WineCX's, also receives the selected driver through that variable. The Wine trees, Sikarugir's Template and the engine of a registered wrapper stay in place. Selected video codecs reach every Wine runtime through `GST_PLUGIN_PATH`.

Translator dependencies and vendor support libraries are found through `DYLD_FALLBACK_LIBRARY_PATH` and `DYLD_FALLBACK_FRAMEWORK_PATH`, so they do not replace macOS system libraries loaded by Apple frameworks. The private Wine loader's `DYLD_LIBRARY_PATH` override names only the folder that holds its already initialized `ntdll.so`. [Chromium in Wine](WEB_RUNTIMES.md#chromium-in-wine) describes how a bundled browser without the necessary Windows resource-sharing API uses WineD3D and its own ANGLE Direct3D 9 implementation.

## Translator options

The **Compatibility** and **Diagnostics** groups of Runtime Settings for the Wine runtimes include options that each belong to one engine. At launch, an option sets its environment variable only when the game actually uses that engine, for one of its Direct3D APIs or as its Vulkan driver, so a fallback to another engine leaves the option unused. When per-API choices use several Direct3D engines, the options of each engine apply. **Runtime default** leaves the variable unset, and the engine keeps its own default. An entry with the same name under **Environment variables** takes precedence over the option.

| Option | Engine | Variable | Values |
| --- | --- | --- | --- |
| DXVK async | DXVK | `DXVK_ASYNC` | `1` for On, `0` for Off. Only DXVK builds that implement async read it. |
| DXVK HUD | DXVK | `DXVK_HUD` | `0` for Off, `fps` for FPS, `fps,frametimes,devinfo` for Performance, `full` for Full. |
| DXMT configuration | DXMT | `DXMT_CONFIG` | `d3d11.preferredMaxFrameRate=30`, `60` or `120`. |
| MetalFX spatial | DXMT | `DXMT_METALFX_SPATIAL_SWAPCHAIN` | `1` for On, `0` for Off. |
| D3DMetal FPS limit | D3DMetal | `D3DM_MAX_FPS` | `30`, `60`, `120`, `144` or `240`. |
| D3DMetal Metal 4 | D3DMetal | `D3DM_MTL4` | `1` for On, `0` for Off. Only D3DMetal builds that implement Metal 4 read it. |
| WineD3D options | WineD3D | `WINE_D3D_CONFIG` | The comma-separated text as entered, such as `csmt=0x1,renderer=gl`. |
| MoltenVK fast math | MoltenVK | `MVK_CONFIG_FAST_MATH_ENABLED` | `1` for On, `0` for Off. |
| MoltenVK argument buffers | MoltenVK | `MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS` | `1` for On, `0` for Off. |
| MoltenVK UE4 compatibility | MoltenVK | `MVK_CONFIG_UE4_HACK_ENABLED` | `1` for On, `0` for Off. |

Two further options apply whichever engines run. **Metal Performance HUD** sets `MTL_HUD_ENABLED`. **Advertise AVX under Rosetta** sets `ROSETTA_ADVERTISE_AVX`; when the Wine process runs under Rosetta in an environment that MacLauncher creates, it is `1` unless the option is turned off. Rosetta launches also set `DOTNET_EnableWriteXorExecute=0`.

vkd3d-proton, Wine vkd3d and KosmicKrisp have no options of their own in Runtime Settings. Their documented environment variables can be entered under **Environment variables** instead and take effect only when that component is loaded.

Every Wine runtime keeps each game's shader caches in its MacLauncher runtime directory, apart from the bottle and the Wine home. DXVK writes its cache to `cache/dxvk` there, and `DXVK_SHADER_CACHE_PATH` holds that folder's Wine DOS path, mapped to a drive in the same way as the game's own folder. Mesa drivers use `cache/mesa` through `MESA_SHADER_CACHE_DIR`, with a `4G` budget through `MESA_SHADER_CACHE_MAX_SIZE` unless an environment value sets another one. MacLauncher sets no cache location for vkd3d-proton, DXMT, D3DMetal, WineD3D or MoltenVK, which keep the cache behavior of their own releases. [KosmicKrisp](KOSMICKRISP.md#selection-and-loading) describes the shader and pipeline caching of each KosmicKrisp build.

## Compatibility and fallback

Before a launch, Play checks the files that the selected Wine process and Windows executable will load. Only the CPU variant that will actually run is checked, so an unused variant in a multi-architecture installation does not affect the result. A component counts as unable to load when any of these holds:

- a required file is missing;
- the files have no PE machine type or native CPU slice for the game and the Wine process;
- a binary declares a macOS minimum above the running system;
- a Unix module needs a symbol that its actual Wine dependency does not export.

Weak imports, imports from system libraries and inspection that cannot be completed do not count as failures. Release numbers, vendor strings and lists of tested versions play no part in the decision.

When a translator cannot load, Play uses the same engine from the selected CrossOver or Template instead. If that runtime has no such engine, Play uses the runtime's automatic choice, as it also does when a saved choice is no longer installed. The saved choice stays selected for later launches, and a warning and the inspector show the selected engine, the engine actually used and the reason.

## Inspector

Each launch records the translators that were resolved, the selected files with their content hashes, and the API that each file was placed for. PE import tables and Mach-O dependency and symbol tables are kept in the shared inspection cache.

For CrossOver, Sikarugir and WineCX games alike, the inspector shows one row for each Direct3D version from 8 to 12, the Vulkan driver and video codecs, in the form **selected → used**. When the choice is also what runs, the row names it once. An automatic selection reads **Automatic** before the component it uses, as in **Automatic → MoltenVK 1.4.2 · WineCX · Intel (Rosetta)**; when the runtime decides without a component that MacLauncher can name, the row reads the runtime's automatic choice once, as in **WineCX's automatic choice**. A default Direct3D engine without a library for an API, such as DXMT for Direct3D 9, leaves that API to the runtime's automatic choice. The Vulkan driver used ends with the CPU build that the Wine process loads, such as **Intel (Rosetta)** or **Apple Silicon**, as described in [CPU build labels](#cpu-build-labels).

Play records its rows together with the translator settings and the Wine installation they were resolved for. While those are unchanged, the inspector shows the recorded rows, including the results of Play's file checks. Before the first launch, after a translator setting changes, or after a different Wine installation is selected, the rows come from the current settings and the installed descriptions instead. When the selected runtime is not installed, the recorded rows remain. Until the game's current rows arrive, a game with recorded rows shows a single pending **Translators** line in place of rows that may describe other settings, and if the runtime returns no status, the line reads **Unavailable**. A plain reason appears under a row only when the two sides differ or when the selected Vulkan driver keeps DLSS from being forwarded:

| Situation | Reason shown |
| --- | --- |
| A saved choice is no longer installed; its row reads **Saved selection (unavailable)** | This saved choice is unavailable. The runtime's current fallback will be used. |
| CrossOver's automatic renderer still applies to the API | CrossOver keeps its automatic renderer until every Direct3D row has a usable choice. |
| Two choices would place different files at one library location | This choice needs its own copy of a library that the Direct3D 9 choice provides, and a game can load only one copy. The sentence names each API whose choice provides the other copy. |
| A file check shows that the choice cannot load | The failed check, such as a missing file |
| MacLauncher's DXVK or vkd3d-proton with the automatic Vulkan driver | MacLauncher's DXVK uses MacLauncher KosmicKrisp. The sentence also names vkd3d-proton when the game uses it, and while the package is missing it adds that Play installs it after consent. |
| A DXVK 1.x pairing on a Mac without Metal 4 or a physical Apple GPU | KosmicKrisp needs Metal 4 and a physical Apple GPU, so MacLauncher's DXVK uses MacLauncher's MoltenVK build. |
| DXVK 2.0 or later, or vkd3d-proton, from Runtimes when MacLauncher KosmicKrisp cannot run or its download was declined in this Play | This DXVK version needs MacLauncher KosmicKrisp, which needs Metal 4 and a physical Apple GPU. For vkd3d-proton the sentence begins with "vkd3d-proton", and after a declined download it ends with "which is not installed." The Direct3D row uses the runtime's automatic choice. |
| A selected Vulkan driver that cannot forward DLSS frames, for a game that would otherwise forward them | This Vulkan driver does not forward DLSS frames. |
| Any other fallback, such as a component without that API's library | This choice cannot load with the selected runtime. Its included copy or automatic choice will be used. |
| A record from an earlier MacLauncher version without a structured reason | The recorded runtime used a different choice. |

Runtime Settings shows the same sentence under a control's label while its selected choice is not used.

When CrossOver makes its own automatic choice and has not resolved which engine that is, the row stays labeled as CrossOver's automatic choice. Once any Direct3D library is placed for a CrossOver game, CrossOver runs with WineD3D, and each Direct3D API without a placed library of its own shows CrossOver's WineD3D as the engine used. Camera support, DLSS and graphics effects use the components that each API actually uses after any fallback. Selecting an API does not by itself provide NGX interception through Vulkan or KosmicKrisp.

## Environment variables

Each translator has global environment variables in **Settings → Environment variables**, which a game's Runtime Settings can change for that game. A game receives the variables of the translators that it actually uses after any fallback. [Translator environment variables](TRANSLATOR_ENVIRONMENT.md) lists each translator's suggested and locked variables.
