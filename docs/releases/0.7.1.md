MacLauncher 0.7.1 keeps Direct3D games that use DXVK 2.0 or later on the runtime's own automatic choice when MacLauncher KosmicKrisp cannot be used, since these DXVK versions cannot start on a MoltenVK build. DLSS forwarding through DXVK and vkd3d-proton now registers its NGX core where the game's NGX library looks for it, and it also passes the Streamline camera, so FSR 2 and FSR 3 work on that route. On CrossOver, choosing CrossOver's own D3DMetal for Direct3D 12 now runs the game on CrossOver's D3DMetal renderer instead of stopping Play.

The app includes graphics 0.3.13.

- With the automatic Vulkan driver, a DXVK 2.0 or later or vkd3d-proton version from Runtimes no longer falls back to MacLauncher's MoltenVK scene support build, on which these versions cannot create a device. On a Mac that cannot run [MacLauncher KosmicKrisp](https://github.com/procrastinine/maclauncher/blob/v0.7.1/docs/runtimes/KOSMICKRISP.md#selection-and-loading), or in a Play whose KosmicKrisp download is declined, those Direct3D versions render with the runtime's automatic choice and its own Vulkan driver, and Play installs nothing for them. The offer's skip button names that choice, such as **Use CrossOver's Automatic Choice**, and the inspector's Direct3D row gives the reason. A DXVK 1.x build made for MoltenVK, such as DXVK-macOS, keeps the MoltenVK scene support pairing and its **Use MoltenVK** button.
- On the [DXVK and vkd3d-proton DLSS route](https://github.com/procrastinine/maclauncher/blob/v0.7.1/docs/graphics/INPUTS_AND_ADAPTERS.md#dlss-through-vulkan-translators), Play now writes the NGX core location, the `FullPath` value under `HKLM\Software\NVIDIA Corporation\Global\NGXCore`, in CrossOver bottles and in Sikarugir and WineCX prefixes. The game's NGX library then loads the forwarding core staged in `system32`. Before, only the D3DMetal route wrote this value. Play reads a stopped prefix first and writes the value only when it is missing, in any spelling of the key, so a prefix that already holds it starts no Wine.
- On the same route, a game with a compatible Streamline interposer (`sl.interposer.dll`) gets MacLauncher's Streamline adapter in its launch folder whenever its DLSS frames are forwarded. This needs no setting and, unlike the DXMT route, no DXMT library. The adapter passes the camera from the game's Streamline constants to the forwarding core under whichever of `nvngx.dll` and `_nvngx.dll` the game's NGX loaded. Because the launch and the graphics inspector then declare camera projection, [FSR 2 and FSR 3](https://github.com/procrastinine/maclauncher/blob/v0.7.1/docs/runtimes/CROSSOVER.md#temporal-upscaling) are available as temporal upscalers on this route.
- On CrossOver, choosing the D3DMetal included with CrossOver for Direct3D 12 no longer stops Play with "The selected DXGI provider has no compatible Direct3D 10/11 libraries." When the default Direct3D engine is automatic, inherited or that D3DMetal and no other Direct3D API has its own choice, the game runs on [CrossOver's own D3DMetal renderer](https://github.com/procrastinine/maclauncher/blob/v0.7.1/docs/runtimes/TRANSLATORS.md#selection), as it does with a D3DMetal default Direct3D engine. This D3DMetal has no Direct3D 10 library, so MacLauncher no longer places its libraries for the game.
