# Game inspection and source tools

MacLauncher exposes inspection, extraction and decompilation in each game's inspector. The tables below cover every game module and its primary runtime IDs. Compatible Windows and Intel Mac execution providers are described separately because selecting an execution provider preserves the detected engine's tools.

Inspection reports describe the original data. Extraction preserves stored resources or scripts. Decompilation reconstructs readable code from compiled data and can lose names, comments or control structure. Native C pseudocode describes machine code; it does not reconstruct an original C++, C#, Haxe, Swift or Objective-C project. These outputs do not change which runtime can play a game.

Tool downloads follow an explicit action or installation request and require consent when missing; catalog discovery for a missing tool follows that consent. Installed tools and their required hosts are reused offline. Each tool command log rotates to one previous log when it reaches 8 MiB. Detection, status and runtime selection do not refresh upstream catalogs. Exports normally belong to the game's launcher data directory and retain original game files. Near Infinity is an external editor: saving edits there can modify original resources.

## Runtime and provider relationships

| Runtime or provider | Inspection and decompilation relationship |
| --- | --- |
| `sikarugir`, `crossover` | Compatible Windows games can retain their detected engine module while selecting either Windows execution provider. Unity, GameMaker and visual-novel tools continue to use the detected engine/data format. A generic Windows entry instead exposes native binary inspection. Windows-only auxiliary tools such as alice-tools, WolfTL, UberWolf and hlbc run in separate private tool environments; their environment is independent of gameplay. |
| `mac32` | Added as an execution alternative for eligible original Intel 32-bit Mac applications. The detected engine's tools remain attached to that engine. A dedicated `mac32` entry has native binary inspection. This provider does not make Windows or ARM binaries executable. |
| `java` | Temurin LTS lines **8, 11, 17, 21 and 25** are independently selectable for games. Bytecode minimums and JNI CPU requirements constrain the selected host. Vineflower, JADX, Apktool, FFDec, Near Infinity and unluac select their own compatible managed Java host; changing a tool's host does not change a game's selected Java line. |
| `klepton` | The MacLauncher Android manager groups **JVM** and **ART** execution packages. JVM uses the adapted Klepton host and converted application bytecode; ART uses Android's original runtime and its matching framework/system-image inputs. Both use the same package inspection and decompilation actions and shared per-game application data, with separate generated-code caches. |
| `macapk`, `aim` | Separate managed Android providers, with separate delivery and execution requirements. Mac.apk and adapted AIM do not replace JADX/Apktool. APK inspection/export is available without claiming that the inspected app can run on either provider. |
| `electron` | Uses the launcher's Electron browser host for supported HTML engines. Shipped JavaScript remains inspectable; a runtime host does not recover absent authoring sources. |
| `nwjs`, `nwjs-patched` | Use managed NW.js releases; `nwjs-patched` applies the module's compatibility preparation to the same game format. NW.js/SDK debugging facilities depend on the selected package. Extraction actions remain owned by the engine module. |
| `native` | Runs a supplied compatible macOS application/runtime where that module exposes the choice. It does not imply the Electron/NW.js debugging interface, source recovery or a portable engine implementation. Engine tools operate on the identified original data independently. |
| `inspection`, `bgi-tools`, `catsystem2-tools` | Inspection routes retain their module's tools without providing a native game interpreter. When none of a module's own runtimes can launch the game, a compatible Windows executable plays through a registered CrossOver application or, otherwise, Sikarugir, with these tools still available. |
| `projector`, `ruffle`; `unity`; `godot`; `love`; other engine runtimes | Player compatibility and decompiler compatibility are separate. A working export does not establish game playback, and a playable game can still contain a script/asset version unsupported by a selected inspection tool. |

## Included readers and direct source access

These production readers and helpers do not need a separate decompiler download. Runtime-specific extraction or compilation can still require its selected managed engine package.

| Included component | Modules and output | Concrete boundary |
| --- | --- | --- |
| Package/archive readers | Construct, Tyrano, Ren'Py, RGSS, LÖVE and supported HTML/application layouts expose stored members through their module actions. | Archive extraction preserves stored bytes; it does not itself reconstruct source from bytecode. Safe paths, format bounds and supported encryption determine readable content. |
| Ren'Py archive/configuration and save-metadata readers | `renpy`: RPA/RPI metadata, literal source/compiled configuration and ZIP/JSON save facts. | Compiled configuration uses inert records, without executing pickle reducers or game Python. Save inspection does not deserialize the game's object graph. RPYC source reconstruction is supplied separately by unrpyc/UnRen. |
| Ruby Marshal/script-table readers | `rgss`: scripts, database/save records and explicit edited-script repacking. | Supported Marshal types are inspected as data. Arbitrary Ruby classes/code are not executed to recover unknown behavior. |
| Inno Setup installer reader | Import: [innoextract](https://github.com/dscharrer/innoextract) unpacks supported Inno Setup offline installers before ordinary engine detection. | A package extractor rather than a game-code decompiler. It reads unencrypted payloads; the managed reader downloads after consent. |
| LCF database/map readers | `easyrpg`: project JSON, text and event records. | RPG Maker 2000/2003 format records are not general-purpose source code. |
| WOLF archive reader | `wolfrpg`: member lists and supported asset extraction. | Pro/key variants requiring UberWolf use that managed tool; the included reader does not guess unknown keys. |
| KIF cipher and CatScene/CSTL/FES/HG-3 readers | `catsystem2`: decrypted archive members, typed script/transcript data and supported lossless images. | The universal cipher helper is included. Only recognized key resources/layouts are decoded; scripts are inspected rather than executed. |
| BGI, XP3, NScripter, MPK/SC3, NPA/NSS, HCB and AI5 metadata readers | Their visual-novel modules expose archive/program metadata and the specific script exports listed above. | Supported format versions, encodings and encryption differ by engine. Message extraction, constant pools and original bytecode exports are distinguished from reconstructed high-level source. |
| Android and iOS package readers | `android`: APK manifest/resources/signing/native-library metadata; `ios`: IPA plist, bundle, entitlement, Mach-O and encryption metadata. | Package inspection does not decompile native code, run application code or remove encryption. JADX, Apktool and Rizin/Ghidra are separate managed actions. |
| Managed PE, Mach-O, ELF and version readers | Unity/FNA, native/mobile modules and engine detection retain original executable/assembly/architecture facts. | A reported product version is distinct from an established engine/runtime version. Header inspection alone does not recover implementation code. |
| Direct text files | Web-family JavaScript/HTML/CSS/JSON, VNDS scripts, Ikemen definitions and plaintext Lua/NSS/Ruby/KAG files. | Already-readable source can be inspected without a decompiler. Minification, obfuscation and absent authoring data remain limitations of the shipped files. |
