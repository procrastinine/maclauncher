# Frame sources and runtime adapters

[Pipeline overview](PIPELINE.md) · [Graphics guide](README.md)

A runtime connects to MacLauncher's graphics processor through a frame adapter. The adapter hands each completed image to the processor, together with any matching scene data the renderer supplies. Graphics support follows the frame producer, the code that actually renders the frames, not the game type or the CPU architecture, and runtime or CPU names never select separate effect implementations.

This page describes each frame source and scene producer, the module contract for launching a game with graphics, renderer input declarations, attachment hosts and completed-window capture. [Renderer integrations](SHARED_PROCESSING.md) describes which runtimes supply scene data and render-size control.

[Frame sources and scene inputs](#frame-sources-and-scene-inputs) · [Module launch entry points](#module-launch-entry-points) · [Renderer input declarations](#renderer-input-declarations) · [Attachment hosts and CPU architecture](#attachment-hosts-and-cpu-architecture) · [Completed-window capture](#completed-window-capture) · [Picked windows and displays](#picked-windows-and-displays)

## Frame sources and scene inputs

A runtime's `graphicsHost` declaration selects an attachment contract. It does not identify the frame source that the game actually uses while rendering. A Java game, for example, can present an OpenGL framebuffer, a Metal drawable or a software bitmap. Wine can present Metal through a Direct3D translator, or OpenGL through WineD3D. These routes use the same adapters as native applications.

CrossOver and Sikarugir resolve their shared translator plan before graphics preparation. ReShade binds only the component records that the plan actually uses after fallback; an unresolved vendor automatic choice stays unresolved. Metal and OpenGL output retain their existing presentation adapters, and depth, motion and camera inputs come from the active frame supplier. Translator names do not create scene data or select a separate effect implementation. Running edits and screenshots retain the launch's resolved plan; a later saved translator choice applies to a later launch.

The shared image pipeline receives completed color images. A frame source can be direct access to the render target, an operating-system window stream, a texture the runtime supplies, or an upload of a software image:

| Frame source | Attachment and GPU handoff | Scene data this route supplies |
| --- | --- | --- |
| Native Metal drawable | `metal.mm` intercepts the selected drawable and its command buffer. Eligible size-preserving FX can run in place, and other chains use owned presentation, in which the processor presents the output itself. This route also covers Metal output from Java and from Wine translators. | Matching depth from a supported render pass, when requested. A Metal drawable alone supplies no motion vectors, jitter or camera projection. |
| Hardware OpenGL framebuffer | `opengl.mm` and `opengl-interop.mm` receive the game's flush, copy its framebuffer into CoreVideo/IOSurface GPU images and submit Metal processing. This includes compatible Java OpenGL and WineD3D output. | Matching default-framebuffer depth, when present and requested. No game motion vectors, jitter or camera projection are inferred. |
| Core Animation surface | `window.mm` and `layer-presentation.mm` receive published IOSurfaces or supported layer images. The adapter accepts only a full image of the selected window, because a compositor tile is not a complete frame. | Composed color only. |
| Completed software bitmap | A supported `CGImage` layer publication, or a complete bitmap drawn during the selected view's `drawRect:`, is uploaded to a reusable IOSurface. Later effects run on the GPU. | Color and image geometry only. The software producer's original pixels are already in CPU memory. |
| Browser window stream | Dedicated Electron and NW.js hosts can use `browser-frame.mm` when native compositor surfaces do not provide the complete window. ScreenCaptureKit supplies the selected window's composed image, and CoreVideo and GPU copies hand it to the shared processor. | Composed color only, with no renderer depth or motion vectors. |
| Picked window or display | `window-source.mm`, driven by the `maclauncher-graphics-window` helper, captures a window or display chosen in the Apply Graphics window or the macOS content picker and presents the processed image in an overlay window over it. | Composed color only, at the window's pixel size, with no source-resolution control, depth or motion vectors. |
| Explicit runtime textures | A runtime calls `rsProcessFrame`, its depth variant or the presenter API with its own Metal textures and synchronization. Android presentation integrations use this contract. | Color, plus only the matching inputs that the producer explicitly supplies. A graphics host declaration alone adds no scene data. |
| Native mpv processing | mpv applies compatible shader prefixes and scaling to its decoded video, with the original video planes and decoder color metadata. Shared effects after that prefix receive the RGB image mpv produced, through the player's actual Metal or OpenGL frame adapter. | The original video planes belong to the mpv prefix. Later shared effects get composed RGB, with no game depth or motion vectors. |
| Decoded GPU video host | `video/native/mpv-render.mm` keeps decoded GPU surfaces and submits them to the shared graph before window fitting. Paused redraws keep the content identity. | Decoder color and format metadata, content identity, source PTS and media duration; no game scene data. |
| Offline video frames | `video-frame.mm` and `graphics-video.mm` import decoded sample buffers as GPU textures for the shared frame API and pass the completed output to the encoder. | Decoded color and media timestamps; no game scene inputs. |

### Presented extent

Owned presentation keeps the source layer's mapping of image to bounds. When a Metal drawable's or Core Animation surface's layer stretches the whole image over its bounds (resize gravity, the full contents rectangle and centered), the output is presented at the view's backing size. Any other mapping, such as Java's top-left drawable that is taller than its view, is presented at the producer's own image size with the same gravity, contents rectangles, contents scale and orientation. Processing therefore never rescales the image or shows pixels that the original layer clips. When the drawable's resolution is reduced, the presented size stays at the size the producer requested.

### Window capture

Two frame sources capture with ScreenCaptureKit. The browser window stream is turned on through the authenticated per-launch channel that `shared/web/runtime/browser-graphics.js` creates for dedicated browser hosts; a `graphicsHost: "window"` declaration does not open that channel for arbitrary Java, Wine or native applications. A [picked window or display](#picked-windows-and-displays) is captured only after a choice in the Apply Graphics window, the macOS content picker or the window graphics shortcut. ScreenCaptureKit shows the macOS sharing indicator while its stream is active. Direct Metal and OpenGL interception does not use that stream. GPU texture copies on either route involve no CPU pixel readback and no recording files. [Completed-window capture](#completed-window-capture) describes the stream itself.

### Color and alpha

Color shaders, processing of derived luma and chroma, resize rows and compatible image-based neural effects all use the common color contract. Frame generation from color pairs also needs consecutive images and an owned presentation timeline. Their image processing can therefore be shared across producers.

Opacity belongs to the producer's frame contract. Opaque display images keep all RGB pixels even when their stored alpha is unused or zero. Transparent images keep their declared straight or premultiplied alpha through compatible filters, including libplacebo processing. The selected model or provider still sets its own color, format and platform requirements. Original subsampled decoder planes stay distinct from luma and chroma derived from a composed RGB image.

### Scene producers

Scene effects have a separate input boundary. A scene producer supplies the renderer data for one scene frame:

| Scene producer | Supplied data | Processing boundary |
| --- | --- | --- |
| Original MetalFX temporal call | The actual color, depth, motion, jitter and output of the intercepted scaler call; camera data only when supplied separately. | A record from the same command buffer ties the original scene to its exact output. Replacing the scaler in an ordered chain also requires the supported acquired-drawable output contract. |
| Godot renderer integration | The helper registers the actual projection and renderer resources, and the matching original MetalFX call supplies its command buffer and jitter. | The bridge hands that matched scene to the shared processor. Registering metadata alone creates no scene producer for another renderer. An ordinary window attachment keeps its frame-adapter inputs. |
| Streamline through the DXMT bridge | The game's actual tagged resources and supplied camera and projection constants. | The API adapter translates the game's scene request and keeps its resources for each context. The native reconstruction method that runs is reported separately from the API the game called. |
| XeSS D3D11 through the DXMT bridge | The game's actual color, depth, motion, jitter and exposure. The XeSS interface itself supplies no camera projection. | Compatible requests enter the MetalFX producer and the shared ordered scene boundary. The native method that runs is independent of the API the game called, and methods that need projection data need a producer of that data. |
| Explicit temporal frame API | The caller's matching textures, camera and scale data, flags, frame identity and command buffer. | `rsProcessTemporalFrame` validates the selected provider's actual inputs. |

The D3D11 Streamline adapter copies `OnlyValidNow` input tags on the owning GPU context before the original tag call returns. These snapshots keep the exact region, format and frame identity through evaluation and GPU completion. Longer-lived tags keep their original resources. When optional shared processing cannot get the resources it needs, both DXMT routes keep the original SDK call and its output.

Compatible in-game XeSS D3D11 translation is selected independently of optional shared postprocessing. When postprocessing is off, it keeps the original game DLL and the game's base upscaling. D3D12 and Vulkan translation needs a translator that exposes matching textures and command insertion, and those game routes keep their original libraries. In-game XeSS API translation is a renderer compatibility feature, and it reports which Mac reconstruction algorithm actually runs.

An engine adapter produces data; it does not decide which effects are eligible. Godot's scene supplier attaches to viewports in the native window, while offscreen viewports keep their own compositor and scaling. The shared completed-image path stays available, and a matching scene frame from another producer can use the same compatible reconstruction or generation provider. [Godot](SHARED_PROCESSING.md#godot) describes the user-facing behavior. Depth-only filters, scene reconstruction and scene generation each declare their own required inputs. Camera matrices, exposure, reactive masks and HUD-free color are separate optional or required resources for each operation, and temporal inputs are separate from other renderer inputs such as normals, albedo and lighting buffers.

### XeSS compute hosts

The scene producer and the algorithm that runs are separate choices. Intel XeSS is a temporal upscaling implementation in the shared graph, and the game's CPU architecture and original upscaling API do not decide whether it can run. [XeSS](PROVIDERS.md#xess) lists its inputs and host routes.

The D3D12 implementation runs the unmodified Intel runtime in an isolated compatible compute host. Metal GPU commands hand the scene over through shared images and aliased D3D12 buffers, and the launcher carries only setup metadata. Backend selection is part of the row's XeSS Options.

- The launcher watches for compute-host setup requests only while a prepared plan has an enabled XeSS row or one of its hosts is still running.
- When a live update is rolled back, the watch state of the plan that keeps running is restored. A plan with an XeSS row keeps the watch, and a plan without one stops it at once when no host is running.
- Launch preparation and live edits each register their XeSS hosts and bind them to the running process. The host table written for the launch keeps every route and names its latest registration, and each setup request is claimed exactly once, by the registration its route names.

### Depth

Depth alone allows compatible depth shaders but does not make temporal upscaling possible. Window framebuffer depth, drawable depth and explicit depth images carry no camera projection, so they are copied only for rows that read depth alone. Image filters that unproject depth need a projection from the renderer; without one, they are bypassed with the reason that the frame source supplies no camera projection.

Depth images have the same orientation as their color image and keep the renderer's depth range and encoding. ReShade `.fx` rows interpret reversed, logarithmic or rescaled depth through the game's [depth-input definitions](EFFECT_PLANS.md#depth-input).

Scene frame generation has its own depth, motion, camera and history requirements. Flow or motion that an image-pair generator or a neural model estimates from the images, including the motion field of MetalFX image interpolation, is never passed on as game motion vectors. Generated color frames do not gain matching renderer guides just by keeping the source frame's identifier.

### Source size

Changing the game's render size is separate from processing. Downsampling after rendering changes the submitted image. Engine controls or the virtual-source protocol can change the producer's allocation, but only after the producer acknowledges the requested size. Neither window-stream dimensions nor the final output fit show that the game renders to a smaller target. [Game render allocation](FRAME_API.md#game-render-allocation-and-processing-extent) describes the source strategies.

## Module launch entry points

A runtime entry declares its `graphicsHost` in module metadata. The launcher prepares the shared processor through `context.getGameEffectsEnvironment()`, and `context.applyGameEnvironment(base)` combines that environment with the game's existing environment. Engine-specific renderer selection stays in the module.

The library UI and `scripts/run-game.mjs` both launch through `createLauncher().launchEntry`, and direct module hosts get the same game context from `getGameLaunchContext(entry, settings, options)`. Action contexts use `getLaunchContext` and leave game effects off. The game context handles lazy preparation, runtime graphics metadata, merging the selected libraries and the final process handoff. A module may replace the context's graphics getter with the scoped environment its sandbox produces before it calls `spawnDetachedChecked`. Callers never prepare or merge a second graphics environment.

### Code-signature check

Before the final native handoff attaches the shared processor, it checks the executable's code-signature policy. Three signing facts confirm a restriction: the hardened runtime without the `com.apple.security.cs.allow-dyld-environment-variables` entitlement, the restrict flag, and library validation that does not admit the processor library. When the game's plan needs processing, a restricted executable runs from a [private copy](#private-copies-of-restricted-apps) of its app instead. When the plan needs no processing, or the copy cannot be used, the game runs without the attachment and its launch binding records the reason. An executable whose signing facts are unknown stays eligible. A launch transport can supply `graphicsExecutable` with its actual executable, or `null` when the descendant process is unknown; this metadata is read before the process is created. Rosetta wrapping happens after the check.

### Private copies of restricted apps

A private copy lets the shared processor attach to an app whose own signature refuses it, without changing the original. It covers the outermost app bundle that contains the restricted executable, or the executable alone when it is not inside a bundle, and it lives in the game's data folder at `games/<gameId>/effects/app-copy/`.

- Each Mach-O program in the bundle whose signature refuses the processor is copied and signed ad hoc, without the hardened runtime, restrict and library-validation flags. When a program is the main executable of a bundle, that bundle's `Info.plist` is copied as well and the bundle is signed as a whole. Nested code is signed before the bundles that contain it.
- Each signed program keeps its entitlements, except the restricted ones that only a provisioning profile can grant: `com.apple.developer.*`, `com.apple.application-identifier`, `keychain-access-groups` and `com.apple.private.*`. An ad hoc signature carrying them would stop the program from launching. The launcher log names the entitlements that a copy leaves out.
- The re-signed programs and copied `Info.plist` files are APFS clones of the originals when both are on one APFS volume, and ordinary copies otherwise. Every other file and folder in the copy is a symbolic link to the original, so libraries, resources and game data are read and written in place, and only the re-signed programs take new disk space. Links beside the signed copy point to the items beside the original app, for programs that find their data relative to their bundle. While the folder that holds the original app is unchanged, its recorded identity is reused without listing it again or updating the links.
- The copy keeps the original bundle identifier, so preferences and save locations stay the same.
- In the process handoff, only the command changes, to the copied executable, and the code-signature check runs again on it. Arguments, the working directory and environment values keep the original paths supplied by the game module. Steam identification and launch arguments are prepared from the original app before the handoff.

Before each launch with processing, the listing of each copied folder and the size, modification time and inode of each copied file are compared with the original and with the copy. A copy that still matches is reused. An app update, or a change to the copied code, rebuilds the copy before the game starts, so a re-signed program never runs with the resources of a newer version. A program that derives a write path from its own executable or bundle can still create files in the copy's real directories; retaining the original working directory does not redirect those paths. Files and folders that the game created there, and links that it replaced, are carried into the refreshed copy. Preparation leaves the earlier copy intact until the replacement and its record are committed; an interrupted replacement restores the earlier copy.

When a refresh finds that a copied executable or `Info.plist` has changed, it keeps the changed file under its relative path in `effects/app-copy/recovered/<snapshot-id>/files/`, with a record of its identity. The refreshed copy still runs code from the current original app. These snapshots are never launched, and the launcher never rewrites them or removes them automatically.

A launch whose plan needs no processing, or whose app no longer refuses the processor, runs the original app. Its copy is removed only when every remaining entry belongs to the launcher and matches its record. Copies containing game-created entries, replaced links or modified files remain in the game's data folder. Each removal goes through the launcher's [guarded trash](../development/DATA_MODEL.md#derived-data-upkeep), and removing the game from the library removes the copy with the rest of its data.

An app that uses the App Sandbox is not copied. macOS ties a sandboxed app's data container to its code signature, so a re-signed copy would need permission to open the original container or would not start. Such an app runs from the original with its original rendering, nothing is written to its copy folder, and its launch binding records that reason.

### Process adapters

An optional `processAdapter(command, args, options, needsRosetta, spawn)` wraps the final handoff for inherited instrumentation. The `spawn` continuation it receives keeps the selected graphics environment, network policy and process ownership. Component callers can supply `graphicsRuntimeRoot` for verified preparation assets and `presentationLibrary` for the processor library to call. Ordinary launches use the included selection.

### Diagnostics

Four boolean `graphicsDiagnostics` fields (`diagnostics`, `capture`, `gpuTiming`, `trace`) configure the same preparation path without changing the saved plan. Detailed diagnostics, GPU timing and frame capture are opt-in:

- When a graphics package declares `features.graphics.screenshotAPI: 1` and diagnostic capture is off, a live launch configures the same frame capture channel in its final-image mode (`RESHADE_CAPTURE_FINAL=1`) for processed screenshots. That mode reads back only the final processed image of one requested frame, before the performance overlay is drawn, and never attaches processing by itself, so an idle or Off game keeps its dormant path. Frame capture writes 8-bit images. When the final image has another format, such as RGBA16Float, a 10-bit format, PQ or HLG, it is converted once with the output color encoder to 8-bit sRGB at the image's reference white. The shared presenter converts its drawable, which is described by the output color, and in-place processing converts the game's target, which is described by the game's image color. The conversion applies the Automatic output mapping, which compresses content above that white when the output can hold it. The launch record holds the channel as `screenshotCapture`. A runtime sandbox that moves the capture prefix and request file into its writable folder rewrites `screenshotCapture` in the launch record to the moved paths. The launcher writes the request file named there, waits up to five seconds for the completed capture, converts its staged pixels to PNG, moves the image to the screenshot folder and removes every file the capture staged.

- Disabled diagnostic entry points read cached enable flags and create no recorder state, writer thread, output file or GPU query.
- Enabled recorders use fixed-size queues, and render callbacks drop records rather than wait for a writer lock.
- Diagnostic file writes verify process and file ownership and stop on failure. They are independent of source acknowledgments and graphics control metadata.

Capture readbacks retain their Metal buffers until a private serial utility queue has written the pixels. Metal completion callbacks perform no image encoding or file writing. The injected process stages packed 8-bit pixels in `-before.rgba` and `-after.rgba`; final-image mode stages only the latter. The launcher converts those files to opaque sRGB PNGs before saving a screenshot, honoring their RGBA or BGRA channel order and top-down or bottom-up row flags. Diagnostic callers use `screenshots.convert(prefix)` to convert the staged pair, including an optional `-neural-input.rgba` capture. Existing PNG captures from older graphics packages remain readable.

Each raw file starts with the eight ASCII bytes `MCLCAP01`, followed by four little-endian 32-bit fields: width, height, packed row stride and flags. Flag bit 0 marks BGRA channel order; bit 1 marks bottom-up rows. All other flag bits are zero. The stride is exactly four times the width, followed by exactly `stride × height` pixel bytes without padding. Each dimension is at most 32768 and each image contains at most 256 MiB of pixel bytes. A per-request temporary file is renamed only after its complete contents have been written; abandoned requests do not publish an image.

Failures of warning and informational notifications, including rejected asynchronous notifications, are contained separately from preparation and live updates. Rendering never waits for these notifications.

### Native prefix routing

A module can export an optional asynchronous `prepareEffectsEntry(entry, context)` hook, which returns the entry that shared processing uses. The hook keeps the supplied entry and removes only the work that the original renderer performs. The launcher passes it to effect preparation as `options.prepareEffectsEntry`, and uses `context.effectsEntry` for the same selection at launch. Main-process validation, live controls and shared plan preparation work on the resulting runtime entry, while the saved game keeps its complete settings and plan. Runtime-specific routing stays in the module. The video module uses this hook for [native video prefixes](SHADERS_AND_MEDIA.md#native-video-prefixes).

## Renderer input declarations

A module may export `resolveGraphicsInputs(entry, context)` to describe the selected renderer's inputs and native controls. The inspector shows the same metadata with runtime status. Status reads use installed metadata and never start a renderer or use the network.

| Field | Meaning |
| --- | --- |
| `nativeVideo` | The renderer supplies decoded video planes. |
| `nativeSpatialMethods`, `nativeSpatialMethodLabels` | The original renderer's filter registry. |
| `sourceResolution` | `false`, or an explicit capability object with `heights` and `multipliers`. Its `control` can identify a source adapter owned by the engine, and the optional `methods` and `methodLabels` list the source renderer's scaling filters and their display names. |
| `shaderBindingsNextLaunch`, `spatialBindingsNextLaunch` | Settings that are bound when the process starts. |
| `architecture` | The actual architecture, when it depends on the selected runtime. See [CPU architecture](#cpu-architecture). |

Source sizing uses explicit heights or divisors, and explicit frame producers keep the divisors they advertise. Native window adapters without a `sourceResolution` declaration keep the producer's allocation unless an included virtual-window adapter is advertised. `features.graphics.virtualWindowAPI: 1` exposes `GraphicsCapabilities.virtualWindow` and its supported source factors to the window host. Explicit source declarations take precedence, and `sourceResolution: false` and native video leave out the virtual-window fallback. The UI reads these capabilities and never assumes that an arbitrary drawable can be resized.

Simple neural processing starts with a 720-pixel input height. An available source adapter may apply that height before completed-frame processing, and smaller natural inputs keep their size. The `virtualSourceAutoAPI` and `automatic: true` source protocol stay compatible with older prepared consumers, but they add no Automatic choice to Downsample. Historical automatic graph extents become an explicit 540-pixel height, so the editor and execution use the same dimensions.

## Attachment hosts and CPU architecture

| Host | Frame source | Ownership |
| --- | --- | --- |
| `window` | Supported native Metal, hardware OpenGL, Core Animation and completed Quartz bitmap frames | The adapter selects the game window and holds its source until GPU reads finish. |
| `remote` | Hosted browser surfaces | The producer supplies its surface and presentation timing. |
| `explicit` | Metal textures supplied by the runtime | The runtime controls ordering, frame identity and submission. |
| `catalyst` | Supported iOS application Metal layers | The adapter preserves the drawable and application lifecycle. |

The host's renderer connects through its declared presentation adapter. Inspection and extraction tools run independently of presentation hosts.

### CPU architecture

Rosetta changes the instruction set of the process that loads the graphics core, not the frame source. An x86_64 Wine or Java process can use the same Metal or OpenGL adapters as an ARM64 process. Neural execution that only exists for ARM64 goes through the GPU helper, and MetalFX availability follows the actual device, OS and framework support. None of these declarations is a list of allowed renderers for each game.

Optional `graphicsArchitecture` metadata names a fixed host architecture, `arm64` or `x86_64`. It describes the process that loads the graphics library, which can be a translated Intel host. Renderer input metadata can supply the actual `architecture` when it depends on the selected runtime. Provider architecture checks use this value, never an engine name.

- A native app bundle without recorded executable metadata resolves its declared bundle executable before its Mach-O slices are inspected.
- Explicit renderer and runtime architecture declarations take precedence, and the architecture of a script stays unspecified when it is unknown.
- A scripted launcher can pass `{needsRosetta: true}` to `context.getGameEffectsEnvironment` or `context.applyGameEnvironment` before it prepares the child environment. This selects the Intel graphics contract for the actual translated executable, including optional provider validation.
- Changing the architecture after the game process is bound is rejected.

### Bitmap and OpenGL lifetime

Metal adapters hold GPU textures directly, and hardware OpenGL adapters use the shared texture and surface bridge. For supported layers that publish `CGImage` contents, each completed software image is uploaded into a reusable IOSurface pool of fixed size, and shader passes and intermediate images then stay on the GPU. A bitmap image carries color, dimensions and timing but no scene depth or game motion vectors.

The Quartz adapter can also keep a full bitmap published during the selected content view's original `drawRect:` call and submit it after drawing finishes. Individual drawing calls and dirty rectangles are not complete frames. Direct Quartz drawing that does not publish through a supported frame adapter is outside that adapter's contract.

When an OpenGL context is retired, graphics ownership is removed before driver cleanup is attempted. An unavailable context leaves its GL objects to native destruction, and independent host resources are released without choosing another context for deletion.

## Completed-window capture

A completed-window adapter captures the selected original window when native ingress supplies only incomplete compositor surfaces. Its capture core, `window-stream.mm`, also serves [picked windows and displays](#picked-windows-and-displays). It uses an independent ScreenCaptureKit window source, GPU texture copies and the shared processor, and on macOS 14.4 and later it can capture in the background. Capture starts only while processing is active and does not need the game in front. Producer throttling can still limit how many fresh source frames arrive. A browser helper whose sandbox refuses the effects plan path accepts no native full-window surface, so the completed-window adapter in the launcher-side process, which reads every edit, processes that window.

Capture is limited to the game window:

- macOS shows its screen-sharing indicator while the capture is active.
- The capture filter includes the selected game window and excludes child windows. Audio capture is off.
- Frames stay in local processing buffers. Ordinary playback has no network transport and no recording file; explicit diagnostic capture can save local before and after images.
- On macOS 14.4 and later, the current process's windows are listed through Apple's consent-free API rather than broad desktop access. The indicator still shows an active capture stream.
- Turning off graphics processing or closing the game stops the capture session.

Capture errors keep the original renderer and release the failed session. A settled stream whose complete images keep a different size or pixel format from the configured window for one second counts as a recoverable capture error. Configuration changes are serialized and coalesced to the latest window geometry. A temporary failure gets a limited number of recovery attempts before the original window returns, and obsolete callbacks cannot replace a newer configuration.

For Electron windows hosted by the launcher, an in-process visibility notification keeps source animations running while the processed output is visible. Covering, minimizing, disabling or closing that output restores the previous background throttling policy. The game keeps control of its own frame timing.

GPU completion and physical presentation have separate callbacks, so covered output can complete processing without a positive drawable `presentedTime`. The opt-in `FrameCapture` records the original and final pixels of one accepted source frame after its GPU work completes successfully.

## Picked windows and displays

Window graphics apply a graphics chain to windows of other apps and to displays, each in its own library entry. [Window entries](../game-types/WINDOW.md) describes the Apply Graphics window, the entries and the saved chains; this section covers the frame path.

Two kinds of process run the `maclauncher-graphics-window` executable of the graphics runtime:

- A chain process per library entry. The `window` module's `capture` runtime starts it as the entry's process. It loads the same `libreshade-macos.dylib` a game loads, declares itself an explicit host and runs exactly one graphics chain with the code games use: the plan, presets, providers and shared presenter. Only its frame input and its overlay window are specific to windows.
- One capture service per MacLauncher process, `--capture-service ID`. It is the only process that calls ScreenCaptureKit (`SCShareableContent`, `SCStream`, `SCScreenshotManager` and `SCContentSharingPicker`). It loads no graphics library and does no GPU work.

The chain process calls the window source ABI in `window-source.h` (`rsWindowSourceAPI` 2): `rsWindowSourceCreate`, `rsWindowSourceSelect`, `rsWindowSourceSetOptions`, `rsWindowSourcePoll` and `rsWindowSourceDestroy` for each output, and `rsWindowSourceSetGeometry`, `rsWindowSourceSubmit`, `rsWindowSourceCaptureInterval`, `rsWindowSourceSetPointer` and `rsWindowSourceSetOverlays` for forwarded frames. The window module offers window graphics only when the runtime record reports `features.graphics.windowSourceAPI` 2 and the helper is published. The runtime entry keeps `graphicsHost: "window"` for its capabilities, such as live switching and adaptive generation, and adds `explicitFrames: true`, so preparation sets the explicit host and installs no load-time hooks. Live edits, the effects plan, live controls and status use the ordinary launch binding of the entry.

The source reuses the [completed-window adapter](#completed-window-capture)'s GPU slots, image budget, bounded recovery and shared presenter, without its stream, so color effects, scaling methods and image-pair frame generation apply. The frame source is reported as `external-window`. The module's renderer input declaration is `{source: "window-capture", sourceResolution: false, depth: false, motionVectors: false, methods: []}`, so source-resolution candidates and scene-input options are absent. Its `generationDefaults: {keepStaticContent: true}` sets **Keep static content** on frame-generation rows added to a window entry.

### Transport

The service and its clients exchange raw Mach messages (`window-capture-wire.hpp`, version 1). Every message carries one port descriptor and one out-of-line JSON descriptor of at most 1 MiB, either of which may be empty, and the receiver takes the sender's process ID from the message's audit trailer. A frame travels as its IOSurface's Mach port with a fixed `FrameInfo`: sequence, geometry generation, display time, width and height. Each feed has one frame in flight and at most one pending; a newer frame replaces the pending one, and the next frame is sent after the client releases the previous one. The chain process copies each surface once on the GPU, with a blit into one of its own slots, releases the frame when that copy completes and runs the chain on the slot. A frame whose generation or size differs from the current geometry, or whose time is not newer than the previous frame's, is dropped.

The service's streams use a queue depth of 6, a minimum frame interval of zero, 32-bit BGRA in sRGB, `scalesToFit` into a destination of the target's pixel size, the best capture resolution and child windows included. With a minimum frame interval of zero, ScreenCaptureKit sends a frame only when the content changes, so silence never counts as a stall: the chain keeps showing the last image and processes it again after a plan edit. The service passes a stream's frames on only when they are complete, match the configured pixel size and pixel format, and arrive no sooner than 0.75 of the plan's capture interval after the previous frame it sent; frames that keep failing the size check for one second fail the feed.

### Geometry

The service reads each target's bounds, owner, layer and on-screen state from window-server metadata ten times a second, and at once when a frame's `SCStreamFrameInfoScreenRect` differs from the applied bounds. The screen with the largest intersection with the target supplies the backing scale and the display ID. Every change raises the feed's geometry generation. The service applies it to the stream with `updateConfiguration:`, one transaction at a time, coalescing later changes, and then sends a `geometry` event, which arrives before any frame of that generation. The chain process applies the event on its main thread before it accepts the next frame. A configuration that has not settled within 2 seconds counts as an internal capture error, which the [capture lifecycle](#capture-lifecycle) handles.

### Filters

A window or display chosen in the Apply Graphics window is opened by ID. The service finds it in `SCShareableContent`, which needs the Screen & System Audio Recording permission, and builds the filter itself: a desktop-independent window filter, or a display filter. Without that permission, an app chosen in the Apply Graphics window is opened by process ID, and the service presents `SCContentSharingPicker` in single-window mode, one pick at a time. The picker is limited to that app's windows: it excludes MacLauncher and every other app by bundle identifier, and every overlay by window number. When the permission is granted, an application target opened with `frontWindow`, as the shortcut opens it, directly takes the app's frontmost on-screen window at layer 0 that measures at least 64 by 64 points; otherwise it uses the picker. A window or display that another feed already captures is refused with "This window already has window graphics" or "This display already has window graphics".

ScreenCaptureKit crops a window capture (`sourceRect`) from the bounds of the window and its child windows together and reports no offset, so a child window that reaches past the window's left or top edge would move the image by that much. For an in-place window, the crop's origin is the window's offset within the bounds of the window and its known child windows, so the image stays on the window. The chain process sends it with the feed's options (`cropX`, `cropY`) as soon as it changes (`RS_WINDOW_SOURCE_CROP_CHANGED`), and the crop takes effect with the next capture configuration, under a new geometry generation. Frames captured between a child window's change and that configuration show the image shifted, so the overlay keeps its last processed image, for at most 0.5 seconds, until a frame of the new generation arrives:

- When the [stacking check](#overlay) finds a change that moves the image, the chain drops the frames of the current generation captured since the previous check. It does the same when the check finds a window of the target's app directly above the target that covers it, because that window may be a child window that is not yet known.
- A captured frame can show a new or moved child window before that check runs. For each frame, the chain therefore compares the window numbers above the target, leaving out overlays, and the bounds of the known child windows with those from the last check, and it drops the frame when they differ.

While one of the target app's own windows at a higher layer overlaps the window, such as a floating palette, the service switches the feed to a display filter that includes only that app's windows (`initWithDisplay:includingApplications:exceptingWindows:`), cropped to the window's bounds on that display at the same size, so the palette appears in the processed image. When no such window overlaps it any more, or the window moves to another display, the filter changes again.

Display filters exclude every overlay of every chain process by window (`initWithDisplay:excludingWindows:`) and leave out the menu bar (`includeMenuBar` is off on macOS 14.2 or later), and each overlay also has `sharingType` set to none. Each chain process sends the window numbers of its overlays to the service. When the set changes, the service waits until `SCShareableContent` lists every overlay, for at most 2 seconds, updates the filter of each display feed and, once every update has settled, sends `excluded` with the acknowledged window numbers. With no display feed, it acknowledges at once. A new overlay stays hidden (`RS_WINDOW_SOURCE_HOLD`) until its number is acknowledged, so it never appears in a display capture, and its chain process sends its list again every 2 seconds while an overlay waits. The acknowledged list also tells every chain process which windows are overlays (`rsWindowSourceSetOverlays`), so another entry's overlay never counts as a window that covers a target.

### Overlay

The overlay is a borderless, nonactivating panel that never becomes key and always ignores the pointer. A display's overlay keeps the floating level, and a scaled overlay keeps the window's front level described next; both are ordered front with `orderFrontRegardless` when they appear and never ordered against the target. An in-place overlay stacks with its target. While no window covers the target, the overlay keeps the front level: the floating level, or one level above a target window that itself sits at the floating level or higher, below pop-up menus. A click or text selection that brings the target's window forward stays within the ordinary levels and leaves the overlay above it. A window covers the target when it is visible, overlaps the target, sits at or above the target's layer and below the front level, and is not an overlay. The target's child windows never cover it: the capture includes them, and the window server keeps a window's child windows directly above it, so nothing can be ordered between the two. An overlay ordered directly above the target lands above the target's child windows, so the windows of the target's app listed between the overlay and the target are recorded as its child windows. Until then, windows of the target's app at the target's layer that lie within the target, such as sheets, count as child windows. While a window covers the target, the overlay takes the target's level and is ordered directly above the target with `orderWindow:NSWindowAbove relativeTo:`, so the covering window covers the effect as it covers the target. The overlay is ordered only when its stacking differs from the one the windows above the target ask for, and an order that has not applied yet shows in the next check, which orders it again.

A display link on the overlay's screen (`displayLinkWithTarget:selector:`; before macOS 14, a timer at the screen's refresh rate from 30 to 120 times a second) runs on every display frame while an in-place overlay shows. It reads the target's bounds and, when the target has moved and kept its size, moves the overlay to them with `setFrame:display:`, without ordering it; a size change waits for the next geometry event, which also reconfigures the capture. It then runs the stacking check, which also runs on each app activation: the check reads the window numbers above the target with `CGWindowListCreate`, and reads those windows' descriptions when the list changes and at least every 50 ms, so a window that moves over the target is seen as well. Menus, the menu bar, the Dock and modal alerts stay above the overlay.

The chain process polls each output ten times a second from its latest geometry. Showing and hiding follow the entry alone: effects running, not suspended, the target on screen and the overlay's number acknowledged. When the overlay is shown but has not been on the active Space for three polls, it hides and the state reason reads "The output cannot be shown on this full-screen Space". Each poll passes the display that holds the largest part of the target to the presenter (`FramePresenter::setDisplay`), so presentation follows that display, and `setOutputVisible` stops presentation while the overlay is hidden. The overlay joins all Spaces as a full-screen auxiliary window, so it can appear over full-screen apps; because it hides whenever the target is not on screen, it shows only in the Space where the target is visible. As a transient window, it is hidden while Mission Control is open, and it stays out of the window cycle. Its content view hosts a container layer that holds the presenter's Metal layer. The presenter's layer stays hidden until the first accepted frame. Once shown, it keeps its last processed image through a change of size, crop or generation until a frame of the new geometry replaces it, as a game's presentation does while its window resizes; after a resize, that image is fitted to the overlay's new bounds. The overlay hides while the target is off screen or minimized, and while the chain process is suspended for sleep, screen sleep or a user switch. Capture continues while the target is covered, off screen or minimized, so the output is current when the target returns. The flag `RS_WINDOW_SOURCE_SCALED` selects the placement for a window; a display is always in place:

- In place, the overlay covers the target in points, and the drawable uses the source's pixel extent at the target's display scale.
- Scaled output with scale 0, **Fit screen**, covers the target's screen: the visible frame, or the whole screen when the target's bounds equal it. A scale factor F covers the target enlarged by F about its center, with F reduced to fit the visible frame and the area moved inside it and aligned to whole points. The presenter's layer is the largest centered rectangle with the target's aspect ratio, on whole points, and the bars show black once a frame is shown. The drawable is that rectangle at the screen's backing scale, so the presenter enlarges the source with the plan's spatial method.

### Scaled pointer

While a scaled overlay shows and the target's process is the frontmost app, an event tap at the session level keeps the pointer within the target's window-server bounds, moving it back to half a point inside an edge with `CGWarpMouseCursorPosition`, and `CGDisplayHideCursor` hides the system pointer; the chain process sets the connection property `SetsCursorInBackground`, so the hidden pointer applies while the chain process runs in the background. Clicks, drags and scrolls therefore reach the target window itself. The overlay draws the arrow pointer at the point of the image that matches the pointer's position in the target. It shows while **Show pointer in picture** is on and the pointer is not held: movement events with deltas but an unchanged position, as an app that holds the pointer produces, hide it until the position changes. When the overlay hides or another app becomes active, the tap stops confining the pointer and every hide is balanced with `CGDisplayShowCursor`. The tap needs the Accessibility permission: the launcher asks for it when a scaled output is chosen and keeps In place while it is missing, and the chain process checks it with `CGPreflightPostEventAccess` before it sets the flag, reporting `{"event":"output","output":"in-place"}` with the reason when it is missing.

### Capture lifecycle

Capture runs only while processing is requested. Turning processing off sends `paused` in the feed's options, and the service stops that stream and keeps its filter, so turning processing back on needs no new pick. A stream that ScreenCaptureKit ends with an interrupted or invalid application connection (`SCStreamErrorFailedApplicationConnectionInterrupted`, `SCStreamErrorFailedApplicationConnectionInvalid`) or an internal capture error starts again at once, at most once in 10 seconds. Any other stream error closes the feed if the capture has not recovered after 5 seconds, a second interruption within 10 seconds closes it at once, and a missing Screen & System Audio Recording permission closes it at once. **Include pointer in capture** sets the stream's `showsCursor` through `updateConfiguration:` on the same stream. A change of **Output** closes and reopens each feed of the entry, which delivers a first image for static content. The plan's [frame-rate cap](FRAME_API.md#source-frame-rate-cap) (`output.frameRateCap`) limits capture through the interval the chain process sends in the feed's options; the service and the chain each drop a frame that arrives sooner than 0.75 of the cap's interval after the previous accepted frame. The service stops every stream while the Mac sleeps, its displays sleep, the screen is locked or the user session is inactive, keeps the filters and starts the streams again afterwards.

The chain process takes its target from its arguments: `--window N`, `--display N`, `--all-displays`, or `--pid N` with optional `--wait-window SECONDS` and `--front-window`; `--scaled` with optional `--scale F`, `--cursor`, `--capture-rate FPS` and `--library PATH` set its options. Target IDs are `w` plus the window ID, `d` plus the display ID and `p` plus the process ID. All Displays opens one display feed per active display, adds a display connected during the session when the screen configuration changes and releases a disconnected display's feed. Option lines such as `{"cursor":false,"scaled":true,"scale":2,"pointer":true}` arrive on standard input and apply to every output; `{"pointer":"toggle"}` turns the drawn pointer off or on, `{"remove":"ID"}` takes one output out, and the launcher sends these lines from the game's worker, where the entry's process runs.

The chain process reports events as JSON lines on standard output, which the launcher writes to its main log, plus a heartbeat each second. Events that concern one output carry `"target"`: `targetAdded` when it joins, with its kind and IDs; `targetRemoved` when it leaves, with the reason, as when its window closes, its app quits, its display is disconnected or it is removed; `state`, with the state name, `revealed` and any reason; and `selected`, `output`, `picking`, `capture`, `waiting-for-window` and `failed`. The entry itself ends, with `stopped`, `closed` or `failed` and no target, when its last output leaves, on the stop line, at the end of standard input or on a signal. A session that produces neither a heartbeat nor other output for more than five seconds is ended. The line `{"stop":true}`, the end of standard input, SIGTERM, SIGINT and SIGHUP stop the entry: the chain process closes its overlays and feeds, ends its connection to the service and waits up to 1.5 seconds for `rsWindowSourcePendingStops` to reach zero before it exits. **Stop** sends the stop line, then SIGTERM to the chain process if it is still running two seconds later, and SIGKILL two seconds after that. The captured app is never signalled.

### Capture service

The service is a singleton per MacLauncher process. Its ID is `org.maclauncher.window-capture.` followed by MacLauncher's process ID, which a chain process derives from its parent. A client reads the rendezvous file `ID.lock` in the per-user temporary directory (`_CS_DARWIN_USER_TEMP_DIR`), which holds the service's unique bootstrap name and process ID, and connects with a hello that the service answers when the client is the same executable and a child of the same MacLauncher process. When no live service answers, the client starts one with `posix_spawn` in a new session (`POSIX_SPAWN_SETSID`), with standard input and output on `/dev/null` and an environment reduced to the home, temporary-directory, locale and time-zone variables and a fixed `PATH`, so stopping a chain process's process group never reaches the service. A starting service takes an exclusive `flock` on the rendezvous file; when another live service holds it, the new one exits, and when a stopping service still holds it, the new one waits for the lock for up to 5 seconds. It then registers a name of the ID and a UUID with `bootstrap_register` and writes the name and its process ID to the file.

The service sends each client a heartbeat every second. A chain process that receives no heartbeat from the service for 5 seconds sends SIGKILL to the service process, after checking its executable and start time, and treats the service as lost, as it does when the service exits. On a loss, it hides its overlays (`RS_WINDOW_SOURCE_HOLD`), connects to a running service or starts one, sends its overlays again and opens each feed again; a second loss within 10 seconds ends the entry with "Window capture stopped unexpectedly". When a client exits, the service learns it from the client port's dead-name notification and closes that client's feeds. It exits 2 seconds after its last client leaves, and when MacLauncher's process is gone or has been replaced, which it checks every second with `kill` and the process start time from `proc_pidinfo`. It also stops on SIGTERM, SIGINT and SIGHUP. Stopping withdraws the bootstrap name first, then stops the catalog, closes every feed and waits up to 1.5 seconds for every stream's `stopCaptureWithCompletionHandler:` completion and for its outstanding content requests, keeping each stream and its output retained until then, before it releases the lock and exits. A replacement service waits on the lock during that time, so two services never hold streams at once.

### Apply Graphics list

The Apply Graphics window's list comes from `maclauncher-graphics-window --catalog --exclude-pid PID`, a relay client of the service. It asks the service for the catalog with thumbnails, writes the service's catalog events to standard output unchanged as JSON lines and keeps the service running while it is open. When the window closes, the launcher closes the relay's standard input and the relay exits; a relay still running two seconds later gets SIGTERM, and SIGKILL two seconds after that. A relay starts only after the previous one has exited. A session chosen while the window is open starts after the relay has exited, and the window then starts the relay again. A lost connection writes `{"event":"failed","reason":"The window list stopped"}` and the relay connects again; a second loss ends it.

The service reads `SCShareableContent` every two seconds, including windows that are not on screen, and writes the displays and the ordinary windows of regular apps when they change. A catalog event lists at most 96 windows in `windows`, in front-to-back order, keeping each app's front window before the others, and the remaining windows in `more`. The launcher lists `windows` and turns up to 2,048 rows of `more` into search-only targets after their app's listed windows, which the window shows only while its search matches them, with the app's icon in place of a thumbnail. A read that fails for a reason other than the permission writes `{"event":"failed","reason":…}` and the catalog keeps running; the window shows the reason in place of the list until the next list arrives. A window showing that reason, or the notice for a relay that ended with an error, starts the list again when it becomes active. Before the first list that names an app, the catalog writes the app's icon from `NSWorkspace`, drawn at 32 points and 2x as a PNG data URL. Thumbnails come from `SCScreenshotManager`, at most four at a time, scaled to fit 400 by 250 pixels and sent as JPEG data only when the image changed; a result later than two seconds is discarded. A newly listed window or display gets its thumbnail at once. After that, one repeat capture starts at most every half second, for the on-screen window or display whose last capture is oldest and at least five seconds old, so a window that is off screen or minimized keeps its first thumbnail. The launcher passes thumbnails to the window in memory. MacLauncher asks for the Screen & System Audio Recording permission itself, once, while macOS reports it as undetermined, by requesting screen sources; the helper processes only check it with `CGPreflightScreenCaptureAccess`. Without the permission, the catalog reports it and the relay exits, and a permission that macOS reports as denied starts no relay.

### Output under resource pressure

During temporary resource pressure, in-place Metal and OpenGL effects reuse only an image whose GPU work has completed and which matches the current settings and output contract. Sustained pressure switches to the original rendering until that contract changes, so processed and untreated frames never alternate. OpenGL reuses its fixed set of interop slots without waiting for command scheduling. None of this adds a window wrapper or a cap on the source frame rate.
