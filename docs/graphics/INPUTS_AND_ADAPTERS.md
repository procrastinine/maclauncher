# Frame sources and runtime adapters

[Pipeline overview](PIPELINE.md) · [Graphics guide](README.md)

This page describes how a game's frames reach MacLauncher's graphics processor and what extra scene data can come with them. Every runtime connects through a *frame adapter*, the code that takes each completed image from the game's renderer and hands it to the processor, together with any matching scene data the renderer supplies. What a game can use therefore depends on its *producer*, the code that actually renders its frames. The game type and the CPU architecture do not decide it, and runtime and CPU names never select separate effect implementations.

The sections below cover each frame source and scene producer, what a module provides to launch a game with graphics, renderer input declarations, attachment hosts, completed-window capture and the capture of picked windows and displays. [Renderer integrations](SHARED_PROCESSING.md) lists which runtimes supply scene data and render-size control.

## Frame sources and scene inputs

Each runtime declares a `graphicsHost`, which selects how the processor attaches to it (see [attachment hosts](#attachment-hosts-and-cpu-architecture)). This declaration does not identify the frame source that the game actually uses while rendering, because one runtime can present its frames in several ways. A Java game, for example, can present an OpenGL framebuffer, a Metal drawable or a software bitmap, and Wine can present Metal through a Direct3D translator or OpenGL through WineD3D. In each of these cases the game goes through the same adapters as a native application.

For each launch, the Wine runtimes (CrossOver, Sikarugir and WineCX) work out one shared translator plan, which records the translators the launch will use, before graphics preparation starts. The launch's graphics binding then refers only to the component records that this plan actually uses after fallback, and when the plan leaves a choice to the vendor's automatic selection, that choice stays unresolved. Metal and OpenGL output from the translators keeps its existing presentation adapters, and depth, motion and camera inputs come from whatever is actually supplying the frames. A translator's name therefore neither creates scene data nor selects a separate effect implementation. The plan also stays fixed for the whole launch: running edits and screenshots keep it, and a translator choice saved later applies only to a later launch.

However a game draws, the shared image pipeline receives completed color images. A *frame source* is where these images come from: direct access to the render target, an operating-system window stream, a texture the runtime supplies, or an upload of a software image. Each source attaches in its own way and can add different scene data:

| Frame source | Attachment and GPU handoff | Scene data supplied with the image |
| --- | --- | --- |
| Native Metal drawable | `metal.mm` intercepts the selected drawable and its command buffer. Eligible size-preserving FX can run in place. Other chains use owned presentation, in which the processor presents the output itself. The same adapter handles Metal output from Java and from Wine translators. | Matching depth from a supported render pass, when requested. A Metal drawable alone supplies no motion vectors, jitter or camera projection. |
| Hardware OpenGL framebuffer | `opengl.mm` and `opengl-interop.mm` receive the game's flush, copy its framebuffer into CoreVideo/IOSurface GPU images and submit Metal processing. This includes compatible Java OpenGL and WineD3D output. | Matching default-framebuffer depth, when present and requested. No game motion vectors, jitter or camera projection are inferred. |
| Core Animation surface | `window.mm` and `layer-presentation.mm` receive published IOSurfaces or supported layer images. The adapter accepts only a full image of the selected window, because a compositor tile is not a complete frame. | Composed color only. |
| Completed software bitmap | A supported `CGImage` layer publication, or a complete bitmap drawn during the selected view's `drawRect:`, is uploaded to a reusable IOSurface. Later effects run on the GPU. | Color and image geometry only. The software renderer's original pixels are already in CPU memory. |
| Browser window stream | Dedicated Electron and NW.js hosts can use `browser-frame.mm` when native compositor surfaces do not provide the complete window. ScreenCaptureKit supplies the selected window's composed image, and CoreVideo and GPU copies hand it to the shared processor. | Composed color only, with no renderer depth or motion vectors. |
| Picked window or display | `window-source.mm`, driven by the `maclauncher-graphics-window` helper, captures a window or display chosen in the Apply Graphics window or the macOS content picker and presents the processed image in an overlay window over it. | Composed color only, at the window's pixel size, with no source-resolution control, depth or motion vectors. |
| Explicit runtime textures | A runtime calls `rsProcessFrame`, its depth variant or the presenter API with its own Metal textures and synchronization. Android presentation integrations attach this way. | Color, plus only the matching inputs that the runtime explicitly supplies. A graphics host declaration alone adds no scene data. |
| Native mpv processing | mpv applies compatible shader prefixes and scaling to its decoded video, with the original video planes and decoder color metadata. Shared effects after that prefix receive the RGB image mpv produced, through the player's actual Metal or OpenGL frame adapter. | Only the mpv prefix sees the original video planes. Later shared effects get composed RGB, with no game depth or motion vectors. |
| Decoded GPU video host | The [mpv host](https://github.com/procrastinine/maclauncher-builds/blob/main/producers/mpv-render/v7/native/mpv-render.mm) in MacLauncher Builds keeps decoded GPU surfaces and submits them to the shared graph before window fitting. Paused redraws keep the same content ID. | Decoder color and format metadata, content ID, source PTS and media duration; no game scene data. |
| Offline video frames | `video-frame.mm` and `graphics-video.mm` import decoded sample buffers as GPU textures for the shared frame API and pass the completed output to the encoder. | Decoded color and media timestamps; no game scene inputs. |

### Presented extent

In owned presentation, the processor keeps the source layer's mapping of image to bounds. When a Metal drawable's or Core Animation surface's layer stretches the whole image over its bounds (resize gravity, the full contents rectangle and centered), the output is presented at the view's backing size. Any other mapping, such as Java's top-left drawable that is taller than its view, is instead presented at the game's own image size, with the same gravity, contents rectangles, contents scale and orientation. As a result, processing never rescales the image or shows pixels that the original layer clips. When the drawable's resolution is reduced, the presented size stays at the size the game requested.

### Metal drawables

The native Metal adapter installs its command-buffer and presentation hooks on the game's own Metal device, either when the game assigns a device to a `CAMetalLayer` while processing is wanted or, failing that, at the layer's first drawable request. Because the adapter never creates a default device or requests a drawable before the game does, Wine can reserve its Windows address space first. Presentation is intercepted on every loaded `CAMetalDrawable` class. A drawable class whose present call forwards to its superclass's present is still processed only once.

Processing sometimes needs to read the presented image in a drawable format that a framebuffer-only attachment cannot read. While that is the case, the adapter turns off the layer's `framebufferOnly`, and once the access is no longer needed, it restores the setting, but only if the adapter was the one that changed it. A value that the game sets later is kept.

### Window capture

Two frame sources take their images from ScreenCaptureKit. The browser window stream is turned on through the authenticated per-launch channel that `shared/web/runtime/browser-graphics.js` creates for dedicated browser hosts. A `graphicsHost: "window"` declaration, however, does not open that channel for arbitrary Java, Wine or native applications. A [picked window or display](#picked-windows-and-displays) is likewise captured only after a choice in the Apply Graphics window, the macOS content picker or the window graphics shortcut. While a stream is active, ScreenCaptureKit shows the macOS sharing indicator. Direct Metal and OpenGL interception uses no such stream, and the GPU texture copies made by either kind of source involve no CPU pixel readback and no recording files. [Completed-window capture](#completed-window-capture) describes the stream itself.

### Color and alpha

Color shaders, processing of derived luma and chroma, resize rows and compatible image-based neural effects all work on color images, using the color encoding and alpha convention that each image carries with it. Frame generation from color pairs reads the same description, although it also needs consecutive images and a presentation timeline that the processor controls. Since every source describes its images the same way, one implementation of these effects serves all of them.

Whether an image is opaque is part of what its source declares. An opaque display image keeps all its RGB pixels even when its stored alpha is unused or zero, while a transparent image keeps its declared straight or premultiplied alpha through compatible filters, including libplacebo processing. The selected model or provider can still set its own color, format and platform requirements. Original subsampled decoder planes also stay distinct from luma and chroma derived from a composed RGB image.

### Scene producers

Scene effects such as temporal upscaling need renderer data that a completed image does not carry: depth, motion vectors, jitter and the other inputs that match one rendered frame. Because a frame adapter cannot supply this data, it reaches the processor separately. A *scene producer* is the code that collects it from the game, in most cases from an upscaler call the game already makes, and hands it over as one scene frame. Each scene producer supplies a different set of inputs:

| Scene producer | Supplied data | How the scene frame reaches the processor |
| --- | --- | --- |
| Original MetalFX temporal call | Color, depth, motion, output, jitter, motion-vector scale, reset, pre-exposure, any exposure texture and, on macOS 14.4 and later, any reactive mask from the intercepted scaler call, with elapsed frame duration. A MetalFX scaler has no transparency-and-composition input. Camera data and HUD-less/UI images need separate registrations. | A record from the same command buffer ties the original scene to its exact output. To replace the scaler in an ordered chain, the processor needs a complete SDK output texture on retaining command buffers that have not been submitted yet, identified by the exact scene producer and frame. That SDK output can be an intermediate scene image. |
| Godot renderer integration | The helper registers the actual projection and renderer resources, and the matching original MetalFX call supplies its command buffer and jitter. | The Godot bridge hands that matched scene to the shared processor. Registering metadata alone does not turn another renderer into a scene producer, and an ordinary window attachment keeps the inputs of its frame adapter. |
| DLSS through the DXMT bridge | Color, depth, motion, output, jitter, motion-vector scale, reset, exposure and any DLSS bias-current-color mask from the game's NGX evaluation, with elapsed frame duration. A game that calls DLSS through Streamline keeps its own interposer, so no Streamline camera or HUD-less/UI images arrive this way. | The NGX implementation in the adapted DXMT library translates the game's scene request and keeps its resources for each context. The native reconstruction method that runs is reported separately from the API the game called. |
| XeSS D3D11 through the DXMT bridge | The game's color, depth, motion, output, jitter, motion-vector scale, reset, exposure and responsive pixel mask, with elapsed frame duration. The responsive mask, clamped to the context's maximum responsive value, becomes the reactive mask. XeSS itself supplies no camera projection, transparency-and-composition mask or separate HUD-less/UI images. | Compatible requests are passed to the MetalFX scene producer and from there into the shared, ordered scene processing. The native method that runs does not depend on the API the game called, and a method that needs projection data needs a scene producer that supplies it. |
| NGX through vkd3d-proton, for Direct3D 12 | Color, depth, motion and output, their regions, jitter, motion-vector scale, reset and depth flags, pre-exposure, optional exposure texture, optional bias-current-color mask and frame duration. Camera parameters come only from the game's Streamline constants, which the NGX core captures in the game's own Streamline interposer. | An NGX Super Resolution evaluation records `VkTemporalFrameInfoMVK` in the game's command list, and a compatible Vulkan driver forwards it to `rsProcessTemporalFrame`. |
| NGX through DXVK, for Direct3D 11 | The same Super Resolution inputs as through vkd3d-proton, including camera parameters only when Streamline supplies them. | `IDXGIVkInteropDevice` and `IDXGIVkInteropSurface` expose the Vulkan queue and images. After flushing the immediate context, NGX submits the recorded `VkTemporalFrameInfoMVK` on that queue. |
| FidelityFX API, for Vulkan and Direct3D 12 | Color, depth, motion and output, jitter, motion-vector scale, reset, depth and motion conventions, HDR, exposure texture or automatic exposure, pre-exposure, sharpening, reactive and transparency-and-composition masks, camera near and far planes and vertical field of view, and frame duration from the game's FidelityFX upscale dispatch. FidelityFX supplies no camera matrices or HUD-less/UI images to the upscaler. | The FidelityFX API adapter records the dispatch as one `VkTemporalFrameInfoMVK`, with both masks in a chained `VkTemporalFrameMasksInfoMVK`: for Vulkan in the game's command buffer, for Direct3D 12 through vkd3d-proton's MetalFX command-list interface. The selected upscaler writes the dispatch's output, and the original dispatch runs only when the frame cannot be recorded or while the game's Graphics are off. [FidelityFX API adapter](../runtimes/CROSSOVER.md#fidelityfx-api-adapter) lists the conditions. |
| Explicit temporal frame API | The caller's matching textures, camera and scale data, flags, frame ID and command buffer. | `rsProcessTemporalFrame` validates the selected provider's actual inputs. |

When optional shared processing cannot get the resources it needs, the DLSS and XeSS paths through DXMT keep the original SDK call and its output.

Translating a game's XeSS calls is a renderer compatibility feature, and it reports which Mac reconstruction algorithm actually runs. For D3D11, compatible translation is selected independently of optional shared postprocessing. When postprocessing is off, the translation keeps the original game DLL and the game's base upscaling. Translating D3D12 and Vulkan XeSS needs a translator that exposes matching textures and command insertion, so games that use those APIs keep their original libraries.

A reactive mask is one channel from 0 to 1, where 1 relies on the current frame instead of history. A DLSS bias-current-color mask and an XeSS responsive mask carry that meaning and are passed as the reactive mask. A transparency-and-composition mask follows FidelityFX's definition. Only the FidelityFX API adapter supplies one, from the game's FidelityFX dispatch, because NGX defines no transparency input with that meaning. FSR, FSR 4 and ASR use it; a MetalFX scaler has no such input. Both masks are read at the color image's region. Through vkd3d-proton and DXVK, a DLSS mask at another offset, or one that does not cover the render extent, is left out of the frame, and the rest of the frame is still processed. Through DXMT, the DLSS mask is passed only when it starts at the origin, covers the input and the device supports MetalFX reactive masks.

A scene producer supplies data, but it does not decide which effects can run. Depth-only filters, scene reconstruction and scene generation each declare the inputs they require. For each operation, camera matrices, exposure, reactive masks and HUD-free color are separate resources, either optional or required, and temporal inputs are kept apart from other renderer inputs such as normals, albedo and lighting buffers.

Godot's scene producer, for example, attaches to viewports in the native window, while offscreen viewports keep their own compositor and scaling. The shared completed-image path stays available, and a matching scene frame from another scene producer can use the same compatible reconstruction or generation provider. [Godot](SHARED_PROCESSING.md#godot) describes the user-facing behavior.

### DLSS through Vulkan translators

Games that use DLSS pass their scene inputs to NVIDIA's NGX interface. MacLauncher supplies its own adaptation of NGX, which forwards each Super Resolution evaluation through vkd3d-proton for Direct3D 12 or through DXVK's Vulkan interop for Direct3D 11. The game loads this adaptation as its NGX core. To make that happen, Wine launch preparation places it in the prefix's `system32` as `nvngx.dll`, sets both the global `NGXCore\FullPath` and the `nvlddmkm` service's `NGXCore\NGXPath` registry values to that folder, and adds the NGX registration markers that NVIDIA's NGX library reads. When a package declares an NGX signing certificate, Play installs its public certificate in that Wine prefix's Root store and verifies the actual core's Authenticode signature, without a dialog or network lookup. No macOS trust settings are changed.

With either translator, the core records each evaluation as a `VkTemporalFrameInfoMVK` structure in the `pNext` chain of `vkCmdPipelineBarrier2`. This structure, the *temporal frame record* on these pages, describes one evaluation and its resources and contains no upscaling implementation of its own. Two Vulkan drivers read it: MacLauncher's KosmicKrisp and a MoltenVK build that supports the record. Each one translates the record into a call to the shared temporal frame API. The selected provider then runs in command order on a retained classic Metal command buffer, and its complete output is copied from a tracked texture into the game's output region. The driver keeps a separate history for each NGX feature and releases it after that feature's last frame. Neither driver creates or encodes a MetalFX scaler itself; when no temporal method is selected, MetalFX is chosen in the shared processor.

Every record needs color, depth, motion and output. An exposure texture is optional, and the record also holds pre-exposure, jitter, motion-vector scale, reset, the depth and motion conventions, the frame ID and the frame duration. When the game gives no duration, the driver supplies the elapsed time. The game's optional DLSS bias-current-color mask travels in a `VkTemporalFrameMasksInfoMVK` structure in the record's `pNext` chain and becomes the frame's reactive mask. The [record layout](https://github.com/procrastinine/maclauncher-builds/blob/main/producers/vkd3d-proton/TEMPORAL_FRAMES.md) also defines HUD-less color, UI and Ray Reconstruction attachments. These two drivers, however, forward only Super Resolution inputs, so they pass no separate HUD-less/UI images, denoising attachments or scene matrices to the processor.

A DLSS call alone carries no camera, so camera near and far planes and the vertical field of view are available only when the game also supplies Streamline constants. They are read from the game's Streamline interposer (`sl.interposer.dll`) when it sits beside the executable or in a supported plugin folder and exports Streamline's application API (`slInit`, `slGetNewFrameToken`, `slSetConstants` and `slEvaluateFeature`). With such an interposer, the launch declares camera projection whenever DLSS frames are forwarded this way, without a setting, so FSR 2 and FSR 3 are available in **Temporal upscaling**. The interposer remains the game's own file. A game that verifies its NVIDIA signature therefore keeps Streamline, and the game still starts from its own folder.

To capture the camera, the NGX core installs in-memory detours on the interposer's `slSetConstants` and `slEvaluateFeature` exports when it initializes. For each `slSetConstants` call, the detour copies the validated perspective camera, keyed by frame token and viewport. When `slEvaluateFeature` runs DLSS, its detour selects the copy for that frame token and viewport as the camera for the evaluations made on its thread and restores the previous camera afterwards, so nested evaluations keep their caller's camera. Both calls still return the original result. Each capture copies one 64-byte camera under a short reader-writer lock and adds no GPU wait, and the core then adds the camera to that evaluation's temporal frame record. Orthographic, oblique and shifted projections supply no camera, and neither do constants whose near and far distances and field of view disagree with the projection matrix.

NVIDIA DLSS Frame Generation and Ray Reconstruction are not exposed this way. Forwarded Super Resolution frames enter the same ordered graph as frames from other scene producers, and a shared frame-generation row in that graph still needs its own matching inputs and presentation timing. A game calling DLSS does not by itself meet those requirements.

#### Wine scene transport

A Direct3D 12 game's scene requests start on the Windows side of Wine and have to reach the native Vulkan driver. The *scene connection* that carries them is set up for each launch. For every Wine runtime, launch preparation reads the Direct3D 12 translator that the launch actually uses and the selected Wine layout, and it enables the connection only when the translator has the typed resource and command exports and the selected Wine module has the scene transport exports. A handshake with the native driver context then makes the final decision to accept it. When an export is missing, the game keeps its ordinary rendering path. Executable names, driver labels and downloadable version numbers are never taken as proof that the connection is supported.

Scene requests travel through an additional export, `MacLauncherWineVulkanRecordScene2`, which carries fixed-width metadata next to the original scene request, while the original export and the context calls keep their layouts. Before the PE side uses the additional Unix selector, it checks that the matching Unix module provides it. Wine devices and command buffers are unwrapped only on the Unix side, which owns them, and the native driver resolves images on that device. The metadata contains no native resource pointers or callbacks.

Reconstruction work can also be prepared ahead of time. The optional preparation calls each negotiate their own Unix selector before a reconstruction request is sent. Preparing a request returns an opaque native operation ID for it and records no commands, and the prepared request is accepted only by the native side that prepared it, with exactly the resource and frame metadata it was prepared for. A separate optional query carries the declared creation dimensions and flags, without commands, images or a frame ID, so the selected provider can check that shape while the matched native driver keeps its actual Metal device. Whether the shape is supported, whether the resources are accepted and whether output was encoded are reported as separate results.

On the native side, the driver still encodes the work through `RSVulkanSceneEncodingV2`, with its actual queue and the retain and release callbacks for each frame in flight. The shared graph chooses and prepares the provider, and the scene connection itself selects no algorithm and creates no command queue or presentation scheduler.

### XeSS compute hosts

Which scene producer supplies a frame and which algorithm processes it are separate choices. Intel XeSS, for example, is one of the temporal upscaling implementations in the shared graph, and neither the game's CPU architecture nor its original upscaling API decides whether it can run. [XeSS](PROVIDERS.md#xess) lists its inputs and the hosts it can run in.

XeSS's D3D12 implementation runs the unmodified Intel runtime in an isolated, compatible compute host, a separate process that supplies the Windows ABI and graphics translation this Windows library needs. Metal GPU commands hand the scene to the host through shared images and aliased D3D12 buffers, while the launcher passes only setup metadata. The backend is selected in the row's XeSS Options, and the launcher coordinates the hosts as follows:

- The launcher watches for compute-host setup requests only while a prepared plan has an enabled XeSS row or one of its hosts is still running.
- When a live update is rolled back, the watch state of the plan that keeps running is restored. A plan with an XeSS row keeps the watch, and a plan without one stops it at once when no host is running.
- Launch preparation and live edits each register their XeSS hosts and bind them to the running process. The host table written for the launch keeps an entry for every host and names each host's latest registration, so each setup request is claimed exactly once, by the registration that its host entry names.

### Depth

Depth on its own is enough for compatible depth shaders, although temporal upscaling needs more. Window framebuffer depth, drawable depth and explicit depth images carry no camera projection, so they are copied only for rows that read depth alone. Image filters that unproject depth need a projection from the renderer, and without one they are bypassed with the reason that the frame source supplies no camera projection.

Automatic Metal depth comes from the render pass that stores the exact presented color image. While that image needs depth, a copied render-pass descriptor changes a depth store action of DontCare to Store. Memoryless attachments are excluded. The supported formats are Depth16Unorm, Depth32Float, Depth32Float_Stencil8 and Depth24Unorm_Stencil8. Attachments without shader-read access are blit-copied into readable storage, and multisample depth uses sample 0. Depth is never taken from an unrelated pass.

Depth images have the same orientation as their color image and keep the renderer's depth range and encoding. ReShade `.fx` rows interpret reversed, logarithmic or rescaled depth through the game's [depth-input definitions](EFFECT_PLANS.md#depth-input).

Scene frame generation has its own depth, motion, camera and history requirements, and motion estimated from the images is kept apart from them. When an image-pair generator or a neural model estimates flow or motion, including the motion field of MetalFX image interpolation, the result is never passed on as game motion vectors. Likewise, generated color frames do not gain matching renderer guides just by keeping the source frame's identifier.

### Source size

Changing the size at which the game renders is separate from processing. Downsampling after rendering changes only the submitted image. Engine controls or the virtual-source protocol, on the other hand, can change the size the game allocates for rendering, although only after the game acknowledges the requested size. Neither window-stream dimensions nor the final output fit show that the game renders to a smaller target. [Game render allocation](FRAME_API.md#game-render-allocation-and-processing-extent) describes the source strategies.

## Module launch entry points

A module tells the launcher how to start its games with graphics. Each runtime entry declares its `graphicsHost` in module metadata, and at launch the launcher prepares the shared processor through `context.getGameEffectsEnvironment()`. `context.applyGameEnvironment(base)` then combines that environment with the game's existing environment. Choosing an engine-specific renderer remains the module's job.

Every game launch goes through one game context, which handles lazy preparation, runtime graphics metadata, merging the selected libraries and the final process handoff. The library UI and `scripts/run-game.mjs` both launch through `createLauncher().launchEntry`, and direct module hosts get the same game context from `getGameLaunchContext(entry, settings, options)`. Action contexts, by contrast, use `getLaunchContext` and leave game effects off. Before it calls `spawnDetachedChecked`, a module may replace the context's graphics getter with the scoped environment its sandbox produces. Callers never prepare or merge a second graphics environment.

### Code-signature check

Some code signatures stop the shared processor library from loading, so the final native handoff checks the executable's code-signature policy before it attaches the processor. Any one of three signing properties marks the executable as restricted: the hardened runtime without the `com.apple.security.cs.allow-dyld-environment-variables` entitlement, the restrict flag, or library validation that does not accept the processor library. What happens next depends on the game's plan. When the plan needs processing, a restricted executable runs from a [private copy](#private-copies-of-restricted-apps) of its app instead. When the plan needs no processing, or the copy cannot be used, the game runs without the processor attached, and its launch binding records the reason. An executable whose signing properties are unknown stays eligible.

For this check, the code that starts the process can supply `graphicsExecutable` with the actual executable, or `null` when the descendant process is unknown. This metadata is read before the process is created, and Rosetta wrapping happens after the check.

### Private copies of restricted apps

A private copy lets the shared processor attach to an app whose own signature would block it, and the original app is left unchanged. The copy covers the outermost app bundle that contains the restricted executable, or the executable alone when it is not inside a bundle. It is kept in the game's data folder at `games/<gameId>/effects/app-copy/`.

- Each Mach-O program in the bundle whose signature blocks the processor is copied and signed ad hoc, without the hardened runtime, restrict and library-validation flags. If such a program is the main executable of a bundle, that bundle's `Info.plist` is copied as well, and the bundle is signed as a whole. Nested code is signed before the bundles that contain it.
- A re-signed program keeps its entitlements, except for the restricted ones that only a provisioning profile can grant: `com.apple.developer.*`, `com.apple.application-identifier`, `keychain-access-groups` and `com.apple.private.*`. These are left out because an ad hoc signature carrying them would stop the program from launching, and the launcher log names the entitlements that a copy leaves out.
- The re-signed programs and copied `Info.plist` files are APFS clones of the originals when both are on one APFS volume, and ordinary copies otherwise. Every other file and folder in the copy is a symbolic link to the original. As a result, libraries, resources and game data are read and written in place, and only the re-signed programs take new disk space. Some programs find their data relative to their bundle, so links beside the signed copy also point to the items beside the original app. While the size, modification time and inode recorded for the folder that holds the original app still match, that folder is not listed again and the links are not updated.
- The copy keeps the original bundle identifier, so preferences and save locations stay the same.
- The process handoff changes only its command, which names the copied executable, and the code-signature check runs again on that executable. Arguments, the working directory and environment values keep the original paths that the game module supplied. Steam identification and launch arguments are also prepared from the original app, before the handoff.

A copy has to stay in step with its original app, so it is checked before each launch with processing. The check compares the listing of each copied folder, and the size, modification time and inode of each copied file, with both the original and the copy. A copy that still matches is reused. After an app update, or a change to the copied code, the copy is rebuilt before the game starts instead, so a re-signed program never runs with the resources of a newer version.

The game can also write into the copy. A program that derives a write path from its own executable or bundle can still create files in the copy's real directories, because keeping the original working directory does not redirect those paths. Files and folders that the game created there, and links that it replaced, are therefore carried into the refreshed copy. Preparation leaves the earlier copy intact until the replacement and its record are committed, and an interrupted replacement restores the earlier copy.

Changes to the copied code itself are set aside. When a refresh finds that a copied executable or `Info.plist` has changed, it keeps the changed file under its relative path in `effects/app-copy/recovered/<snapshot-id>/files/`, together with a record of the file's size, modification time and inode, while the refreshed copy still runs code from the current original app. These snapshots are never launched, and the launcher never rewrites them or removes them automatically.

When a launch's plan needs no processing, or its app no longer blocks the processor, the launch runs the original app. Even then, the copy is removed only when every remaining entry belongs to the launcher and matches its record; a copy that contains game-created entries, replaced links or modified files remains in the game's data folder. Each removal goes through the launcher's [guarded trash](../development/DATA_MODEL.md#derived-data-upkeep). Removing the game from the library also removes the copy, along with the rest of the game's data.

Apps that use the App Sandbox are never copied. Because macOS ties a sandboxed app's data container to its code signature, a re-signed copy would either need permission to open the original container or would not start. Such an app therefore runs from the original with its original rendering, nothing is written to its copy folder, and its launch binding records that reason.

### Process adapters

A module can wrap the final handoff for instrumentation that the child process inherits, by supplying an optional `processAdapter(command, args, options, needsRosetta, spawn)`. The `spawn` continuation that this process adapter receives keeps the selected graphics environment, network policy and process ownership. Component callers can also supply `graphicsRuntimeRoot` for verified preparation assets and `presentationLibrary` for the processor library to call, whereas ordinary launches use the included selection.

### Diagnostics

Diagnostics are configured through four boolean `graphicsDiagnostics` fields (`diagnostics`, `capture`, `gpuTiming`, `trace`). They go through the same preparation path and leave the saved plan unchanged. Detailed diagnostics, GPU timing and frame capture are all opt-in:

- Disabled diagnostic entry points read cached enable flags and create no recorder state, writer thread, output file or GPU query.
- Enabled recorders use fixed-size queues, and render callbacks drop records instead of waiting for a writer lock.
- Diagnostic file writes check process and file ownership and stop on failure. They do not depend on source acknowledgments or graphics control metadata.

Processed screenshots use the same frame capture channel. When a graphics package declares `features.graphics.screenshotAPI: 1` and diagnostic capture is off, a live launch configures that channel in its final-image mode (`RESHADE_CAPTURE_FINAL=1`), which reads back only the final image of one requested frame, before the performance overlay is drawn. Until its image is published, a pending request makes the game present frames, so a game with processing captures its processed image. A Metal game whose live connection is dormant presents the requested frame through the hooks without processing and captures the game's own image, and a dormant OpenGL game reads its back buffer once, before that frame is flushed. Without a pending request, an idle or Off game keeps its dormant path.

A process starts polling the request file every 250 ms when its hooks first see Metal or OpenGL presentation work, including while they are dormant. A process that presents nothing, such as a helper process of a Wine game, therefore leaves the request to the game's own process. The launch record holds the channel as `screenshotCapture`. A runtime sandbox that moves the capture prefix and request file into its writable folder rewrites `screenshotCapture` in the launch record to the moved paths. To take a screenshot, the launcher writes the request file named there and waits up to five seconds for the completed capture. It then converts the captured pixels to PNG, moves the image to the screenshot folder and removes every intermediate file that the capture wrote.

Frame capture writes 8-bit SDR images and 16-bit HDR images. An HDR final image, meaning one whose transfer is PQ or HLG or whose peak luminance is above its reference white, is converted once with the output color encoder to full-range BT.2020 PQ in RGBA16Unorm, at the image's reference white and peak luminance, with the Preserve tone mapping and no dither. Any other image that is not already 8-bit RGB, such as an SDR RGBA16Float or 10-bit image, is converted once to 8-bit sRGB at the image's reference white with the Automatic output mapping. When the HDR conversion fails, the capture falls back to that 8-bit sRGB conversion, and the Automatic mapping compresses content above the reference white. Which image is converted depends on where processing runs. The shared presenter converts its drawable, described by the output color, while in-place processing converts the game's target, described by the game's image color. Diagnostic source images and drawable captures without an active effect use the same conversions with the source image color. When the game's command buffers do not retain their resources, the conversion resources are kept alive until the work completes.

Image encoding and file writing are kept out of Metal completion callbacks. Capture readbacks instead retain their Metal buffers until a private serial utility queue has written the pixels. The injected process writes the captured images as packed pixels to the intermediate files `-before.rgba` and `-after.rgba`, and final-image mode writes only the latter. Before saving a screenshot, the launcher converts these files to PNG, honoring their channel order and top-down or bottom-up row flags. An 8-bit image becomes an opaque 8-bit sRGB PNG with an `sRGB` chunk. A 16-bit HDR image becomes a 16-bit RGB PNG with a `cICP` chunk of 9, 16, 0 and 1, which marks BT.2020 primaries, the PQ transfer, RGB samples and full range. Diagnostic callers can convert the pair of files, including an optional `-neural-input.rgba` capture, with `screenshots.convert(prefix)`. Existing PNG captures from older graphics packages remain readable.

Each raw file starts with eight ASCII bytes, `MCLCAP01` for an 8-bit image or `MCLCAP02` for a 16-bit HDR image, followed by four little-endian 32-bit fields: width, height, packed row stride and flags. In the flags, bit 0 marks BGRA channel order, bit 1 marks bottom-up rows and bit 2 marks a 16-bit HDR image; all other bits are zero. An `MCLCAP01` image has four bytes per pixel and bit 2 clear. An `MCLCAP02` image has eight bytes per pixel, little-endian RGBA16Unorm in BT.2020 PQ, with bit 2 set and bit 0 clear, so its flags are 4 or 6. The stride is exactly the width times the bytes per pixel, and the fields are followed by exactly `stride × height` pixel bytes without padding. Each dimension is at most 32768, and an image contains at most 256 MiB of pixel bytes. Every request writes a temporary file of its own, which is renamed only after its complete contents have been written, so an abandoned request publishes no image.

When a warning or informational notification fails, including an asynchronous one that is rejected, the failure is handled apart from preparation and live updates, and rendering never waits for these notifications.

### Native prefix routing

Some renderers run part of the effect chain themselves, as the video module's mpv player does with [native video prefixes](SHADERS_AND_MEDIA.md#native-video-prefixes). For such a renderer, a module can export an optional asynchronous `prepareEffectsEntry(entry, context)` hook, which returns the entry that shared processing uses. The hook keeps the supplied entry and removes only the work that the original renderer performs. The launcher passes it to effect preparation as `options.prepareEffectsEntry` and uses `context.effectsEntry` for the same selection at launch. Main-process validation, live controls and shared plan preparation then work on the resulting runtime entry, while the saved game keeps its complete settings and plan. In this way, runtime-specific routing stays in the module.

## Renderer input declarations

A module may export `resolveGraphicsInputs(entry, context)` to describe the selected renderer's inputs and native controls. The inspector shows the same metadata together with runtime status. These status reads use installed metadata, so they never start a renderer or use the network. Graphics settings request the inputs from the game's backend worker, so reading game files never blocks the launcher's main process. While a game runs, the inputs recorded with its launch apply.

| Field | Meaning |
| --- | --- |
| `nativeVideo` | The renderer supplies decoded video planes. |
| `nativeSpatialMethods`, `nativeSpatialMethodLabels` | The original renderer's filter registry. |
| `sourceResolution` | `false`, or an explicit capability object with `heights` and `multipliers`. Its `control` can name a source adapter that the engine provides, and the optional `methods` and `methodLabels` list the source renderer's scaling filters and their display names. |
| `shaderBindingsNextLaunch`, `spatialBindingsNextLaunch` | Settings that are bound when the process starts. |
| `architecture` | The actual architecture, when it depends on the selected runtime. See [CPU architecture](#cpu-architecture). |

The `sourceResolution` field determines whether and how the game's render size can be changed. The part of a runtime integration that controls the render size is called its *source adapter*. Source sizing uses explicit heights or divisors, and runtimes that submit their own frames keep the divisors they advertise. Native window adapters without a `sourceResolution` declaration leave the game's render size alone, unless an included virtual-window adapter is advertised: `features.graphics.virtualWindowAPI: 1` exposes `GraphicsCapabilities.virtualWindow` and its supported source factors to the window host. Explicit source declarations take precedence over this virtual-window fallback, which `sourceResolution: false` and native video turn off. The UI reads these capabilities and never assumes that an arbitrary drawable can be resized.

Simple neural processing starts with an input height of 540 pixels. An available source adapter can apply that height before completed-frame processing, while smaller natural inputs keep their size. The `virtualSourceAutoAPI` and `automatic: true` source protocol remain for compatibility with older prepared components that read them, but they add no Automatic choice to Downsample. Automatic graph extents saved earlier become an explicit 540-pixel height instead, so the editor and execution use the same dimensions.

## Attachment hosts and CPU architecture

A runtime's `graphicsHost` declaration selects an *attachment host*, the way the processor attaches to that runtime. Each host determines where the frames come from and which side controls them:

| Host | Frame source | What each side controls |
| --- | --- | --- |
| `window` | Supported native Metal, hardware OpenGL, Core Animation and completed Quartz bitmap frames | The adapter selects the game window and holds its source until GPU reads finish. |
| `remote` | Hosted browser surfaces | The browser host supplies its surface and presentation timing. |
| `explicit` | Metal textures supplied by the runtime | The runtime controls ordering, frame IDs and submission. |
| `catalyst` | Supported iOS application Metal layers | The adapter preserves the drawable and application lifecycle. |

Each host's renderer connects through its declared presentation adapter. Inspection and extraction tools run independently of presentation hosts.

### CPU architecture

Rosetta changes the instruction set of the process that loads the graphics core, but the frame source stays the same. An x86_64 Wine or Java process can therefore use the same Metal or OpenGL adapters as an ARM64 process. Neural execution that exists only for ARM64 goes through the GPU helper, and MetalFX availability follows the actual device, OS and framework support. None of these declarations is a list of allowed renderers for each game.

Optional `graphicsArchitecture` metadata names a fixed host architecture, `arm64` or `x86_64`, for the process that loads the graphics library, which can be a translated Intel host. When the architecture depends on the selected runtime, renderer input metadata can also supply the actual `architecture`. Provider architecture checks use this value and never an engine name. The architecture is resolved as follows:

- A native app bundle without recorded executable metadata resolves its declared bundle executable before its Mach-O slices are inspected.
- Explicit renderer and runtime architecture declarations take precedence, and the architecture of a script stays unspecified when it is unknown.
- A scripted launcher can pass `{needsRosetta: true}` to `context.getGameEffectsEnvironment` or `context.applyGameEnvironment` before it prepares the child environment. This selects the Intel graphics setup for the actual translated executable, including optional provider validation.
- Changing the architecture after the game process is bound is rejected.

### Bitmap and OpenGL lifetime

Metal adapters hold GPU textures directly, and hardware OpenGL adapters use the shared texture and surface bridge. Software images, by contrast, start in CPU memory. For supported layers that publish `CGImage` contents, each completed software image is uploaded into a reusable IOSurface pool of fixed size, after which shader passes and intermediate images stay on the GPU. A bitmap image carries color, dimensions and timing but no scene depth or game motion vectors.

The Quartz adapter can also keep a full bitmap published during the selected content view's original `drawRect:` call and submit it after drawing finishes. Individual drawing calls and dirty rectangles are not complete frames, so they are not used. Direct Quartz drawing that does not publish through a supported frame adapter is not handled by that adapter.

Transfers to or from a multisampled OpenGL default framebuffer use identical source and destination rectangles. Orientation is changed in a separate blit between single-sample images, after resolving the captured framebuffer or before copying the processed image back.

When an OpenGL context is retired, the graphics layer releases its hold on the context before driver cleanup is attempted. If the context is unavailable, its GL objects are left to native destruction, and independent host resources are released without choosing another context for deletion.

## Completed-window capture

Some games present their window only through compositor surfaces that never hold the complete image. For them, a completed-window adapter captures the selected original window instead. This adapter combines an independent ScreenCaptureKit window source, GPU textures imported from the captured IOSurfaces and the shared processor, and on macOS 14.4 and later it can capture in the background. Its capture core, `window-stream.mm`, is also used for [picked windows and displays](#picked-windows-and-displays). Capture starts only while processing is active and does not need the game in front, although the game's own throttling can still limit how many fresh source frames arrive. A browser helper whose sandbox blocks the effects plan path is handled the same way. Since it accepts no native full-window surface, the completed-window adapter in the launcher-side process, which reads every edit, processes that window.

Capture is limited to the game window:

- macOS shows its screen-sharing indicator while the capture is active.
- The capture filter includes the selected game window and excludes child windows. Audio capture is off.
- Frames stay in local processing buffers. Ordinary playback sends nothing over the network and writes no recording file; explicit diagnostic capture can save local before and after images.
- On macOS 14.4 and later, the current process's windows are listed through Apple's consent-free API instead of broad desktop access. The indicator still shows an active capture stream.
- Turning off graphics processing or closing the game stops the capture session.

Each captured frame is cropped to its content. The content rectangle comes from the frame's `SCStreamFrameInfoContentRect` in points and is converted to pixels with its `SCStreamFrameInfoScaleFactor`, and `SCStreamFrameInfoContentScale` records how ScreenCaptureKit fitted the window into that content. Finite metadata that reaches outside the surface, which can happen while a window or display changes, keeps the full surface, and a frame with invalid metadata is dropped. A frame whose content covers its whole surface is processed directly from the imported IOSurface texture, without a copy; a smaller content rectangle is copied once into one of the adapter's GPU slots. Imported textures are kept for up to four recycled surfaces of the current geometry generation and reused when a surface returns. The stream has a queue depth of 4, and the adapter retains at most three of its frames at once: the image kept for replay, frames that GPU work still reads and the newest pending frame.

When capture fails, the original renderer keeps running and the failed session is released. A settled stream whose complete images keep a different pixel format from the configured window for one second also counts as a recoverable capture error. A temporary failure gets a limited number of recovery attempts before the original window returns. Configuration changes are serialized and coalesced to the latest window geometry, and obsolete callbacks cannot replace a newer configuration.

For Electron windows hosted by the launcher, an in-process visibility notification keeps source animations running while the processed output is visible. When that output is covered, minimized, disabled or closed, the previous background throttling policy is restored. The game keeps control of its own frame timing throughout.

GPU completion and physical presentation have separate callbacks, so covered output can complete processing without a positive drawable `presentedTime`. For diagnostics, the opt-in `FrameCapture` records the original and final pixels of one accepted source frame after its GPU work completes successfully.

## Picked windows and displays

Window graphics apply a graphics chain to the windows of other apps and to displays, each in its own library entry. [Window entries](../game-types/WINDOW.md) describes the Apply Graphics window, the entries and the saved chains, while this section covers the frame path.

The work is divided between two kinds of process, both running the `maclauncher-graphics-window` executable of the graphics runtime:

- A chain process for each library entry, which the `window` module's `capture` runtime starts as the entry's process. It loads the same `libreshade-macos.dylib` that a game loads, declares itself an explicit host and runs exactly one graphics chain with the code that games use: the plan, presets, providers and shared presenter. Only its frame input and its overlay window are specific to windows.
- One capture service for each MacLauncher process, run with `--capture-service ID`. It is the only process that calls ScreenCaptureKit (`SCShareableContent`, `SCStream`, `SCScreenshotManager` and `SCContentSharingPicker`), and it loads no graphics library and does no GPU work.

The chain process calls the window source ABI in `window-source.h` (`rsWindowSourceAPI` 2). It uses `rsWindowSourceCreate`, `rsWindowSourceSelect`, `rsWindowSourceSetOptions`, `rsWindowSourcePoll` and `rsWindowSourceDestroy` for each output, and `rsWindowSourceSetGeometry`, `rsWindowSourceSubmit`, `rsWindowSourceCaptureInterval`, `rsWindowSourceSetPointer` and `rsWindowSourceSetOverlays` for forwarded frames. A forwarded frame's `RSWindowSourceFrame` keeps its original 40-byte layout. When its `size` also covers the appended fields, it carries the content crop rectangle, content scale and scale factor, and a crop of zero width and height stands for the full surface. The window module offers window graphics only when the runtime record reports `features.graphics.windowSourceAPI` 2 and the helper executable is listed among the runtime's files and present on disk.

In the module's runtime entry, `graphicsHost: "window"` is kept for the capabilities it brings, such as live switching and adaptive generation. The entry also adds `explicitFrames: true`, so preparation sets the explicit host and installs no load-time hooks. Live edits, the effects plan, live controls and status all use the entry's ordinary launch binding.

Inside the chain process, the window source reuses the GPU slots, image limit, limited recovery attempts and shared presenter of the [completed-window adapter](#completed-window-capture), but not its stream. Color effects, scaling methods and image-pair frame generation therefore apply. The frame source is reported as `external-window`, and the module's renderer input declaration is `{source: "window-capture", sourceResolution: false, depth: false, motionVectors: false, methods: []}`, so source-resolution candidates and scene-input options are absent. In addition, the module's `generationDefaults: {keepStaticContent: true}` sets **Keep static content** on frame-generation rows added to a window entry.

### Transport

The capture service and its clients exchange raw Mach messages (`window-capture-wire.hpp`, version 2). Every message carries one port descriptor and one out-of-line JSON descriptor of at most 1 MiB, either of which may be empty. The receiver takes the sender's process ID from the message's audit trailer.

For each output that a chain process captures, the service keeps a *feed* with its own ScreenCaptureKit stream. A frame travels as the Mach port of its IOSurface, with a fixed `FrameInfo`: sequence, geometry generation, display time, surface width and height, and the content crop rectangle, content scale and scale factor that the service reads from the frame's metadata as the [completed-window adapter](#completed-window-capture) does. Each feed has at most two frames leased to its client and one pending. A newer frame replaces the pending one, and the pending frame is sent when the client releases a lease, provided it still belongs to the current geometry generation.

On the receiving side, the chain process imports each surface as a GPU texture and reuses the imports of recycled surfaces. A frame whose content covers the whole surface goes to the chain directly and is released after the image kept for replay and every GPU read of it are done. A smaller content rectangle is copied once into one of the chain process's own slots, and that frame is released when the copy completes. A frame is dropped when its generation differs from the current geometry, when its surface does not match its `FrameInfo` size or its crop rectangle lies outside the surface, or when its time is not newer than the previous frame's.

The service configures its streams with a queue depth of 4, a minimum frame interval of zero, 32-bit BGRA in sRGB, `scalesToFit` into a destination of the target's pixel size, the best capture resolution and child windows included. Because the minimum frame interval is zero, ScreenCaptureKit sends a frame only when the content changes. A period without frames therefore never counts as a stall: the chain keeps showing the last image and processes it again after a plan edit. The service passes a stream's frame on only when it is complete, has valid content geometry and the configured pixel format, and arrives no sooner than 0.75 of the plan's capture interval after the previous frame it sent. Frames that keep failing the geometry or format check for one second fail the feed.

### Geometry

A target can move, resize or change screens, so the service keeps its geometry current. It reads each target's bounds, owner, layer and on-screen state from window-server metadata ten times a second, and also at once when a frame's `SCStreamFrameInfoScreenRect` differs from the applied bounds. The backing scale and the display ID come from the screen with the largest intersection with the target.

Every change raises the feed's geometry generation. The service applies the new geometry to the stream with `updateConfiguration:`, one transaction at a time and coalescing later changes, and then sends a `geometry` event. This event arrives before any frame of that generation, and the chain process applies it on its main thread before it accepts the next frame. A configuration that has not settled within 2 seconds counts as an internal capture error, which the [capture lifecycle](#capture-lifecycle) handles.

### Filters

A ScreenCaptureKit stream captures what its content filter selects. A window or display chosen in the Apply Graphics window is opened by ID: the service finds it in `SCShareableContent`, which needs the Screen & System Audio Recording permission, and builds the filter itself, either a desktop-independent window filter or a display filter. Without that permission, an app chosen in the Apply Graphics window is opened by process ID instead, and the service presents `SCContentSharingPicker` in single-window mode, one pick at a time. The picker is limited to that app's windows: it excludes MacLauncher and every other app by bundle identifier, and every overlay by window number.

An application target can also be opened with `frontWindow`, as the shortcut opens it. When the permission is granted, such a target directly takes the app's frontmost on-screen window at layer 0 that measures at least 64 by 64 points; otherwise, it uses the picker. A window or display that another feed already captures is refused with "This window already has window graphics" or "This display already has window graphics".

Child windows need extra handling, because ScreenCaptureKit crops a window capture (`sourceRect`) from the combined bounds of the window and its child windows and reports no offset. A child window that reaches past the window's left or top edge would therefore move the image by that much. For an in-place window, the crop's origin is the window's offset within the bounds of the window and its known child windows, which keeps the image on the window. As soon as this origin changes (`RS_WINDOW_SOURCE_CROP_CHANGED`), the chain process sends it with the feed's options (`cropX`, `cropY`). The crop then takes effect with the next capture configuration, under a new geometry generation.

Frames captured between a child window's change and that configuration still show the image shifted. Until a frame of the new generation arrives, the overlay keeps its last processed image, for at most 0.5 seconds, and the chain drops frames that may be shifted:

- When the [stacking check](#overlay) finds a change that moves the image, the chain drops the frames of the current generation captured since the previous check. It also does so when the check finds a window of the target's app directly above the target that covers it, because that window may be a child window that is not yet known.
- A captured frame can show a new or moved child window before that check runs. For each frame, the chain therefore compares the window numbers above the target, leaving out overlays, and the bounds of the known child windows with those from the last check, and it drops the frame when they differ.

A window of the target's own app at a higher layer, such as a floating palette, can also overlap the target window. While one does, the service switches the feed to a display filter that includes only that app's windows (`initWithDisplay:includingApplications:exceptingWindows:`), cropped to the window's bounds on that display at the same size, so the palette appears in the processed image. The filter changes again when no such window overlaps the target any more, or when the window moves to another display.

Overlays are kept out of display captures in two ways: display filters exclude every overlay of every chain process by window (`initWithDisplay:excludingWindows:`), and each overlay also has `sharingType` set to none. Display filters also leave out the menu bar (`includeMenuBar` is off on macOS 14.2 or later).

To keep these exclusions current, each chain process sends the window numbers of its overlays to the service. When the set changes, the service waits until `SCShareableContent` lists every overlay, for at most 2 seconds, and then updates the filter of each display feed. Once every update has settled, it sends `excluded` with the acknowledged window numbers; with no display feed, it acknowledges at once. A new overlay stays hidden (`RS_WINDOW_SOURCE_HOLD`) until its number is acknowledged, so it never appears in a display capture, and while an overlay waits, its chain process sends its list again every 2 seconds. The acknowledged list also tells every chain process which windows are overlays (`rsWindowSourceSetOverlays`), so another entry's overlay never counts as a window that covers a target.

### Overlay

Each output's processed image appears in an overlay window over its target. This overlay is a borderless, nonactivating panel that never becomes key and always ignores the pointer, and its stacking depends on the kind of output. A display's overlay keeps the floating level, and a scaled overlay keeps its window's front level, described below. Both are ordered front with `orderFrontRegardless` when they appear and are never ordered against the target.

An in-place overlay, by contrast, stacks with its target. While no window covers the target, the overlay keeps the front level: the floating level, or one level above a target window that itself sits at the floating level or higher, below pop-up menus. A click or text selection that brings the target's window forward stays within the ordinary levels, so the overlay remains above it. While a window does cover the target, the overlay takes the target's level and is ordered directly above the target with `orderWindow:NSWindowAbove relativeTo:`. As a result, the covering window covers the effect as it covers the target.

A window covers the target when it is visible, overlaps the target, sits at or above the target's layer and below the front level, and is not an overlay. The target's child windows never cover it: the capture includes them, and the window server keeps a window's child windows directly above it, so nothing can be ordered between the two. An overlay ordered directly above the target consequently lands above the target's child windows, and the windows of the target's app listed between the overlay and the target are recorded as the target's child windows. Until then, windows of the target's app at the target's layer that lie within the target, such as sheets, count as child windows. The overlay is ordered only when its stacking differs from the one that the windows above the target ask for, and an order that has not applied yet shows in the next check, which orders the overlay again.

An in-place overlay also follows its target as it moves. While one shows, a display link on the overlay's screen (`displayLinkWithTarget:selector:`; before macOS 14, a timer at the screen's refresh rate from 30 to 120 times a second) runs on every display frame. Each run reads the target's bounds. When the target has moved and kept its size, the overlay is moved to the new bounds with `setFrame:display:`, without being ordered; a size change instead waits for the next geometry event, which also reconfigures the capture. The run then performs the stacking check, which also runs on each app activation. This check reads the window numbers above the target with `CGWindowListCreate`, and it reads those windows' descriptions when the list changes and at least every 50 ms, so a window that moves over the target is seen as well. Menus, the menu bar, the Dock and modal alerts stay above the overlay.

Whether an overlay shows is decided by polling. The chain process polls each output ten times a second from its latest geometry, and showing and hiding follow the entry alone: the overlay shows while effects are running, the chain process is not suspended, the target is on screen and the overlay's number is acknowledged. It hides while the target is off screen or minimized, and while the chain process is suspended for sleep, screen sleep or a user switch. Capture, however, continues while the target is covered, off screen or minimized, so the output is current when the target returns. When the overlay is shown but has not been on the active Space for three polls, it hides, and the state reason reads "The output cannot be shown on this full-screen Space". Each poll also passes the display that holds the largest part of the target to the presenter (`FramePresenter::setDisplay`), so presentation follows that display, and `setOutputVisible` stops presentation while the overlay is hidden.

The overlay joins all Spaces as a full-screen auxiliary window, so it can appear over full-screen apps. Because it hides whenever the target is not on screen, it still shows only in the Space where the target is visible. As a transient window, it is also hidden while Mission Control is open, and it stays out of the window cycle.

The overlay's content view hosts a container layer that holds the presenter's Metal layer. The presenter's layer stays hidden until the first accepted frame. Once shown, it keeps its last processed image through a change of size, crop or generation until a frame of the new geometry replaces it, as a game's presentation does while its window resizes. After a resize, that image is fitted to the overlay's new bounds.

For a window, the flag `RS_WINDOW_SOURCE_SCALED` selects the placement; a display is always in place:

- In place, the overlay covers the target in points, and the drawable uses the source's pixel extent at the target's display scale.
- Scaled output with scale 0, **Fit screen**, covers the target's screen: the visible frame, or the whole screen when the target's bounds equal it. With a scale factor F, the overlay instead covers the target enlarged by F about its center; F is reduced to fit the visible frame, and the area is moved inside it and aligned to whole points. Within that area, the presenter's layer is the largest centered rectangle with the target's aspect ratio, on whole points, and the bars around it show black once a frame is shown. The drawable is that rectangle at the screen's backing scale, so the presenter enlarges the source with the plan's spatial method.

### Scaled pointer

Scaled output also manages the pointer, so that clicks, drags and scrolls reach the target window itself. While a scaled overlay shows and the target's process is the frontmost app, an event tap at the session level keeps the pointer within the target's window-server bounds, moving it back to half a point inside an edge with `CGWarpMouseCursorPosition`. At the same time, `CGDisplayHideCursor` hides the system pointer. Because the chain process sets the connection property `SetsCursorInBackground`, the pointer stays hidden while the chain process runs in the background.

Instead of the system pointer, the overlay draws the arrow pointer at the point of the image that matches the pointer's position in the target. This drawn pointer shows while **Show pointer in picture** is on and the pointer is not held. An app that holds the pointer produces movement events with deltas but an unchanged position, and such events hide the drawn pointer until the position changes.

When the overlay hides or another app becomes active, the tap stops confining the pointer, and every hide is balanced with `CGDisplayShowCursor`. The tap needs the Accessibility permission, so the launcher asks for it when a scaled output is chosen and keeps In place while it is missing. The chain process also checks the permission with `CGPreflightPostEventAccess` before it sets `RS_WINDOW_SOURCE_SCALED`, and when the permission is missing, it reports `{"event":"output","output":"in-place"}` with the reason.

### Capture lifecycle

Capture runs only while processing is requested. Turning processing off sends `paused` in the feed's options, and the service then stops that stream but keeps its filter, so turning processing back on needs no new pick. The service also stops every stream while the Mac sleeps, its displays sleep, the screen is locked or the user session is inactive; it keeps the filters and starts the streams again afterwards.

When ScreenCaptureKit ends a stream with an interrupted or invalid application connection (`SCStreamErrorFailedApplicationConnectionInterrupted`, `SCStreamErrorFailedApplicationConnectionInvalid`) or an internal capture error, the stream starts again at once, at most once in 10 seconds. A second interruption within 10 seconds, however, closes the feed at once, and so does a missing Screen & System Audio Recording permission. Any other stream error closes the feed if the capture has not recovered after 5 seconds.

**Include pointer in capture** sets the stream's `showsCursor` through `updateConfiguration:` on the same stream, whereas a change of **Output** closes and reopens each feed of the entry, which delivers a first image for static content. The plan's [frame-rate cap](FRAME_API.md#source-frame-rate-cap) (`output.frameRateCap`) also limits capture, through the interval that the chain process sends in the feed's options. Both the service and the chain drop a frame that arrives sooner than 0.75 of the cap's interval after the previous accepted frame.

The chain process takes its target from its arguments: `--window N`, `--display N`, `--all-displays`, or `--pid N` with optional `--wait-window SECONDS` and `--front-window`. Its options are set by `--scaled` with optional `--scale F`, and by `--cursor`, `--capture-rate FPS` and `--library PATH`. Target IDs are `w` plus the window ID, `d` plus the display ID and `p` plus the process ID. All Displays opens one display feed for each active display; when the screen configuration changes, it adds a display connected during the session and releases a disconnected display's feed.

Option lines such as `{"cursor":false,"scaled":true,"scale":2,"pointer":true}` arrive on standard input and apply to every output. In addition, `{"pointer":"toggle"}` turns the drawn pointer off or on, and `{"remove":"ID"}` takes one output out. The launcher sends these lines from the game's worker, where the entry's process runs.

In the other direction, the chain process reports events as JSON lines on standard output, which the launcher writes to its main log, and it adds a heartbeat each second. A session that produces neither a heartbeat nor other output for more than five seconds is ended. Events that concern one output carry `"target"`: `targetAdded` when it joins, with its kind and IDs; `targetRemoved` when it leaves, with the reason, as when its window closes, its app quits, its display is disconnected or it is removed; `state`, with the state name, `revealed` and any reason; and `selected`, `output`, `picking`, `capture`, `waiting-for-window` and `failed`. The entry as a whole ends, reporting `stopped`, `closed` or `failed` with no target, when its last output leaves, on the stop line, at the end of standard input or on a signal.

The entry stops on the line `{"stop":true}`, at the end of standard input, and on SIGTERM, SIGINT and SIGHUP. In each case, the chain process closes its overlays and feeds, ends its connection to the service and waits up to 1.5 seconds for `rsWindowSourcePendingStops` to reach zero before it exits. **Stop** sends the stop line, then SIGTERM to the chain process if it is still running two seconds later, and SIGKILL two seconds after that. The captured app is never signalled.

### Capture service

Each MacLauncher process has a single capture service. Its ID is `org.maclauncher.window-capture.` followed by MacLauncher's process ID, which a chain process derives from its parent. Clients find the service through the rendezvous file `ID.lock` in the per-user temporary directory (`_CS_DARWIN_USER_TEMP_DIR`), which holds the service's unique bootstrap name and process ID. A client reads this file and connects with a hello, which the service answers when the client is the same executable and a child of the same MacLauncher process.

When no live service answers, the client starts one with `posix_spawn` in a new session (`POSIX_SPAWN_SETSID`), with standard input and output on `/dev/null` and an environment reduced to the home, temporary-directory, locale and time-zone variables and a fixed `PATH`. Because the service runs in its own session, stopping a chain process's process group never reaches it. A starting service first takes an exclusive `flock` on the rendezvous file. If another live service holds the lock, the new one exits; if a stopping service still holds it, the new one waits for the lock for up to 5 seconds. The service then registers a name made of the ID and a UUID with `bootstrap_register` and writes that name and its process ID to the file.

The service and its clients also watch each other. The service sends each client a heartbeat every second, and a chain process that receives none for 5 seconds sends SIGKILL to the service process, after checking its executable and start time. The chain process then treats the service as lost, as it does when the service exits. After a loss, it hides its overlays (`RS_WINDOW_SOURCE_HOLD`), connects to a running service or starts one, sends its overlays again and opens each feed again. A second loss within 10 seconds, however, ends the entry with "Window capture stopped unexpectedly".

On its side, the service learns that a client has exited from the client port's dead-name notification and closes that client's feeds. The service exits 2 seconds after its last client leaves, and also when MacLauncher's process is gone or has been replaced, which it checks every second with `kill` and the process start time from `proc_pidinfo`. SIGTERM, SIGINT and SIGHUP stop it as well.

When it stops, the service first withdraws its bootstrap name, then stops the catalog and closes every feed. It waits up to 1.5 seconds for every stream's `stopCaptureWithCompletionHandler:` completion and for its outstanding content requests, keeping each stream and its output retained until then, before it releases the lock and exits. A replacement service waits on the lock during that time, so two services never hold streams at once.

### Apply Graphics list

The Apply Graphics window also gets its list from the capture service, through `maclauncher-graphics-window --catalog --exclude-pid PID`, a relay client of the service. This relay asks the service for the catalog with thumbnails, writes the service's catalog events to standard output unchanged as JSON lines and keeps the service running while it is open. When the window closes, the launcher closes the relay's standard input and the relay exits; a relay still running two seconds later gets SIGTERM, and SIGKILL two seconds after that.

A relay starts only after the previous one has exited. Similarly, a session chosen while the window is open starts after the relay has exited, and the window then starts the relay again. When the relay loses its connection, it writes `{"event":"failed","reason":"The window list stopped"}` and connects again; a second loss ends it.

To build the catalog, the service reads `SCShareableContent` every two seconds, including windows that are not on screen, and writes the displays and the ordinary windows of regular apps when they change. A catalog event lists at most 96 windows in `windows`, in front-to-back order with each app's front window kept before the others, and the remaining windows in `more`. The launcher lists `windows` and turns up to 2,048 rows of `more` into search-only targets after their app's listed windows. The Apply Graphics window shows these targets only while its search matches them, with the app's icon in place of a thumbnail.

A read that fails for a reason other than the permission writes `{"event":"failed","reason":…}`, and the catalog keeps running. Until the next list arrives, the window shows the reason in place of the list. A window showing that reason, or the notice for a relay that ended with an error, starts the list again when it becomes active.

Before the first list that names an app, the catalog writes the app's icon from `NSWorkspace`, drawn at 32 points and 2x, as a PNG data URL. Thumbnails come from `SCScreenshotManager`, at most four at a time. Each is scaled to fit 400 by 250 pixels and sent as JPEG data only when the image changed, and a result later than two seconds is discarded. A newly listed window or display gets its thumbnail at once. After that, one repeat capture starts at most every half second, for the on-screen window or display whose last capture is oldest and at least five seconds old; as a result, a window that is off screen or minimized keeps its first thumbnail. The launcher passes thumbnails to the window in memory.

MacLauncher asks for the Screen & System Audio Recording permission itself, once, by requesting screen sources while macOS reports the permission as undetermined. The helper processes only check it, with `CGPreflightScreenCaptureAccess`. Without the permission, the catalog reports it and the relay exits, and when macOS reports the permission as denied, no relay starts.

### Output under resource pressure

During temporary resource pressure, in-place Metal and OpenGL effects reuse only an image whose GPU work has completed and which matches the current settings and output configuration. If the pressure lasts, processing switches to the original rendering until that configuration changes, so processed and untreated frames never alternate. OpenGL also reuses its fixed set of interop slots without waiting for command scheduling. None of this adds a window wrapper or a cap on the source frame rate.
